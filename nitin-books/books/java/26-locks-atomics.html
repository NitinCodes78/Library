Locks, Atomic Variables and volatile

Beyond synchronized: explicit locks, lock-free counters, and what volatile really does.

Why more locks?

Monitor locks are associated with every object, for a synchronized method or block. Suppose three objects obj1, obj2, obj3 all run the same synchronized critical section. Since they are different objects, they'll be able to access it in parallel.

But I want only one thread to access this critical section (they may be from different objects). So we have certain locks to tackle this, and they do not depend on an object like a synchronized method does. There are four types.

1. ReentrantLock

public class SharedResource {
    boolean isAvailable = false;

    public void produce(ReentrantLock lock) {      // no synchronized keyword
        try {
            lock.lock();
            isAvailable = true;
            Thread.sleep(4000);
        } catch (Exception e) {
        } finally {
            lock.unlock();                          // always unlock in finally
        }
    }
}

// main: one lock object shared by two different SharedResource objects
ReentrantLock lock = new ReentrantLock();
SharedResource r1 = new SharedResource();
Thread th1 = new Thread(() -> { r1.produce(lock); });
SharedResource r2 = new SharedResource();
Thread th2 = new Thread(() -> { r2.produce(lock); });   // on different objects
th1.start();  th2.start();
// we'll observe th2 runs 4 seconds later, after the lock is released

Even though r1 and r2 are different objects, the lock object is the one point of control.

Why "reentrant"?

The thread that already owns the lock can acquire it again without blocking itself (it keeps a hold count). Also unlike synchronized, it offers tryLock(), tryLock(timeout), lockInterruptibly() and a fairness option.

Shared lock and exclusive lock

  • Shared lock (S-lock) = read lock: multiple transactions can hold a shared lock on a data item simultaneously.
  • Exclusive lock (X-lock) = write lock: allows a transaction to both read and update a data item, preventing any other transaction from obtaining a shared or exclusive lock on that same data.

2. ReadWriteLock

Read lock: more than 1 thread can acquire the read lock. Write lock: only 1 thread can acquire the write lock.

ReadWriteLock lock = new ReentrantReadWriteLock();     // interface's implementation

lock.readLock().lock();      lock.writeLock().lock();
lock.readLock().unlock();    lock.writeLock().unlock();
// more threads can access at the same time     // only one thread at a time, others wait
// if this lock is the read lock

Suppose T1 and T2 are using readLock() and T3 wants writeLock() using the same lock object: T3 waits, even if the resource is different (SharedResource R1 vs R2). The lock object itself acts as the single point of synchronization control for any and all resources, regardless of the specific resource being accessed.

Mostly used when reads are more than writes.

3. StampedLock

Supports read/write lock functionality, plus optimistic read.

Optimistic concurrency, seen in a database

idnametyperow version
123SJStudent1
456RamStudent1
  1. Time 1: T1 and T2 both read id 123 (row version = 1).
  2. Time 2: T1: update table set type = 'teacher', version = version + 1 where id = 123 and version = 1. T2: update table set type = 'ex-student', version = version + 1 where id = 123 and version = 1.
  3. Time 3: say T2 physically reaches first: it updates 123 and the version becomes 2. So T1's update will be rolled back (it won't even be executed), because the version is now 2.

To use this in SQL we have to do the versioning manually. (Hibernate gives it through @Version.)

Side note: Postgres uses MVCC by default

Multi-Version Concurrency Control: updates don't lock reads, and reads don't block writes. It creates a new version (snapshot) of a row whenever it is updated, rather than overwriting the original data in place. Readers can view the old version without being blocked by writers.

For 2 concurrent writes: (i) the first writer reaches the row, locks it and creates a new version; (ii) the second writer hits the lock and pauses; (iii) the first writer commits; (iv) the second writer "wakes up", sees the new version and overwrites it with its own update. The "last one to finish" effectively wins. So we can use version = X to prevent this "last win" behaviour.

Because of MVCC, rows are never physically deleted or overwritten immediately. Instead they are marked as "dead" so older, long-running transactions can still see them if needed. The autovacuum daemon periodically wakes up and scans the table for those "dead tuples"; once a row version is no longer visible to any active transaction, vacuum marks that spot on the disk as reusable (new inserts happen there). We do a manual vacuum if there were massive data changes. The background autovacuum only marks space as "reusable" inside the existing file; it almost never returns space to the operating system. If a table ballooned to 100 GB and now it's 10 GB of real data, the disk will stay "90% empty air" until we run a manual VACUUM FULL.

Back to StampedLock

public class SharedResource {
    int a = 10;
    StampedLock lock = new StampedLock();

    // optimistic READ: no lock taken
    public int consumer() {
        long stamp = lock.tryOptimisticRead();   // returns a stamp: similar to a version
        int local = a;                           // read the fields into local variables
        if (!lock.validate(stamp)) {             // true if no writer came in since the stamp
            stamp = lock.readLock();             // a writer did: fall back to a real read lock
            try {
                local = a;                       // and read again
            } finally {
                lock.unlockRead(stamp);
            }
        }
        return local;
    }

    // WRITE: a real lock (the write lock call returns a stamp)
    public void producer() {
        long stamp = lock.writeLock();
        try {
            a = 11;
        } finally {
            lock.unlockWrite(stamp);
        }
    }
}

The optimistic read did no lock/unlock like the others do: it takes a stamp, reads, and then only checks whether a writer interfered. That is what makes it fast when writes are rare. Optimistic locking is meant for reading: never write to shared state under an optimistic stamp, because another thread could see your half-done write before you "roll back". Use writeLock() for updates. StampedLock is also not reentrant.

4. Semaphore

A semaphore holds a number of permits. Suppose 4 threads try to access this: the permit value is 2, so only 2 threads will be able to access it; the other 2 wait until those are finished.

boolean flag = false;
Semaphore lock = new Semaphore(2);       // permits

try {
    lock.acquire();
    flag = true;
    Thread.sleep(4000);
} catch (Exception e) {
} finally {
    lock.release();
}

Just like we used wait(), notify(), notifyAll() in a monitor lock, for these locks we can use await(), signal() and signalAll() (from a Condition created with lock.newCondition()) for inter-thread communication.

CAS (compare-and-swap)

CAS is very similar to optimistic concurrency control (mostly with DB). The CAS technique:

  1. It's a low-level operation, supported by the CPU.
  2. It's atomic, and all modern processors support it.

It involves 3 main parameters:

  1. Memory location: where the variable is stored.
  2. Expected value: the value which should be present in the memory.
  3. New value: the new value to be written to the memory, written only if the current value equals the expected value.
CAS(memory, expectedValue, newValue) {
    (i)   load / read the variable at memory M
    (ii)  compare the memory data vs expected
    (iii) update the memory data to new, if current == expected
}

The ABA problem

10changed to12changed back10

CAS(memory, 10, 15): ideally the expected value is 10, but the memory went from 10 to 12 to 10. That's not exactly the same situation (something happened in between), yet CAS sees 10 and succeeds. The ABA problem in this scenario is solved using a version / timestamp (Java: AtomicStampedReference).

Atomic variables

Atomic means single or "all or nothing". int a = 10; is an atomic operation: a single operation, so it will be consistent regardless of the number of threads doing it.

public class SharedResource {
    int counter;
    public void increment() { counter++; }     // NOT atomic: 3 operations
    public int get() { return counter; }
}
// (i) load the counter value  (ii) add 1  (iii) assign it back

If two threads try to increment at exactly the same time, there may be data loss:

SharedResource resource = new SharedResource();
Thread t1 = new Thread(() -> { for (int i = 0; i < 200; i++) resource.increment(); });
Thread t2 = new Thread(() -> { for (int i = 0; i < 200; i++) resource.increment(); });
t1.start();  t2.start();
// output: 371 (should have been 400): two threads may have incremented the same value at exactly the same time

Two solutions:

// (i) using a lock like synchronized
public synchronized void increment() { counter++; }

// (ii) using a lock-free operation like AtomicInteger (internally CAS)
public class SharedResource {
    AtomicInteger counter = new AtomicInteger(0);
    public void increment() { counter.incrementAndGet(); }     // uses compare and swap
    public int get() { return counter.get(); }
}

Internally incrementAndGet does a CAS loop (read, modify, update):

do {
    // (i) read: it's 10    (ii) modify: 11    (iii) value is now 11
} while (!cas(memory, expected, newValue));
  1. For T1, the value becomes 11 as shown above.
  2. Now T2 had also come at the same time. In the while, the CAS function returns false, because expected is 10 but the current value is 11. So it goes in the do block again, and expected is now 11. It gets updated to 12.

If it were not atomic, the second thread would have set it to 11 only (10 + 1). Atomic classes also have getAndIncrement(), addAndGet(n), compareAndSet(expected, new).

volatile

Atomic is thread-safe, whereas volatile has no relation with concurrency as such. So what's volatile?

T1 works here
CPU core 2
T2 working here
L1 cache
L1 cache
L2 cache
Memory (RAM)

T1 updates x = 11 and it's in its own L1 cache currently. T2 also tries to increment x: it checks its own L1 and L2 caches, the value of x isn't present there; in memory it's 10, so it updates to 11, i.e. data loss, because the cache has not been synced. (Modern hardware keeps caches coherent, but the compiler or CPU may still keep a value in a register and reorder instructions, which gives the same symptom.)

volatile guarantees visibility (a write is seen by later reads in other threads) and ordering (no reordering across it), using memory barriers, which makes it slower than a normal variable. It does not make compound actions atomic: volatile int counter; counter++; still loses updates, so use AtomicInteger for that. Good uses of volatile: a stop flag, or the singleton instance in double-checked locking.

Interview corner
synchronized vs ReentrantLock?

ReentrantLock adds tryLock, timeouts, interruptible locking, fairness and multiple Conditions, but you must unlock in finally yourself.

Why is i++ not thread-safe?

It is read-modify-write: three steps that can interleave. Fix with synchronized, a lock or AtomicInteger.

volatile vs atomic?

volatile gives visibility and ordering for a single read or write. Atomic classes also make read-modify-write (increment, compareAndSet) atomic via CAS.

What is the ABA problem?

A value goes A to B and back to A, so CAS thinks nothing changed. Solved by versioning, e.g. AtomicStampedReference.

When would you use a Semaphore?

To cap concurrent access to N, e.g. at most 10 simultaneous DB connections or API calls.
