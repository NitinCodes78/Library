String and the String Pool

Why String is special: immutable, pooled, and the classic == vs equals trap.

What makes String special

  • Strings are immutable.
  • Written as string literals ("hello").
  • String is non-primitive. It has inbuilt Java methods like length(), charAt().

The String Constant Pool

Inside heap memory there is a special area, the String Constant Pool.

String s1 = "hello";     // literal: goes into the pool
String s2 = "hello";     // checks if already present → reuses it
s1
s2
Heap → String Constant Pool
"hello"

s1 == s2 returns true: both point to the same object.

new String(...) is different

String s3 = new String("hello");   // not a literal any more

It creates an object in the heap, outside the pool, at a different address.

s1 == s3falsedifferent address in memory

Why "immutable" matters

s1 = "hello world";
s1 = "SJ";

The pool now holds "hello", "hello world" and "SJ". The old values are still present: a String object is never changed, s1 just points to a new one. Literals live in the String Constant Pool.

Good to know
  • Immutability is why pooling is safe: if one reference could change the shared "hello", every other reference would see it.
  • Also why String is safe as a HashMap key and across threads.
  • For lots of changes, use StringBuilder (fast, not thread-safe) or StringBuffer (thread-safe), instead of making many String objects.
  • s3.intern() returns the pooled copy of a string.

Interview corner
== vs equals() on strings?

== compares references (same object?). equals() compares content. Always use equals() for text.

How many objects does new String("hello") create?

Up to two: the literal "hello" in the pool (if not already there) and a new String object on the heap.

Why is String immutable?

For pooling, security, thread safety and safe hashing. It lets Java share one object among many references.
