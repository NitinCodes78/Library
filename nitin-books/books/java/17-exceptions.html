Exception Handling

What happens when things go wrong at runtime, and how to deal with it.

What is an exception?

An event that occurs during the execution of the program. It creates an Exception object that contains the type of exception, a message, the stack trace, etc.

How an exception travels

maincallsmethod1callsmethod2

Suppose the exception occurs in method2. Can method2 handle it? If no, it goes to method1, which called method2. If method1 also can't handle it, it goes to main. If nobody handles it, the runtime system terminates the program and prints the stack trace: method2, method1, main.

Error indicates serious, unrecoverable system-level problems that the application should not try to catch, such as running out of memory or a JVM crash. Exception indicates that the application might want to catch it and allow the program to keep running, such as "file not found".

What "checked" means for you

A checked exception must be handled, either by:

  1. a try/catch block, or
  2. declaring throws on the method, which tells the caller to handle it. We delegate the handling to the caller. Ultimately, somebody has to use try/catch to really handle it.

If you use throws even on main and don't handle it, the exception bubbles up to the JVM (no class above main), and the JVM prints "Exception in thread "main" java.lang.ClassNotFoundException ... at ... at ...".

An unchecked exception compiles fine. It's good to handle but not a compulsion, and the compiler won't force you.

public static void method1(String name) throws ArithmeticException {
    // no need to handle it via try-catch: it's a runtime exception
}

try / catch / finally

It can be try/catch, try/finally or try/catch/finally.

void method1() {
    FileReader reader = new FileReader("test.txt");
    // either use throws FileNotFoundException, or use try/catch else the compile will fail
}

If we add throws, it becomes the responsibility of the caller to handle the exception.

Rule 1: a catch can only catch what the try can throw

try {
    // something related to file code should be here if we are catching it
} catch (FileNotFoundException e) {
    // if the try block can't throw FileNotFoundException, the compiler won't compile this
}

Rule 2: throws on a method is allowed even if nothing throws

void method1() throws FileNotFoundException {
    System.out.println("Hey");          // contrary to the above, the code compiles successfully
}

throws is a declaration that becomes part of the method's contract, not just a warning. The caller of method1() must still handle FileNotFoundException (try/catch or its own throws). Rule 1 applies only to checked exceptions; you can always catch Exception, Throwable or any unchecked exception.

Multiple catch blocks

Exception is the parent of all exceptions.

try {
} catch (Exception e) {
    // will work for any kind of exception: handles everything
}

Wrong syntax, the parent first:

try {
} catch (Exception exp) {
} catch (ClassNotFoundException exp) {   // ✗ compile error: Exception already eats every exception,
}                                        //   so this is useless, already caught above

Always put the child (specific) exceptions first, the parent last. You can also catch multiple exceptions in one block:

try {
} catch (ClassNotFoundException | InterruptedException e) {
}

The real root of the hierarchy is Throwable, with Exception and Error below it. So catch (Exception e) does not catch an Error such as OutOfMemoryError, which is intended.

The finally block

  1. Can be used after try or after a catch block.
  2. It always gets executed, even if you return from the try block or from the catch block.
  3. At most, we can add 1 finally block.
  4. Mostly used for closing resources (like closing the streams opened for file reading), adding logs etc.
  5. It doesn't get executed in JVM-related issues like out of memory, the system shutting down (e.g. System.exit()), or the process being forcefully killed.
  6. It can't be used like a catch block to catch or handle exceptions.
Good to know: try-with-resources 
try (FileReader reader = new FileReader("test.txt")) {
    // use reader
}   // closed automatically, no finally needed

Anything implementing AutoCloseable works. Prefer it over a manual finally for closing.

throw and re-throw

throw is also used to re-throw the exception (for bubble-up purposes):

try {
    // ...
} catch (ClassNotFoundException e) {
    throw e;                     // re-throw
}

Custom exception

public class MyCustomException extends Exception {
    MyCustomException(String message) {
        super(message);
    }
}

throw new MyCustomException("Some issue");

Extending Exception makes it checked. Extend RuntimeException to make it unchecked.

Why checked exceptions cost

Exception handling is a little expensive if the stack trace is huge and it's not handled at the parent class. For example, with a chain from Method 100 down to Method 1: if the exception occurs in Method 100 and it is a checked one, the compiler won't even let it compile unless each of the 100 methods handles it or uses the throws keyword. That is a lot of overhead. Runtime exceptions avoid this, which is why many modern frameworks (Spring included) prefer unchecked exceptions.

Interview corner
Checked vs unchecked?

Checked are verified by the compiler and must be handled or declared (IOException, SQLException). Unchecked extend RuntimeException and are not forced (NullPointerException).

Does finally run if there's a return in try?

Yes, finally runs just before the method returns. If finally itself returns, it overrides the earlier return.

Error vs Exception?

Error: JVM-level, not meant to be caught (OutOfMemoryError, StackOverflowError). Exception: application-level, often recoverable.

When does finally not run?

System.exit(), JVM crash, or the process being killed.

throw vs throws?

throw raises an exception object; throws declares one in the method signature.
