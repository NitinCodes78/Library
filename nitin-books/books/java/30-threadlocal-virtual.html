ThreadLocal and Virtual Threads

Per-thread data, and Java's lightweight threads (JDK 21).

ThreadLocal

  1. The ThreadLocal class provides access to thread-local variables.
  2. This thread-local variable holds the value for a particular thread.
  3. That means each thread has its own copy of the thread-local variable.
  4. We need only 1 object of the ThreadLocal class, and each thread can use it to set and get its own thread variable.
ThreadLocal<String> threadLocalObj = new ThreadLocal<>();

// main thread is currently executing
threadLocalObj.set(Thread.currentThread().getName());     // main thread's variable is set to its name

Thread thread1 = new Thread(() -> {
    threadLocalObj.set(Thread.currentThread().getName());   // same object, but sets the variable of thread1
    System.out.println("Task1");
});
// internally it stores in a map, for different threads

Remember to clean up if reusing the thread

Suppose thread1 was doing task1 and it had data for task1; then it takes up task4, and the leftover data may cause problems. In a pool, threads are reused, so always clean up:

poolObj.submit(() -> {
    threadLocalObj.set("value");
    try {
        // my work
    } finally {
        threadLocalObj.remove();      // always remove
    }
});
Where it is used

Per-request context in web apps (user id, trace id, transaction), SimpleDateFormat (not thread-safe), Spring's SecurityContextHolder and transaction synchronisation. Forgetting remove() in a pool causes data leaks between requests and memory leaks.

Virtual thread vs platform thread

Motto of virtual threads: to get higher throughput, not lower latency (let's say more tasks per second).

Platform (native) thread

Thread t1 = new Thread(() -> { ... });
t1.start();          // JVM tells the system: hey OS, create one native thread
Platform thread1 : 1Native / OS thread

A platform thread is managed by the JVM, but the JVM is just a wrapper of the OS thread.

Disadvantages

  1. It's slow. Thread creation takes time; that's why we used the thread pool executor, so that we don't create threads again and again. When we call t1.start(), Java calls the OS (a system call: expensive). Even with a pool executor we have to create the threads some time (min-max pool).
  2. Blocking wastes the OS thread. T1 (platform thread) performs a DB call (let's say 4 seconds): this T1 is just a wrapper to an OS thread, so the OS thread is just waiting for those 4 seconds.

  • Lightweight: unlike traditional "platform" threads, which are 1:1 wrappers around OS threads and consume about 1 MB of stack memory each, virtual threads are managed by the JVM and start with a footprint of only a few hundred bytes.
  • Scalable: you can create millions of virtual threads on a single JVM, whereas platform threads are limited to a few thousand by OS resources.

How they work

Virtual threads run on a small pool of platform threads called carrier threads.

  • Mounting: when a virtual thread has work to do, the JVM "mounts" it onto a carrier thread.
  • Unmounting: when the virtual thread performs a blocking operation (like a database call or network request), the JVM "unmounts" it and stores its state in the heap. This frees the carrier thread to execute other virtual threads.

The actual "waiting" for data is handled by a background thread in the JVM, often called the Read-Poller. Once the OS signals that the data is ready (e.g. the database sent the response), the poller notifies the JVM scheduler. The scheduler then takes the virtual thread's state from the heap, remounts it onto any available carrier thread, and the code continues exactly where it left off.

Good to know
  • Don't pool virtual threads. They are cheap, so create one per task. Pools exist to ration expensive resources (use a Semaphore to limit access to a scarce downstream resource).
  • Virtual threads help I/O-bound work (many waiting requests). They do nothing for CPU-bound work.
  • Pinning: blocking inside a synchronized block (before JDK 24) can pin the virtual thread to its carrier. Prefer ReentrantLock there.
  • Spring Boot 3.2+ can turn them on with spring.threads.virtual.enabled=true.
  • Virtual threads are always daemon threads.
Interview corner
Platform vs virtual threads?

Platform threads are 1:1 with OS threads and heavy; virtual threads are JVM-managed, tiny, and release the carrier while blocked.

Do virtual threads make code faster?

They raise throughput for blocking I/O workloads, not single-task latency or CPU-bound speed.

Why must ThreadLocal be cleaned up in thread pools?

Pool threads are reused, so stale values leak into the next task and can cause memory leaks.
