Thread implements Runnable.

Way 1: implement Runnable

Step 1: create a Runnable object: create a class that implements Runnable, and implement the run() method to tell the task what the thread has to do.

public class MultiThreading implements Runnable {
    @Override
    public void run() {
        System.out.println("Code by thread: " + Thread.currentThread().getName());
    }
}

Step 2: start the thread: create an instance of the class that implements Runnable, pass the Runnable object to the Thread constructor, and start the thread.

MultiThreading runnableObj = new MultiThreading();
Thread thread = new Thread(runnableObj);       // constructor param
thread.start();
System.out.println(Thread.currentThread().getName());     // main

start() internally calls the run() method: it checks that the Runnable object is not null (a child class implementing it is there) and then executes its run(). This is useful, as our class can do a lot of other stuff other than just implementing the run() method.

Way 2: extend Thread

Why two methods?

  • Java does not support multiple inheritance. If my class already extends some other class, then I cannot extend Thread. That is why we have Runnable.
  • When I implement Runnable, it just defines the task (run() logic); we pass it to a Thread object. Our class is not a Thread.

So: Runnable defines the task; Thread handles thread mechanics. We separate what to do and how to run it: a good OOP principle.

Always start(), never run(). Calling thread.run() directly just executes the method like a normal call on the current thread. Only start() creates a new thread. Calling start() twice throws IllegalThreadStateException.

The lambda way

Since Runnable is a functional interface: new Thread(() -> System.out.println("hi")).start();

StateDescription
NewThe thread has been created but not started. Just an object in memory.
RunnableThe thread is ready to run and waiting for CPU time.
RunningWhen the thread starts executing its code.
BlockedThe thread wants to enter a synchronized block or method whose monitor lock is held by another thread, so it has to wait. It keeps the locks it already holds. (A thread waiting on I/O, like reading a file or database, still shows as RUNNABLE.)
WaitingThe thread goes into this state when we call the wait() method, which makes it non-runnable. It goes back to runnable once we call notify() or notifyAll(). We can explicitly call this until we call notify.
Timed waitingThe thread waits for a specific period of time and comes back to the runnable state after specific conditions are met, like sleep(), join(). Does not release any monitor locks.
TerminatedThe life of the thread is completed; it can't be started again.
  • Java officially has 6 states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. "Running" is not a separate state: it is part of RUNNABLE.
  • BLOCKED means specifically "waiting to enter a synchronized block/method (monitor lock)". A thread waiting for I/O still shows as RUNNABLE.
  • A BLOCKED thread keeps the locks it already holds (that is how deadlocks happen). wait() releases only the monitor of the object it is called on, not other locks it holds.

join()

The join method pauses the execution of the current (calling) thread until the thread on which join() was called completes its task. It ensures sequential, synchronized execution, allowing one thread to wait for another to finish before proceeding.

Thread t1 = new Thread(new MyRunnable());
t1.start();
t1.join();      // main thread waits here until t1 finishes
System.out.println("t1 is finished, now proceeding");

wait() vs sleep()

wait() is used for inter-thread communication and releases the object lock, while sleep() is used for a simple time-based pause and does not release the lock it holds.

Monitor lock

A built-in synchronization mechanism associated with every object, ensuring that only one thread can execute a synchronized method or block for that object at a time. When a thread enters a synchronized block or method, it must first acquire the monitor lock of the object. As long as one thread owns the lock, any other thread attempting to acquire the same lock will be blocked. It helps to make sure that only 1 thread goes inside the particular section of code.

public class MonitorLockExample {
    public synchronized void task1() {
        try {
            System.out.println("inside task1");
            Thread.sleep(10000);
        } catch (Exception e) { }
    }

    public void task2() {
        System.out.println("task2, but before synchronized");
        synchronized (this) {
            System.out.println("task 2, inside synchronized");
        }
    }

    public void task3() {
        System.out.println("task3");
    }
}

// main class
MonitorLockExample obj = new MonitorLockExample();
Thread t1 = new Thread(() -> { obj.task1(); });     // Thread contains one abstract method run(): the lambda way
Thread t2 = new Thread(() -> { obj.task2(); });
Thread t3 = new Thread(() -> { obj.task3(); });
t1.start();  t2.start();  t3.start();
Output:
inside task1
task3
task2, but before synchronized
(10 seconds pass: task1 completed)
task 2, inside synchronized

The monitor lock was acquired by task1. The lock was released, then task2 got into the monitor lock.

Key takeaway

A synchronized method does not lock the entire object, it only blocks access to other synchronized blocks on the same object. If you have a synchronized withdraw() and a non-synchronized checkBalance(), a user can still check the balance while a withdraw is happening. If you want checkBalance to wait, you must also mark it synchronized. Synchronized only makes the code blocks thread-safe relative to each other.

Producer-consumer with wait / notify

A classic scenario for using wait(): two threads must coordinate to share a fixed-size buffer (like a queue). A shared buffer with a capacity of 1: the producer wants to add an item to the buffer; if the buffer is already full, it must wait until the consumer removes the item. The consumer wants to take an item; if the buffer is empty, it must wait() until the producer adds something.

public class SharedResource {
    boolean isItemPresent = false;

    public synchronized void addItem() {       // working on the same resource, so monitor lock comes into play
        isItemPresent = true;
        notifyAll();                           // any thread on wait for this will continue
    }

    public synchronized void consumeItem() {
        while (!isItemPresent) {               // while, not if: re-check after every wake-up
            try {
                wait();                        // releases the monitor lock
            } catch (InterruptedException e) { }
        }
        isItemPresent = false;
    }
}

// main
SharedResource sharedResourceObj = new SharedResource();
Thread producerThread = new Thread(() -> { sharedResourceObj.addItem(); });
Thread consumerThread = new Thread(() -> { sharedResourceObj.consumeItem(); });
producerThread.start();
consumerThread.start();

This can be done by creating separate classes implementing Runnable. You can also add a put condition (the buffer-full wait) in the producer, for example when the queue size is greater than 1, while the buffer can hold more items.

Wrap wait() in a while loop, not an if. A waiting thread can wake up without the condition being true (spurious wakeup, or another consumer took the item first), so the safe pattern is while (!isItemPresent) { wait(); }, which re-checks the condition each time. Also remember: wait(), notify() and notifyAll() must be called while holding that object's monitor, or you get IllegalMonitorStateException.

Why are stop(), suspend() and resume() deprecated?

  • stop: terminates the thread abruptly. No lock release, no resource clean-up happens.
  • suspend: puts the thread on hold temporarily. No lock is released either.
  • resume: used to resume the execution of a suspended thread.

Both these operations could lead to issues like deadlock. The safe way to stop a thread is to set a flag (or call interrupt()) and let the thread exit by itself.

Thread priority

  • Priorities are integers ranging from 1 to 10: 1 is low priority, 10 is the highest.
  • Even if we set the thread priority at creation, it is not guaranteed to follow any specific order: it's just a hint to the thread scheduler about which to execute next (not a strict rule). We can't rely on this.
  • When a new thread is created, it inherits the priority of its parent thread.
  • We can set a custom priority using setPriority(int priority).

Daemon thread

Something which runs async, in the background. If only daemon threads remain, the JVM will exit and return. They are low-priority background threads designed for non-critical supporting tasks, such as garbage collection and monitoring, and are automatically terminated by the JVM when all user threads finish.

    Thread t1 = new Thread(() -> { /* time-consuming task */ });
    t1.setDaemon(true);
    t1.start();
    System.out.println("main finished");
}   // main method finished: JVM won't wait for t1 to finish, and will exit
Good to know

setDaemon(true) must be called before start(), or you get IllegalThreadStateException.

Interview corner
Runnable vs extending Thread?

Prefer Runnable: it keeps the task separate from the thread, lets your class extend something else, and works with executors.

start() vs run()?

start() creates a new thread that calls run(); calling run() directly just runs it on the caller's thread.

wait() vs sleep()?

wait releases the monitor and is woken by notify (Object method, needs synchronized). sleep keeps all locks and wakes after the time (Thread static method).

What does synchronized actually lock?

The monitor of one object (or the Class object for static methods). Different objects don't block each other.

What is a daemon thread?

A background service thread that does not keep the JVM alive, e.g. the garbage collector.
