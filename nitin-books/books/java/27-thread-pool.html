Thread Pool and ThreadPoolExecutor

Reuse workers instead of creating a thread for every task.

What is a thread pool?

  • A collection of threads (aka workers) which are available to perform the submitted tasks.
  • Once a task is completed, the worker thread gets back to the pool and waits for a new task to be assigned.
  • That means threads can be reused. Otherwise we had to create them manually using new Thread(), which takes some time. Via a thread pool, we have already created the threads.

Advantages of a thread pool

BenefitWhy
Thread creation time is savedWhen each thread is created, space is allocated to it (stack, program counter etc.) and this takes time. With a pool this is avoided by reusing the thread.
Overhead of managing the thread lifecycle is removedA thread has different states like running, waiting, terminated; managing thread state adds complexity. The pool abstracts this management away.
Increased performanceMore threads means more context-switching time. With control over thread creation, excess context switching can be avoided.

ThreadPoolExecutor

It helps to create a customizable thread pool.

How it works: a worked scenario

Say core (min) pool size = 3, max pool size = 5, queue size = 5.

  1. Tasks 1 to 3 come: each gets a free thread (T1, T2, T3). Check whether any thread is free in the pool.
  2. Tasks 4 to 8 come, all 3 threads are busy: they go in the queue (size = 5), no new thread is made.
  3. Task 9 comes, the pool has all its threads occupied and the queue is also full. Since max pool size = 5, one more thread T4 gets in the pool and takes task 9.
  4. Task 10 comes: a new thread T5 takes task 10.
  5. Now we'll have to reject task 11 if it comes, as max pool size has been reached and the queue is full.
  6. Suppose T3 is now free: then T3 will take task 4 from the queue.

ParameterMeaning
corePoolSizeNumber of threads initially created and kept in the pool, even if they are idle.
allowCoreThreadTimeOut (not a constructor parameter)If this property is set to TRUE (by default it's FALSE), idle core threads are kept alive only for the time specified by keepAliveTime, else they get terminated.
keepAliveTimeThreads which are idle get terminated after this time.
TimeUnitUnit for the keepAliveTime: milliseconds, seconds, hours etc.
maxPoolSizeMaximum number of threads allowed in a pool. If number of threads == corePoolSize and the queue is also full, then new threads are created (till it's less than maxPoolSize). Excess threads remain in the pool until the pool is shut down, or, if allowCoreThreadTimeOut is true, they get terminated after remaining idle for keepAliveTime.
BlockingQueueQueue used to hold tasks before they get picked by a worker thread.
ThreadFactoryFactory for creating a new thread. We can give a custom thread name, custom priority, set the daemon flag etc.
RejectedExecutionHandlerHandler for tasks that cannot be accepted by the pool. Generally logging logic can be put here, for debugging purposes.
Why queue first, not a new thread?

We put tasks in the queue and do not get new threads in the pool till the queue is full: that's the intended behaviour. Say min pool size = 3 and max = 5 and a 4th task comes: we don't get a new thread but put it in the queue, because we assume the 3 threads are consumed only on average. After task 4 is finished, there is no thread 4 sitting idle in the pool.

  • Bounded queue: queue with a fixed capacity, like ArrayBlockingQueue. Gives you full control over how many tasks wait in the queue.
  • Unbounded queue: queue with no fixed capacity, like LinkedBlockingQueue.

An unbounded queue means maxPoolSize is never used. The pool only grows beyond core size when the queue is full. With an unbounded queue it is never full, so the pool stays at corePoolSize and a task flood just piles up in memory (a classic production out-of-memory cause).

RejectedExecutionHandler policies

PolicyWhat it does
new ThreadPoolExecutor.AbortPolicy()Throws RejectedExecutionException (the default).
new ThreadPoolExecutor.CallerRunsPolicy()Executes the rejected task in the caller thread (the thread that attempted to submit the task). This also slows the producer down naturally.
new ThreadPoolExecutor.DiscardPolicy()Silently discards the rejected task, without throwing any exception.
new ThreadPoolExecutor.DiscardOldestPolicy()Discards the oldest task in the queue, to accommodate the new task.

Lifecycle of a ThreadPoolExecutor

Runningshutdown()Shutdownqueue drainedTerminated
RunningshutdownNow()Stopall stoppedTerminated
  • Running: executor is in running state and the submit() method is used to add new tasks.
  • Shutdown: executor does not accept new tasks, but continues to process existing tasks; once existing tasks are finished, the executor moves to the terminated state. Method used: shutdown().
  • Stop (force shutdown): executor doesn't accept new tasks. It also forcefully stops all the tasks which are currently running. Moves to terminated state once fully shut down. Method used: shutdownNow().
  • Terminated: end of life for the particular ThreadPoolExecutor. The isTerminated() method can be used to check if the pool is terminated or not.
Good to know

shutdownNow() interrupts running tasks and returns the list of tasks that never started; tasks must respond to interruption to actually stop. Use awaitTermination(timeout, unit) after shutdown() to wait for completion. Forgetting to shut a pool down keeps the JVM alive, because its core threads are non-daemon.

Why core pool size 2 and not 10 or 15?

Generally the pool's min and max size depend on various factors:

  • CPU cores
  • JVM memory
  • Task nature: CPU-intensive or I/O-intensive. For CPU-bound work use fewer threads (waiting time is low). For I/O-bound work use more threads, as they spend more time on a DB call and the other tasks should not wait.
  • Concurrency requirement: do we want high, medium or low concurrency?
  • Memory required to process a request
  • Throughput etc.

And it's an iterative process to update the min and max values based on monitoring.

Rule of thumb

CPU-bound: threads ≈ number of cores (or cores + 1). I/O-bound: cores × (1 + wait time / compute time).

Interview corner
Order in which ThreadPoolExecutor uses core threads, queue and extra threads?

Core threads first, then the queue, then extra threads up to max, then the rejection handler.

shutdown() vs shutdownNow()?

shutdown finishes queued work and stops accepting new work; shutdownNow interrupts running tasks and returns the unstarted ones.

Why is an unbounded queue risky?

maxPoolSize is never reached and the queue can grow until memory runs out.

How do you choose pool size?

By task type (CPU vs I/O bound), cores, memory and measured throughput, then tune with monitoring.
