Optional (Java 8 to 11)

Say "this value may be absent" in the type itself.

The problem

User user = new UserRepository().findUserByID(1);
System.out.println(user.getName());     // NullPointerException, because user is null

Methods generally return null, and if we forget to add a null check we get a NullPointerException. So we used to add null checks like if (user != null).

Optional<T>

Optional<User> as a return type tells the client that the return value may or may not exist.

public Optional<User> findUserByID(int id) { ... }

Optional<User> userOptional = new UserRepository().findUserByID(1);
if (userOptional.isPresent()) {
    User user = userOptional.get();
    System.out.println(user.getName());
}

Earlier we put a condition for the null check, and still we are using an if condition: what's the advantage?

  1. The API clearly says "value may be absent". We don't need to guess whether the value can be null or not: if it's Optional, the value may or may not exist.
  2. The compiler forces us to handle the Optional return type. Optional<User> u = repo.findByID(1); System.out.println(u.getName()); does not compile.
  3. A null return type doesn't give us anything, while Optional provides many utility methods to handle the response: isPresent(), ifPresent(), orElse(), orElseGet() ...

Optional class structure

public final class Optional<T> {
    private final T value;                                     // holds the actual value
    private static final Optional<?> EMPTY = new Optional<>(null);   // shared empty instance

    private Optional(T value) {                                // private constructor
        this.value = value;
    }
}
  • Whenever we need to return an empty Optional object, it does not create a new object every time, it just uses EMPTY. Here the unknown type (? wildcard) holds a null value.
  • The constructor is private: we can't do new Optional(). So it provides various methods for creation of an Optional object.

Creating an Optional

1. Optional.of(value)

public static <T> Optional<T> of(T value) {
    if (value == null) {
        throw new NullPointerException("value must not be null");
    }
    return new Optional<>(value);       // invokes the private constructor
}

It's a static method used to create a non-empty Optional object. If null is passed, it will throw NullPointerException.

public Optional<String> getUserName(String value) {
    return Optional.of(value);
}

2. Optional.ofNullable(value)

public static <T> Optional<T> ofNullable(T value) {
    return value == null ? (Optional<T>) EMPTY : new Optional<>(value);
}

The value may or may not contain a non-null value.

3. Optional.empty()

Returns a shared, immutable empty Optional instance, representing "no value present".

public static <T> Optional<T> empty() {
    Optional<T> t = (Optional<T>) EMPTY;       // type cast Optional<?> to specific Optional<T>
    return t;
}

Optional<String>  s = Optional.empty();
Optional<Integer> i = Optional.empty();

Presence checking

public boolean isPresent() { return value != null; }     // that "final T value"
public boolean isEmpty()   { return value == null; }     // Java 11

Retrieving values

MethodBehaviour
get()Returns the value; throws NoSuchElementException("No value present") if empty.
orElse(T other)Returns the value if present, else other.
orElseGet(Supplier)Returns the value if present, else executes the lambda (supplier) to compute the default. Use when the default value requires custom computation.
orElseThrow()Returns the value, else throws NoSuchElementException (Java 10).
orElseThrow(Supplier)Returns the value, else creates and throws our custom exception.
// orElse
Optional<String> usrNameOptional = Optional.of("Shreyansh");
String output = usrNameOptional.orElse("defaultUsrName");      // returns Shreyansh

// orElseGet
Optional<String> usrNameOptional = Optional.empty();
String output = usrNameOptional.orElseGet(() -> {
    return "default ...";                                        // this will return as it's empty
});

// orElseThrow(supplier)
public <X extends Throwable> T orElseThrow(Supplier<? extends X> exceptionSupplier) throws X {
    if (value != null) return value;
    else throw exceptionSupplier.get();
}
usrNameOptional.orElseThrow(() -> new IllegalArgumentException("User not found"));

orElse vs orElseGet: the argument of orElse(x) is always evaluated, even when a value is present (so an expensive call or side effect inside it still runs). orElseGet(() -> x) evaluates the supplier only if empty. Prefer orElseGet for anything non-trivial.

Transforming values

map(Function), flatMap(Function) and filter(Predicate): conceptually similar to stream methods. But streams work on 0 to N elements (a collection), whereas Optional works on 0 or 1 element (Optional is a wrapper of only 1 value).

Optional<String> outputOptional = Optional.of("Nitin");
Optional<Integer> outputLen = outputOptional.map((String val) -> {
    int len = val.length();
    return len;
});
System.out.println(outputLen.get());      // 5

Problem with Optional.map: what if the function (lambda expression) is also returning an Optional? Then we get a nested Optional. Use flatMap then.

Optional<Integer> outputLen = outputOptional.flatMap((String val) -> {
    return Optional.of(val.length());
});
System.out.println(outputLen.get());      // 5 prints

filter

In Optional, filter keeps the value only if it matches the condition, else it will return Optional.empty().

Optional<String> oo = Optional.of("Nitin");
oo = oo.filter((String val) -> {
    return val.length() > 3;
});
System.out.println(oo.isPresent());       // prints true

Action-based methods

// (i) ifPresent(Consumer)
oo.ifPresent((String val) -> {
    // some logic
});

// (ii) ifPresentOrElse(Consumer, Runnable): Java 9
oo.ifPresentOrElse(
    (String name) -> System.out.println(name),        // runs if present, with the value
    () -> System.out.println("Not found")             // runs if empty
);

Stream integration

Optional.stream() (Java 9)

Converts an Optional into a stream. If the value is empty, it creates an empty stream.

public Stream<T> stream() {
    if (isEmpty()) {
        return Stream.empty();
    } else {
        return Stream.of(value);
    }
}

Optional<String> nameOpt = Optional.of("Nitin");
nameOpt.stream().forEach((String name) -> System.out.println(name));

Why was stream() needed (an Optional holds only 1 value)? When working with streams and invoking a method which may return Optional<T>, to plug the Optional into the stream pipeline, this is handy.

public class UserDetails {
    private String email;
    public UserDetails(String email) { this.email = email; }
    public Optional<String> getEmail() { return Optional.ofNullable(email); }
}

List<UserDetails> users = Arrays.asList(new UserDetails("a@gmail.com"), new UserDetails(null));

// the lengthy way
List<String> emails = users.stream()
        .map((UserDetails user) -> user.getEmail())
        .filter((Optional<String> mail) -> mail.isPresent())
        .map((Optional<String> mail) -> mail.get())
        .collect(Collectors.toList());
System.out.println(emails);      // [a@gmail.com]

// the short way, using Optional.stream()
List<String> emails = users.stream()
        .map((UserDetails user) -> user.getEmail())          // Stream<Optional<String>>
        .flatMap((Optional<String> mail) -> mail.stream())  // converts each Optional to Stream<String>
        .collect(Collectors.toList());

Each Optional<String> becomes a Stream<String>, so we have Stream<Stream<String>>, but flatMap flattens it to Stream<String>; the empty ones simply vanish.

When NOT to use Optional

  1. Class variable: class User { private Optional<String> name; } is a bad design. Every access now requires user.getName().orElse("default"). It will break existing frameworks: (i) JSON serialization, (ii) Lombok, (iii) Hibernate/JPA.
  2. Method parameters: public void createUser(Optional<String> email). Now createUser(Optional.of("Nitin")) and createUser(Optional.empty()) are fine, but createUser(null) ✗: the Optional is null itself, so we must check null for the Optional before doing isPresent() or get(). That's why we use Optional: to avoid null checks!
  3. Serializable class: class UserDTO implements Serializable { private Optional<String> name; } (bad design). Optional itself is not Serializable, most serializers (Jackson) expect standard getter/setter methods, and the JSON payload may include the internal structure of Optional: instead of {"name":"Nitin"} we may get {"name":{"present":true,"value":"Nitin"}}.
  4. Leaking it through every layer: threading Optional through the whole call chain (controller to DB) pollutes the code instead of isolating null handling.
Where to use it

Best use case: the service layer. It can take the decision about what to pass to the client ultimately. Regardless of what we get from the DB or anywhere else, the service layer performs business logic and decides what goes out of the application. We can control its usage for the specific business flow.

Returning Optional from a repository (e.g. Spring Data's Optional<User> findById(id)) is the standard, idiomatic use: Optional as a return type is exactly what it was designed for. The advice above is about not leaking it through fields, parameters and DTOs. Never call get() without checking (prefer orElseThrow()), and never return null from a method whose return type is Optional.

Interview corner
of vs ofNullable vs empty?

of: value must be non-null (else NPE). ofNullable: wraps null as empty. empty: the shared empty instance.

orElse vs orElseGet?

orElse evaluates its argument always; orElseGet runs the supplier only when empty.

map vs flatMap on Optional?

Use flatMap when your function itself returns an Optional, to avoid Optional<Optional<T>>.

Why not Optional fields or parameters?

Not serializable, awkward for frameworks, and a null Optional defeats the purpose. It is intended for return types.
