Fork means divide into smaller sub-tasks. It brings more parallelism: multiple threads can work on a task.

How work stealing works

The thread pool has a shared submission queue, and each thread maintains its own work-stealing queue (a deque).

  1. Task 1 goes to T1. Task 2 goes to T2 (it is recursive: it can be divided into sub-tasks). Task 3 stays in the submission queue.
  2. Task 2 splits into subtask 1 and subtask 2. T2 takes subtask 1; for now no thread is available, so T2 puts subtask 2 into its own work-stealing queue.
  3. Now let's say Task 1 is completed (to be more precise, T1's execution is complete). T1 first checks its own work-stealing queue: nothing. Then it checks the submission queue: Task 3 is waiting, so it picks it.
  4. Now say Task 3 is also completed while subtask 1 is still running. T1 again checks its own queue (nothing) and the submission queue (nothing).
  5. Now T1 asks: can I steal some task from a busy thread? It takes subtask 2 from Thread 2's queue and works on it.
Why it is efficient

Owners take from their own end of the deque, thieves take from the opposite end, so contention is tiny and idle threads are never wasted.

Writing a fork-join task

Tasks can be split into multiple small sub-tasks. For that the task should extend:

  • RecursiveTask → returns a value (then we go for this)
  • RecursiveAction → does not return a value (then we go for this)

Both are subclasses of ForkJoinTask.

class ComputeSumTask extends RecursiveTask<Integer> {      // Integer = return type
    // computes sum from start to end: 1+2+3 ... 10
    int start;
    int end;

    ComputeSumTask(int start, int end) {
        this.start = start;
        this.end = end;
    }

    @Override
    protected Integer compute() {                 // main method that does the things
        if (end - start <= 4) {                   // small enough: do it directly
            int totalSum = 0;
            for (int i = start; i <= end; i++) {
                totalSum += i;
            }
            return totalSum;
        } else {
            // split the task
            int mid = (start + end) / 2;
            ComputeSumTask leftTask  = new ComputeSumTask(start, mid);        // only creates the object, does not call compute
            ComputeSumTask rightTask = new ComputeSumTask(mid + 1, end);

            leftTask.fork();                      // submits the task to the ForkJoinPool's work queue,
            rightTask.fork();                     // then an available thread calls compute(): fork the subtasks for parallel execution

            // combine the results
            int leftResult  = leftTask.join();    // wait until the task finishes and return the result
            int rightResult = rightTask.join();
            return leftResult + rightResult;
        }
    }
}

fork() does not immediately create a new thread. Instead it (a) places the task in a work-stealing queue and (b) existing pool threads execute it. That is why ForkJoinPool is very efficient.

// way 1: Executors.newWorkStealingPool()
//   by default: number of available processors (can also give the number of parallel threads here)
//   it uses ForkJoinPool internally, and its threads are usually daemon threads
ExecutorService pool = Executors.newWorkStealingPool();

// another way:
ForkJoinPool pool = ForkJoinPool.commonPool();
Future<Integer> futureObj = pool.submit(new ComputeSumTask(0, 100));
System.out.println(futureObj.get());
Good to know

A common optimisation is left.fork(); int r = right.compute(); int l = left.join();: the current thread does one half itself instead of just forking both. Parallel streams (.parallelStream()) and CompletableFuture default to the common ForkJoinPool.

shutdown vs awaitTermination vs shutdownNow

shutdown()

  1. Initiates an orderly shutdown of the ExecutorService.
  2. After calling shutdown, the executor will not accept new task submission.
  3. Already submitted tasks will continue to execute. It does not impact already running tasks.
ExecutorService poolObj = Executors.newFixedThreadPool(5);
poolObj.submit(() -> { /* some work */ });
poolObj.shutdown();                              // continue working
poolObj.submit(() -> { /* some work */ });       // throws RejectedExecutionException

awaitTermination()

  1. It is an optional functionality. Returns true/false.
  2. It is used after calling the shutdown method.
  3. Blocks the calling thread for a specific timeout period, and waits for the ExecutorService to shut down.
  4. Returns true if the ExecutorService gets shut down within the timeout, else false.
poolObj.shutdown();
boolean isTerminated = poolObj.awaitTermination(2, TimeUnit.SECONDS);
// false if the pool thread is taking, say, 5 seconds; true if it completes within 2 seconds

shutdownNow()

  1. Best-effort attempt to stop/interrupt the actively executing tasks.
  2. Halts the processing of tasks which are waiting.
  3. Returns the list of tasks which are awaiting execution (the ones still in the queue).

It is called "best effort" because it interrupts threads, but if the task ignores interrupts, it may continue working. Like Thread.sleep() is an interruptible operation, but suppose the task is while (true) { ... }: shutdownNow() cannot force-stop it, because Java cannot kill threads safely, it only sends an interrupt signal.

// the standard clean-shutdown recipe
pool.shutdown();
try {
    if (!pool.awaitTermination(30, TimeUnit.SECONDS)) {
        pool.shutdownNow();
    }
} catch (InterruptedException e) {
    pool.shutdownNow();
    Thread.currentThread().interrupt();
}

ScheduledThreadPoolExecutor

Helps to schedule tasks. ScheduledThreadPoolExecutor extends ThreadPoolExecutor; the methods present other than those of the parent are:

(i) schedule(Runnable command, long delay, TimeUnit unit)

A one-time task runs after the delay.

ScheduledExecutorService poolObj = Executors.newScheduledThreadPool(5);   // min threads; max here can be Integer.MAX_VALUE

poolObj.schedule(() -> {
    System.out.println("Hello");
}, 5, TimeUnit.SECONDS);

(ii) schedule(Callable<V> callable, long delay, TimeUnit unit)

Returns a value.

Future<String> fo = poolObj.schedule(() -> {
    return "Hello";
}, 5, TimeUnit.SECONDS);
try {
    System.out.println(fo.get());
} catch (Exception e) { }

(iii) scheduleAtFixedRate

Future<?> fo = poolObj.scheduleAtFixedRate(() -> {
    System.out.println("Hello");
}, 3, 5, TimeUnit.SECONDS);          // 3 = initialDelay, 5 = period

fo.cancel(true);                     // we can use this to interrupt it

Suppose the first iteration took 10 seconds: the next task will wait in the queue and start as soon as the previous one is finished.

(iv) scheduleWithFixedDelay

Very much similar to the above one, but here it runs n seconds (or whatever unit we gave) after the previous has completed its execution.

Interview corner
Why avoid Executors.newFixedThreadPool in production?

Unbounded LinkedBlockingQueue can eat all memory under load; cached pool can create unlimited threads. Build a ThreadPoolExecutor with bounded queue and a rejection policy.

What is work stealing?

Each worker has its own deque; idle workers steal tasks from the tail of busy workers' deques.

RecursiveTask vs RecursiveAction?

RecursiveTask returns a result, RecursiveAction returns nothing.

scheduleAtFixedRate vs scheduleWithFixedDelay?

Fixed rate measures from start to start; fixed delay waits after the previous run ends.

Does shutdownNow() always stop tasks?

No. It only interrupts; tasks that ignore interrupts keep running.
