Singleton and Immutable Classes

Exactly one object, and objects that never change. Both are very common interview questions.

Singleton class

The objective of this class is to create only one and only one object. There are different ways.

Throughout, we use a DBConnection class. The constructor is private so no one can create an object with new.

1. Eager initialization

public class DBConnection {
    private static DBConnection conObject = new DBConnection();  // belongs to the class, but is private

    private DBConnection() { }          // private constructor: can't initialize an object from outside

    public static DBConnection getInstance() {
        return conObject;
    }
}

// call this to get conObject (one and only object)
DBConnection conObject = DBConnection.getInstance();

Problem: even if we never use it, the object is created in memory at class-loading time.

2. Lazy initialization

public class DBConnection {
    private static DBConnection conObject;      // not initialized here
    private DBConnection() { }

    public static DBConnection getInstance() {
        if (conObject == null) {
            conObject = new DBConnection();
        }
        return conObject;
    }
}

Problem: if two threads come in parallel when it's null, two objects will be created.

3. Synchronized method

public static synchronized DBConnection getInstance() {   // lock and unlock
    if (conObject == null) {
        conObject = new DBConnection();
    }
    return conObject;
}

If T1 is accessing, then a lock is created and the others wait.

Problem: slow. Say 100 parallel requests: because we put synchronized at method level, every call takes the lock, even long after the object exists.

4. Double-check locking

public class DatabaseConnection {
    private static volatile DatabaseConnection conObject;
    private DatabaseConnection() { }

    public static DatabaseConnection getInstance() {
        if (conObject == null) {                              // check 1
            synchronized (DatabaseConnection.class) {
                if (conObject == null) {                      // check 2
                    conObject = new DatabaseConnection();
                }
            }
        }
        return conObject;
    }
}

Thread 1 comes and takes the lock. For other threads, the object is already created and they will simply return it, without waiting on the lock.

Why volatile?

Creating an object has 3 steps: allocate memory, initialize the fields, and assign the memory address to conObject. Each CPU core has its own private cache (L1), and there is a shared memory below (L3 cache / RAM).

Say T1 initialises the object in Core 1's L1 cache. Now T2 runs on Core 2, and the memory between Core 1 and Core 2 isn't synced yet, so T2 can see a stale or half-built conObject. That causes the issue.

volatile guarantees two things: visibility (a write by one thread is seen by the next read in any thread) and no reordering (the compiler and CPU may not shuffle the three object-creation steps, so another thread can never see the reference before the fields are initialised). That is the real bug it prevents. A handy mental model is "volatile pushes the value out to shared memory instead of keeping it in one core's cache".

Problem with double-check: volatile is slower and so is synchronized, so we pay a cost on top.

5. Bill Pugh singleton

No volatile, no synchronized. It is based on eager-style loading, but it solves its disadvantage.

public class DatabaseConnection {
    private DatabaseConnection() { }

    private static class DBConnectionHelper {      // nested class
        private static final DatabaseConnection INSTANCE_OBJECT = new DatabaseConnection();
    }

    public static DatabaseConnection getInstance() {
        return DBConnectionHelper.INSTANCE_OBJECT;
    }
}

The nested class isn't loaded at the time of application startup, unless it is called. The JVM itself guarantees class loading is thread-safe, so the instance is created once, lazily, with no locks.

6. Enum

enum DBConnection {
    INSTANCE;
}

Enums have a private constructor by default and are singleton by default: only one instance is created, by the JVM.

Good to know

Enum is the safest way. Every other approach can be broken by reflection (calling the private constructor) or by serialization (deserializing creates a new object). Enums resist both. That is why Joshua Bloch recommends it in Effective Java.

Immutable class

We cannot change the value of an object once it's created. Examples: String, wrapper classes.

  1. Declare the class final so that it cannot be extended.
  2. All class members should be private (and final), so direct access can be avoided.
  3. Members are initialized only once, using the constructor.
  4. No setter methods, just getters (which return a copy of mutable members).
public final class MyImmutableClass {
    private final String name;
    private final List<Object> petNameList;

    MyImmutableClass(String name, List<Object> petNameList) {
        this.name = name;                          // values are set only during initialization
        this.petNameList = new ArrayList<>(petNameList);   // defensive copy of what the caller gave us
    }

    public String getName() { return name; }       // no setter method

    public List<Object> getPetNameList() {
        return new ArrayList<>(petNameList);       // return copy, not the original one
    }
}

If we returned petNameList directly, we know it works by reference, so the caller could modify the original list. That's why we just return its copy. The same leak exists on the way in: if the constructor stored the caller's list reference, the caller could still change it afterwards, so we also make a defensive copy in the constructor (on Java 10+ you can use List.copyOf(petNameList)).

Interview corner
How do you break a singleton, and how do you prevent it?

Reflection, serialization, cloning and multiple class loaders. Throw an exception in the constructor if an instance exists, implement readResolve(), or simply use an enum.

Why is the second null check needed in double-check locking?

Two threads can both pass check 1 and queue at the lock. Without check 2 the second would create another object once it gets the lock.

Why is String immutable?

String pool sharing, thread-safety, safe hash keys (hashCode cached) and security (e.g. file paths, URLs, DB credentials can't be altered after validation).

Is Spring's singleton scope the same thing?

No. A Spring singleton bean is one instance per container, not one per JVM, and the class itself can still be instantiated elsewhere.
