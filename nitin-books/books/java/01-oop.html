OOP: Thinking in Objects

Why Java is built around objects, and the four pillars every interview starts with.

Procedural programming vs OOP

Older languages like C work procedurally: you write functions, and data sits somewhere else for any function to touch. Java works with objects: data and the code that uses it are kept together.

Procedural (C)OOP (Java)
Program is divided into parts called functionsProgram is divided into objects
No proper way to hide data. Importance goes to functions, and data moves around freelyObjects provide data hiding. Importance goes to the data
Overloading is not possibleOverloading is possible
Inheritance is not possibleInheritance is possible
No code reusabilityCode is reusable
Examples: Pascal, C, FORTRANExamples: Java, C#, Python, C++

What an object has

Every object has two things:

  1. Properties (state): the data it holds.
  2. Behaviour (functions): what it can do.
Example: a Dog

Properties: age, breed, colour. Behaviour: bark, sleep, eat.

A class is a blueprint of the object. You write the class once, then create as many objects from it as you need.

1st pillar: Data Abstraction

Abstraction hides the internal implementation and shows only the essential functionality to the user. In Java it is achieved through interfaces and abstract classes.

Advantage: increases security and confidentiality.

Examples from daily life
  • Car: we are only shown the brake pedal, and if we press it the speed reduces. But how? That is abstracted from us.
  • Cell phone: how a call is made is abstracted from us.

2nd pillar: Data Encapsulation

Think of it as data in a capsule.

  • Encapsulation binds the data and the code working on that data in a single unit.
  • Also known as data hiding.

Steps to achieve encapsulation:

  1. Declare the variables of a class as private.
  2. Provide public getters and setters to view and modify the values of those variables.
Example 
class Dog {
    private String color;          // data member, hidden from outside

    public String getColor() { return color; }
    public void setColor(String color) {
        this.color = color;
    }
}

We encapsulated the data member and the functions that work on the data into a single unit. This class has full control over its data.

Advantages:

  • Loosely coupled code. With different objects/classes, if the data in one changes, the others remain unchanged.
  • Better access control and security.
Good to know

Strictly speaking, data hiding is the result of encapsulation (the private keyword does the hiding), while encapsulation is the bundling itself. In interviews, saying "encapsulation = bundling data and methods, and data hiding is achieved using private fields plus getters and setters" is the safest answer.

3rd pillar: Inheritance

The capability to inherit properties from the parent class. It can be both functions and variables.

  • Promotes code reusability.
  • Can achieve polymorphism.

Types: Single, Multilevel, Hierarchical, Multiple.

Single

A↓B

One parent, one child.

Multilevel

A↓B↓C

A chain of parents.

Hierarchical

A↙ ↘BC

One parent, many children.

Multiple inheritance and the diamond problem

Class C extends both class A and class B, and both have a getEngine() method. If you call c.getEngine(), which one runs? It clashes, so this is not allowed in Java with classes. This is the diamond problem.

But if A and B are interfaces, it is allowed, because class C has to override the method itself, so there is no confusion. Through interfaces we can resolve the diamond problem.

interface A { void getEngine(); }
interface B { void getEngine(); }

class C implements A, B {
    public void getEngine() {      // C decides what happens
        System.out.println("C's engine");
    }
}

4th pillar: Polymorphism

Poly = many, morph = forms. The same method behaves differently in different situations. A person can be a father, a husband, an employee, all at once.

Types:

  • Compile time / Static polymorphism / Method overloading
  • Run time / Dynamic polymorphism / Method overriding

Overloading (compile time)

Same method name, different parameters. The compiler picks the right one at compile time: when I write sum(5, 2) it already knows which version to call.

int sum(int a, int b)          { return a + b; }
String sum(String a, String b) { return a + b; }

It can be done only on the parameters, not the return type. This is not valid:

int    sum(int x, int y)  { ... }
String sum(int x, int y)  { ... }   // compile error: same parameters

Overriding (run time)

The child class gives its own implementation of a parent method. Even the arguments must be the same. Only the internal implementation differs.

Suppose

Parent has show(). Child has show(String msg) and show(int x).

That is completely valid, but it is overloading, not overriding. If the child had show() with the same signature, then it would be overriding.

Is-a and Has-a relationships

  • Is-a: Dog is a Animal. This is inheritance.
  • Has-a: an object of class A is used in class B.
    • Can be one-to-one, one-to-many, many-to-one.
    • Examples: School has students, Bike has engine.

Interview corner
Abstraction vs encapsulation?

Abstraction is about hiding complexity by showing only what is needed (interfaces, abstract classes). Encapsulation is about protecting data by bundling it with its methods and restricting direct access (private fields, getters and setters).

Why does Java not support multiple inheritance with classes?

To avoid the diamond problem: if two parents have the same method, the child cannot know which to inherit. Interfaces are allowed because the implementing class must provide its own body.

Overloading vs overriding?

Overloading: same name, different parameters, resolved at compile time, within one class (or across parent and child). Overriding: same name and same parameters, child replaces parent behaviour, resolved at run time.

Can we overload by changing only the return type?

No. The compiler looks at the method name and parameter list, so two methods that differ only in return type clash.

Aggregation vs composition?

Both are "has-a". In aggregation the parts can live without the whole (students without the school). In composition the parts cannot (rooms without the school).
