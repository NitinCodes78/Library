Modern Java: Sealed, Switch, Pattern Matching, Records, Text Blocks

Java 14 to 21 features, each one aimed at removing a pain point.

Java 17: Sealed classes and interfaces

The problem

The biggest problem is lack of control in inheritance.

Shape
Circle
Rectangle
Triangle
ColoredCircle
RedCircle
GreenCircle
RotatingCircle

It is not possible to control the hierarchy: any class can join it by implementing the interface or extending the class, even if we did not plan for it (for example, we didn't plan for "RotatingCircle"). So how do we bring control over who can extend or implement an interface or class? Through sealed classes/interfaces: it can be subclassed only by its own permits list.

public sealed interface Shape permits Circle, Rectangle { }

public final class Circle implements Shape { }              // "final" tells it can't be subclassed further

public non-sealed class Rectangle implements Shape { }      // "non-sealed" removes all restriction: can be subclassed freely
// (could have used sealed + permits here also)

Rules to consider

  1. A permits type should be a direct subclass of the sealed interface or class.
  2. A permits type should be either final, sealed or non-sealed.
  3. All permits types should be present (future classes or interfaces are not considered).
Good to know

If subclasses are in the same file, permits can be omitted. Records and enums are implicitly final, so they are ideal permitted types. Sealed types shine with pattern-matching switch: the compiler knows all subtypes, so no default is needed (exhaustive).

Switch expressions (Java 14 onwards)

They solved many problems of the old switch statement. (Basic yield was also met in the Operators chapter.)

1. Multiple lines of case stacking

Old switch statement
each case needs its own line
switch (day) {
 case MONDAY:
 case FRIDAY:
 case SUNDAY:
  System.out.println(6);
  break;
 case TUESDAY:
  System.out.println(7);
  break;
}
Java 14 switch
comma-separated case grouping
switch (day) {
 case MONDAY, FRIDAY, SUNDAY:
  System.out.println(6);
  break;
 case TUESDAY:
  System.out.println(7);
  break;
}

2. Fall-through by default

// old switch statement
switch (day) {
    case MONDAY:
    case FRIDAY:
        System.out.println(6);
    case TUESDAY:                 // missed "break"
        System.out.println(7);
        break;
    case WEDNESDAY:
        System.out.println(10);
        break;
}
// day = FRIDAY: it prints 6 and 7. It found break only after printing 7.

// Java 14: arrow form
switch (day) {
    case MONDAY, FRIDAY -> System.out.println(6);
    case TUESDAY        -> System.out.println(7);
    case WEDNESDAY      -> System.out.println(10);
}

The new form of switch label, i.e. case L ->, tells that only the code to the right of the label needs to be executed if the label is matched. No need to add break for each case now.

3. No return value

int count = switch (day) {              // Java 14: switch is now an expression
    case MONDAY, FRIDAY -> 6;
    case TUESDAY        -> 7;
    case WEDNESDAY      -> 9;
};

If there is a block, we can use yield:

int count = switch (day) {
    case MONDAY, FRIDAY, SUNDAY -> {
        if (day == Days.SUNDAY) {
            throw new RuntimeException("...");
        }
        yield 6;
    }
    case TUESDAY   -> 7;
    case WEDNESDAY -> 9;
};

4. No exhaustiveness check

Old switch: the compiler doesn't force us to cover all values. Java 14 switch: when we use switch as an expression, the compiler will force us to cover all the cases.

Days day = Days.FRIDAY;
int count = switch (day) {
    case MONDAY   -> 6;
    case THURSDAY -> 8;
};   // error: the switch expression does not cover all possible values
// so we should use default:
//     default -> 0;

5. All case blocks share the same scope

// old switch statement
switch (day) {
    case MONDAY:
        String stringVal = "Monday";
        System.out.println(stringVal);
        break;
    case TUESDAY:
        String stringVal = "Tuesday";   // error: variable is already defined
        break;
}
// in order to solve this problem, use blocks:  case MONDAY: { ... }

// Java 14: each 'case' with '->' is treated as an independent scope
String msg = switch (day) {
    case MONDAY  -> { String val = "..."; yield val; }
    case TUESDAY -> { String val = "..."; yield val; }
    default      -> "others";
};

Old-style case L: with the new feature

int day = 1;
String typeOfDay = switch (day) {
    case 1, 7:
        yield "end";
    case 2, 3, 4, 5, 6:
        yield "day";
    default:
        yield "Invalid";
};
  • Before Java 14, old cases could not return values. Now they can, via yield.
  • We still need break if it's just a statement switch (not returning), else it will fall through.

Java 16: Pattern matching for instanceof

// old way: extra overhead of doing the type casting
if (obj instanceof String) {
    String s = (String) obj;            // type casting
    System.out.println(s.toUpperCase());
}

// Java 16
Object obj = "hello world";
if (obj instanceof String s) {          // block scope only of s
    System.out.println(s.toUpperCase());
}
// 1. first the comparison happens
// 2. if true, then s is automatically type cast and initialized

Can we use &&? Yes:

if (obj instanceof Integer i && i < 10) { ... }

Object obj = new TwoWheeler();
if (obj instanceof Vehicle vehicleObj) {      // Vehicle: an interface that TwoWheeler implements
    vehicleObj.drive();
}

Scope: the binding variable exists only where the compiler can prove the match succeeded: inside the true branch, or the rest of the expression after &&. obj instanceof Integer i || i < 10 does not compile.

Java 21: Pattern matching for switch

It supports all that the classic switch can (no change in that), plus pattern matching for objects: classes, interfaces, abstract types, wrapper objects.

Object obj = "hello world";
switch (obj) {
    case String s:                         // scope limited to this block only
        System.out.println("String: " + s);   // s is automatically cast
        break;
    case Integer i:
        System.out.println(i);
        break;
    default:
        System.out.println("other type");
}

With enum

// old way
Object obj = Color.RED;
switch (obj) {
    case Color.RED:   System.out.println("Red");   break;
    case Color.GREEN: System.out.println("Green"); break;
    default:          System.out.println("other");
}

// new way
switch (obj) {
    case Color c:
        System.out.println(c.name());
        break;
    default:
        System.out.println("other");
}

Pattern-matching switch is not null-safe by default: it throws NullPointerException on null unless you add case null.

Object obj = null;
switch (obj) {
    case String s: System.out.println(s); break;
    case null:     System.out.println("null");  // without this line: NPE (plain default does not match null)
    default:       System.out.println("");
}

Not possible:

Shape obj = new Circle();
switch (obj) {
    case Circle c:           // dominance problem
    case Square s: ...
}

Because here the compiler will be confused with case labels where more than one is valid (for example a general type placed before a more specific one, which makes the later label unreachable).

  • Pattern-matching switch was a preview in Java 17–20 and final in Java 21.
  • A pattern switch throws NPE on null unless you add case null (which may be combined: case null, default ->); the plain default does not match null. Old (non-pattern) switches always threw NPE on null.
  • Dominance rule: put the more specific case first. Guards use when: case Integer i when i > 10 -> ....
  • With a sealed interface, covering all permitted subtypes makes default unnecessary.

Java 16: Records

The problem first

To create an immutable class, which is required as simply a data carrier (like a POJO), we need to write this code:

public final class User {
    private final String name;
    private final int age;

    // no setter methods, initialized via constructor only
    public User(String name, int age) {
        this.name = name;
        this.age = age;
    }

    // only getter methods available
    public String getName() { return name; }
    public int getAge() { return age; }
    // and generally we also provide equals, hashCode and toString methods
}

Lots of boilerplate code, just for a basic immutable POJO class. That's where Java 16 Records come into the picture.

But wait: Lombok helps in reducing boilerplate like automatic generation of getters and setters, equals, hashCode, constructor, toString and immutable class (via @Value). Then why Records? (First understand how it works.)

Records

  • It helps us create an immutable class in a short way.
  • It is mostly designed to reduce boilerplate for data-carrying classes (like POJO).
// syntax: record YourRecordName(Type field1, Type field2) { }
public record User(String name, int age) { }       // (name, age) = the record components

It is equivalent to a POJO with a constructor, getter methods, equals(), hashCode() and toString(). No setter methods. The record is a final class; access modifier rules are similar to a normal class (it can be a private record when it is a nested one, as the outermost class is always public or package-private).

  • All record classes by default extend java.lang.Record implicitly, because Java can identify "User" is a record only via the superclass. Internally getSuperclass() == java.lang.Record.class.
  • That's why extends is not allowed on a record (no multiple inheritance). But we can implement more than one interface like any other normal class.
  • It generates private final fields, generally called record components.
  • We cannot add more instance fields. All instance fields must be defined in the record header only, so that by just seeing the record we can find what this record is carrying.
  • Static fields are allowed, as they don't belong to an individual instance. So each User object is still immutable.
public record User(String name, int age) {
    String lastName;            // not allowed: instance field
    static int count = 0;       // allowed
}

Records do not generate getName(); the accessors are named after the component: user.name() and user.age(). "Immutable" is also shallow: if a component is a mutable List, the list itself can still change (use List.copyOf in the constructor).

Constructors in records

  • A canonical constructor (takes all record components, in order) is generated automatically.
  • We can override the canonical constructor if we want:
public User(String name, int age) {
    if (age < 0) throw new IllegalArgumentException();
    this.name = name;               // required
    this.age = age;
}
  • We can have a compact constructor, a shorthand form of the canonical constructor. The compiler implicitly assumes the parameters are the record components in the declared order, and assigns the fields at the end.
public User {
    if (age < 0) throw new IllegalArgumentException();
    // compiler does this.name = name; this.age = age;
}

We can also add another constructor, but it must delegate to the canonical one:

public User(int age) {
    this("defaultName", age);      // internally we have to call the canonical constructor
}

For a public record, the canonical constructor must be public. If it is a default (package-private) record, then the constructor can be default or public: you can't restrict a constructor more than the record itself. We can also override equals, hashCode and toString.

Nested records

In records, we can also create nested records, which can be private/protected/public like nested classes. But the difference is: only static nested records are possible (they are implicitly static); non-static nested records are not.

public record User(/* ... */) {
    record NestedRecord() {             // by default static only
        public void display() { }
    }
}
// access it similar to nested classes
User.NestedRecord ao = new User.NestedRecord();
ao.display();

Why only static nested records? One view: a record is a transparent data carrier, meaning all its fields must be defined in the record header. Say record User(String a) { record Address(String b) {} }. If the nested record were non-static it could access parent fields, so internally Address would contain a hidden reference private final User outer. That violates the promise of records: the state of Address isn't fully declared in record Address(String b), it carries extra invisible state (the User object), and that breaks the transparency principle.

Local records

  1. Similar to local classes, we can create local records: records within a block like a method block, while-loop block, if-condition block.
  2. Access modifier rules are similar to local classes: a local record can't be declared public/private/protected, because its scope is limited to the block.
  3. It can't be used outside of the block.
  4. There are no static local records, because static belongs to a class, but a local record's scope is a block, not a class (they are implicitly static, so they can't capture local variables).
public void printAddress(String city, String country) {
    // a local record only for this method
    record Address(String city, String country) {
        public String fullAddress() {
            return city + ", " + country;
        }
    }
    Address address = new Address(city, country);
    System.out.println(address.fullAddress());
}

Lombok is via adding a dependency, but Java internally supports Records. Lombok doesn't restrict setter methods (a Lombok @Data class stays mutable), whereas a record guarantees there are none.

Java 15: Text blocks

Two common use-cases for multi-line strings in Java code:

String query = "SELECT e.id, e.name \n"
             + "FROM employees e \n"
             + "WHERE e.salary > 6000 \n"
             + "ORDER BY e.name ASC;";

String jsonString = "{\n"
                  + "  \"name\": \"Shreyansh Jain\", \n"
                  + "  \"country\": \"India\", \n"
                  + "  \"profession\": \"Software Engineer\" \n"
                  + "}";

Difficult to read due to newline characters, escape characters and string concatenation (so many special characters). We can't simply try running the SQL query, and it is difficult to debug.

Solution: text block

  • It is finalized in Java 15.
  • It's a multi-line string literal used to make writing and reading multi-line text easier. It starts and ends with three double quotes (""").
String query = """
    SELECT e.id, e.name
    FROM employees e
    WHERE e.salary > 6000
    ORDER BY e.name ASC;
    """;

String jsonString = """
    {
      "name": "Shreyansh Jain",
      "country": "India",
      "profession": "Software Engineer"
    }
    """;

Internally, a text block (""") is compiled into a regular String object only (in the class file we'll see the same thing as we had written before).

Certain rules

  1. After the opening delimiter ("""), text or content is not allowed on the same line: """{ is wrong (✗); put the content on the next line (✓).
  2. Preserving trailing white space (the notes' example): a trailing escape \s is preserved as a space, e.g. "name": "Nitin",\s.
  3. Continuation without adding a newline: a backslash \ at the end of a line joins lines:
String text = """
    This is a single line \
    even though it looks \
    like multiple lines.
    """;

We can apply methods on text blocks like we do on Strings:

String json = """
    {
      ...
    }
    """.toUpperCase();
Good to know

Incidental indentation (the common left margin) is stripped automatically, based on the closing """ position and the least-indented line. formatted(...) works for placeholders: """Hello %s""".formatted(name).

Interview corner
What problem do sealed classes solve?

Uncontrolled inheritance. You list exactly which classes may extend, which enables exhaustive pattern matching and safer domain models.

Record vs class vs Lombok @Value?

Record: language-level, final, transparent, accessors like name(), cannot extend. Lombok @Value: library, generated getX(), can be customised more.

Switch statement vs switch expression?

Statement uses colons and fall-through; the expression uses arrows, returns a value, no fall-through, and must be exhaustive.

What does pattern matching for instanceof save?

The explicit cast: test and bind in one step.

Can a record have a setter, or extend a class?

No setters (fields are final) and no extends (it already extends java.lang.Record); it may implement interfaces.
