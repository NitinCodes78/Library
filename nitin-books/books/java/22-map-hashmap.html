The Entry sub-interface

Entry is the sub-interface of Map, so it's accessed via Map.Entry. Methods: getKey(), getValue(), int hashCode(), boolean equals(Object o).

Since it's an interface, inside HashMap it's implemented as:

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;
    final K key;
    V value;
    Node<K,V> next;
    // then a constructor to initialize these 4 fields, and getters and setters
}

How HashMap stores data

Internally, a HashMap is an array of Entry<K,V> (Node objects). Each Node holds hash, key, value, next. The array is of size 16 unless the size is explicitly defined: check the HashMap implementation, the initial capacity is 16 by default (all the constants are there in the HashMap class).

Working illustration: put(1, "SJ")

  1. Compute the hash of the key: hash(1), let's say 1234567.
  2. Take its modulo with the array capacity to get the index where it's stored: 1234567 % 16 = 7.
  3. It's stored at index 7: { hash: 1234567, key: 1, value: "SJ", next: null }.
Why hash & (n-1) instead of %

These days, instead of hash % n, a better alternative is index = hash & (n - 1), as it's high-performance: a modulo operation requires division, which can take 10 to 30 clock cycles on a CPU. In contrast, a bitwise AND is a fundamental hardware-level operation that typically takes 1 clock cycle.

It works only if n is a power of 2 (true in our case). For example 16 = 00010000 has a single bit set. When we do 16 - 1 = 15 = 00001111, all the bits to the right of that become 1. This acts as a bitmask: AND with this mask effectively "truncates" the hash code and always results within the range [0, 15].

When the map reaches its load factor threshold (default 0.75 of capacity), it triggers a resize (it's doubled), and elements are rehashed to new positions. If I define an initial capacity of 13, inside the HashMap constructor a specialised method tableSizeFor(int cap) always rounds it to the next power of 2, i.e. 16.

Hash collision

Now the user does map.put(10, "PJ") and its index also comes out to be 7. This is known as a hash collision. If the key is the same, its value is overridden; otherwise the new node is chained:

When we do get(10) → compute hash(10) = 5493217 → modulo with 16 → index 7 (assumed here for the example), so it will iterate over the linked list at index 7 to find the key-value pair, comparing keys with equals().

The hashCode / equals contract

get(key) should always give the same hash. There's a contract between hashCode() (generates the hash) and equals() (are two objects equal):

  1. If obj1.equals(obj2) then their hash should also be the same.
  2. If two objects have the same hash, it doesn't mean the two objects are equal. This is not always true.

No matter how many times we find the hash of a key, say 5, it will always be the same. Maybe hash(6) == hash(8) does not mean 6 and 8 are equal. equals() and hashCode() should go hand-in-hand.

What breaks if they don't

Suppose a Map has (1, "Nitin") and (3, "Nitin"). Say hashCode is based on name and equals checks if ids are the same:

class Person {
    int id;
    String name;
    Person(int id, String name) { this.id = id; this.name = name; }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof Person)) return false;
        Person other = (Person) obj;
        return this.id == other.id;
    }

    @Override
    public int hashCode() {
        return name.hashCode();          // ✗ based on name, but equals is based on id
    }
}

map.put(new Person(1, "Nitin"), "A");
map.put(new Person(3, "Nitin"), "B");    // same name: both go into the same bucket x

map.get(new Person(1, "Rahul"));         // different name = different hash = different bucket → returns null
// we expect "A" because (1, "Nitin") equals (1, "Rahul"): same ids!

The lookup depends first on hashCode (to find the appropriate bucket to search in), then on equals. So even if equals says "same id", the HashMap won't find it if the hashCode puts it into a different bucket.

If equals is based on id, then hashCode() must also be based on id: return Integer.hashCode(id); (or Objects.hash(id)).

In a HashMap, hashCode() decides the bucket, equals() decides the exact key inside that bucket. If you don't use the same key, your get() / containsKey() breaks. This Person object won't break in lists (no buckets), but it will break in HashMap, HashSet etc.

The contract in one line: equal objects (by equals()) must have equal hash codes (== is just the identical-object special case). Don't use mutable fields in hashCode for objects used as keys: if the field changes after insertion, the entry is lost in the wrong bucket.

Complexity

Insertion, deletion and find are O(1) in HashMap on average. The worst case can be O(n) when so many hash collisions occur.

Avoiding the worst case: treeification

TREEIFY_THRESHOLD (8 by default): whenever a linked list at an index grows to 8 nodes, the bucket is converted to a balanced binary search tree (red-black tree), bringing the complexity down to O(log n).

A bin (bucket) is treeified only when both hold:

  1. the number of nodes in the bucket ≥ 8 (TREEIFY_THRESHOLD = 8), and
  2. the table size (capacity) ≥ 64 (MIN_TREEIFY_CAPACITY = 64).

If the capacity is less than 64, the HashMap prefers to resize (rehash) instead of treeifying. These constants are defined in the HashMap class.

Good to know

When a tree bucket shrinks back to 6 nodes or fewer (UNTREEIFY_THRESHOLD), it becomes a linked list again. Also, HashMap spreads the key's hash bits first (h ^ (h >>> 16)) so the low bits used by hash & (n-1) carry information from the high bits.

Nulls and thread-safety

  • HashMap allows one null key, and values can also be null.
  • Hashtable and ConcurrentHashMap are thread-safe and do not store a null key or value.
  • HashMap is not thread-safe.

Interview corner
Explain how HashMap works internally.

Hash the key, compute the bucket with hash & (n-1), store a Node there. Collisions chain in a linked list (tree after 8 nodes and capacity ≥ 64). get hashes again, finds the bucket and uses equals() inside it. At 75% load it doubles and rehashes.

Why must you override hashCode when you override equals?

Otherwise equal objects can land in different buckets and lookups fail.

Why is HashMap capacity always a power of 2?

So the index can be computed with a cheap bit mask hash & (n-1) instead of division, and so resizing splits buckets cleanly.

HashMap vs Hashtable vs ConcurrentHashMap?

HashMap is unsynchronized and allows null. Hashtable locks the whole map and bans null. ConcurrentHashMap locks at a finer level, so it scales far better.
