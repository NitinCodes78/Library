Memory Management and Garbage Collection

Where your variables and objects live, how Java cleans up after you, and how the garbage collector decides.

Two types of memory

Both are created by the JVM and stored in RAM.

Stack

Temporary variables, primitives, and references. One per thread.

Heap

Objects. Shared by all threads. Cleaned by the garbage collector.

Stack memory

  1. Stores temporary variables, with a separate memory block for methods (scope is that block only).
  2. Stores primitive data types.
  3. Stores the references of heap objects. A reference can be strong, weak or soft.
  4. Each thread has its own stack memory, but they all share a common heap memory.
  5. Variables within a scope are visible only there. As soon as a variable goes out of scope, it is deleted from the stack in LIFO order.
  6. When stack memory goes full, it throws java.lang.StackOverflowError.

Walking through an example

public class MemoryManagement {
    public static void main(String[] args) {
        int primitiveVariable = 10;
        Person personObj = new Person();
        String stringLiteral = "24";
        MemoryManagement memObj = new MemoryManagement();
        memObj.memoryManagementTest(personObj);
    }

    private void memoryManagementTest(Person personObj) {
        Person personObj2 = personObj;
        String stringLiteral2 = "24";
        String stringLiteral3 = new String("24");
    }
}

  • stringLiteral and stringLiteral2 both point to the same "24" in the pool.
  • stringLiteral3 points to a separate object in the heap, because it was created using new.
  • personObj and personObj2 point to the same PersonObject.

Now the closing bracket of memoryManagementTest is reached. Its scope is deleted from the stack memory, before main(), in LIFO order. Its references are removed too. Similarly, when main() closes, its scope and references are removed and the stack becomes empty.

But the heap still has the objects (PersonObject, MemoryManagement, the pool's "24", the new String "24"). They are now unreferenced, so the garbage collector can remove them later.

What really sits where

MyObject obj = new MyObject();

MyObject obj (on the stack)

  • Does not hold object data
  • Just a memory address (e.g. FA32) that points to the heap
  • Space used is very small, in bytes

new MyObject() (the actual object)

  • Allocates memory on the heap
  • Space = the object header size + all its internal variables' size
  • The header is metadata used by Java for locking, garbage collection, etc.
class MyObject {
    int a;
    String b;
}

a lives in the heap, inside the object's memory block. b also lives in the heap: it stores an address inside the object and points to another heap location (where the String is).

Heap memory

  1. There is no order of allocating memory.
  2. The garbage collector (GC) is used to delete the unreferenced objects from memory. It runs periodically and the JVM controls it.
  3. System.gc() can run it manually in code, but there is still no guarantee, as the JVM decides whether to remove unreferenced objects.
  4. If the JVM feels heap memory is filling fast, it invokes the GC more often; else it may run very rarely.

With a strong reference (personObj) the object won't be removed on GC as there is still a reference. The weak one goes at the next GC.

Strength order: strong > soft > weak > phantom. Weak dies at the next GC, soft survives until memory is tight, which suits caches.

Non-heap: Metaspace
(replaced PermGen in Java 8)

Metaspace (non-heap) replaced the old permanent generation (PermGen) in Java 8. It holds class metadata (class structures, method data) and constants like static final. Static variables themselves are stored in the heap, along with the class's Class object.

The heap also contains the String pool, and heap memory is shared with all the threads. When heap memory goes full, it throws java.lang.OutOfMemoryError.

How garbage collection works, step by step

Step 1: new objects go to Eden

Initially there are 5 objects, O1 to O5, just created. They all go into Eden.

Eden: O1 O2 O3 O4 O5
S0: –
S1: –
Old: –

Step 2: first GC (minor GC)

The garbage collector invokes for the first time and uses the Mark & Sweep algorithm:

  • Mark: finds out which objects are no longer referenced and need to be deleted.
  • Sweep: deletes those; objects still referenced and which survived go into S0 or S1.

Suppose O2 and O5 are unreferenced and are deleted. The others are swept to whichever survivor space is available, and O6 and O7 are newly created and come in Eden. O1, O3, O4 now have age = 1 (survived one GC).

Eden: O6 O7
S0: O1 O3 O4 (age 1)
S1: –
Old: –

This is a minor GC: it performs GC in the young generation and happens more often than a major GC (which happens in the old generation).

Step 3: second GC

Suppose O7 and O4 now have no reference. The sweep happens. S0 gets emptied and S1 is free, so the survivors move there with their age increased.

Eden: –
S0: –
S1: O6 (age 1), O1 (age 2), O3 (age 2)
Old: –

Step 4: promotion to the old generation

Suppose the threshold age is 3: after that, objects are promoted to the old generation. Suppose O3 is now unreferenced. O1 hits age = 3 (third GC), so it moves to the old generation.

Eden: –
S0: O6 (age 2)
S1: –
Old: O1

Cleaning the old generation is a major GC. It happens less frequently than minor GC. Here also: mark the unreferenced ones, sweep (delete) them.

Versions of GC

GCNotes
1. Serial GCOnly one thread. Slow. GC is very expensive, and all application threads are paused.
2. Parallel GCDefault in Java 8.
3. Concurrent Mark & Sweep (CMS)Better than Parallel GC. No memory compaction. Runs mark & sweep in parallel to application threads: more efficient, but doesn't guarantee 100% efficiency.
4. G1 GCBetter than CMS. Compaction occurs and it is more efficient: application threads work better, pause time reduced.

Application thread pause time is the time the application stops while GC runs. Order from most pause to least: Serial > Parallel > CMS > G1 (still, zero pause time is not guaranteed).

A very rough, theoretical example of throughput: 500 APIs/min, 700 APIs/min, 900 APIs/min, 1300 APIs/min going from Serial up to G1.

Good to know
  • G1 became the default GC in Java 9. Parallel was the default in Java 8.
  • CMS was deprecated in Java 9 and removed in Java 14.
  • Newer low-pause collectors exist: ZGC and Shenandoah (pause times in milliseconds even on huge heaps).
  • Useful flags: -Xms and -Xmx set initial and maximum heap, -Xss sets thread stack size.
Interview corner
Stack vs heap?

Stack: per thread, holds method frames, primitives and references, automatic LIFO cleanup, small and fast; overflows with StackOverflowError. Heap: shared, holds objects, cleaned by GC; fills up with OutOfMemoryError.

When is an object eligible for garbage collection?

When it is no longer reachable through any strong reference from a running thread (for example, all references went out of scope or were set to null).

Does System.gc() force garbage collection?

No, it is only a request. The JVM decides.

Minor GC vs major GC?

Minor GC cleans the young generation (frequent, fast). Major GC cleans the old generation (less frequent, slower).

Why are there two survivor spaces?

At every minor GC the live objects are copied from Eden and the current survivor space into the empty one, which also compacts them. Then the roles swap.

What causes a StackOverflowError?

Usually infinite or very deep recursion filling the thread's stack.

Strong vs weak vs soft references?

Strong is never collected while referenced. Soft is collected only when memory is low. Weak is collected at the next GC. Use WeakHashMap or soft references for caches.
