Generics

Writing one class or method that works safely with many types, with no casting.

The problem generics solve

Without generics, a "box" class would hold an Object, the parent of all, so it accepts everything:

public class Print {
    Object value;
    public Object get() { return value; }
    public void set(Object value) { this.value = value; }
}

We know a parent reference can hold a child object, so this works. But when you read it back, it is just an Object. If you stored a number, it is an Integer, so you have to typecast every time (e.g. (int)).

Generic class

public class Print<T> {
    T value;
    public T getPrintValue() { return value; }
    public void setPrintValue(T value) { this.value = value; }
}

The generic type <T> can be any non-primitive object.

Print<Integer> printObj1 = new Print<Integer>();
printObj1.setPrintValue(1);
Integer printValue = printObj1.getPrintValue();
if (printValue == 1) { }

No typecasting needed, as we defined that this Print can hold only Integer, whereas in the earlier example it could be a String, an Integer or anything.

Subclassing a generic class

// (i) Non-generic subclass: fixes the type
public class ColorPrint extends Print<String> { }

// (ii) Generic subclass: keeps the type open
public class ColorPrint<T> extends Print<T> { }

More than one generic type

public class Pair<K, V> {
    private K key;
    private V value;
    void put(K key, V value) {
        this.key = key;
        this.value = value;
    }
}

new Pair<>();                       // both are correct
new Pair<Integer, String>();

Generic method

Make only the method generic, not the complete class.

  • The type parameter goes before the return type in the method declaration.
  • The type parameter's scope is limited to that method only.
public <K, V> void printValue(Pair<K, V> pair1, Pair<K, V> pair2) {
    if (pair2.getKey().equals(pair1.getKey())) {
        // ...
    }
}

Raw type

For class Print<T> { }, instead of

Print<String> ptpO = new Print<>();   // internally it passes Object as the parameterized type

we can write:

Print rppo = new Print();            // raw type object
rppo.setPrintValue(1);
Good to know

Raw types exist only for backward compatibility with pre-generics code. They switch off the compiler's type checks, so avoid them in new code: you lose exactly the safety generics give.

Bounded generics

Can be used at generic class and method.

  • Upper bound: <T extends Number>. T can be of type Number or its subclass only.
  • Multi bound: <T extends SuperClass & Interface1 & InterfaceN>
    • The first restrictive type should be a concrete class.
    • The 2nd, 3rd and so on can be interfaces.
public class A extends ParentClass implements Interface1, Interface2 { }

public class Print<T extends ParentClass & Interface1 & Interface2> { }

Not more than one concrete class (the diamond problem again).

When you create its object:

Print<A> pobj = new Print<>();

A must be a child of ParentClass and implement both Interface1 and Interface2. If A only implemented Interface1, it could not be used in pobj.

Generics and inheritance

VehicleextendsCarBus
List<Vehicle> vehicleList = new ArrayList<>();
List<Bus>     busList     = new ArrayList<>();

vehicleList = busList;       // ✗ invalid
Vehicle vehicleObj = busObj; // ✓ valid (just one object)

Why invalid? If it were allowed, vehicleList would reference busList, and then you could add a Car through it, but busList can only store buses, not cars. So BusList is not a child of VehicleList; only a busObj is a child of vehicleObj.

void print(List<Vehicle> ls) { }
print(busList);              // ✗ not valid: not a child

Wildcards

The fix for the problem above.

KindSyntaxMeaning
Upper bounded<? extends UpperBound>that class and below (its subclasses)
Lower bounded<? super LowerBound>that class and above (its parents)
Unbounded<?>anything; you can only read
// (i) can accept a list of anything that is a Vehicle or below
public void setPrintValue(List<? extends Vehicle> vehicleList) { }
setPrintValue(busList);              // now it's valid

// (ii) can accept a list of Vehicle or anything above it
public void setPrintValue(List<? super Vehicle> vehicleList) { }
List<Object> objList = new ArrayList<>();
setPrintValue(objList);              // now it's valid

Wildcard vs generic method

public void computeList(List<? extends Number> source, List<? extends Number> dest) { }
// source can be a list of Integer and dest a list of Float

public <T extends Number> void computeList(List<T> source, List<T> dest) { }
// if source is Integer, dest also has to be Integer

With the generic method, both lists must have the same T. With wildcards, each list is free to be a different Number type.

Good to know: PECS

"Producer Extends, Consumer Super". Use ? extends T when you only read from the collection, and ? super T when you only write into it. You cannot add to a List<? extends Vehicle> (except null), because the compiler can't know the exact type.

Type erasure

Type erasure is a process performed by the Java compiler during compilation (i.e. when converting to bytecode), where all generic type information is removed and replaced with their bounds, or with the Object class if unbounded.

You writeBytecode sees
List<T>List<Object>
List<T extends Number>List<Number>

That is why generics exist only at compile time: at runtime a List<String> and a List<Integer> are the same class.

Interview corner
Why can't generics hold primitives?

Because of type erasure the type becomes Object or a bound, and primitives are not objects. Use wrappers: List<Integer>.

Is List<Object> a parent of List<String>?

No. Generics are invariant. Use List<? extends Object> or List<?> to accept any list.

extends vs super in wildcards?

? extends X: X or subclasses, read-only. ? super X: X or parents, good for writing.

What is type erasure and what follows from it?

The compiler removes generic types after checking them. So you cannot do new T(), instanceof List<String>, or overload two methods that differ only in their generic type.
