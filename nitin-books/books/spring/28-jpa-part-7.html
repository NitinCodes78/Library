JPA: One-to-Many Unidirectional (Part 7)

One parent with many children: the join table vs @JoinColumn, lazy/eager fetch, cascade types and orphanRemoval.

What it is

  • One entity is associated with multiple records of another entity, for example a User can have many Orders.
  • Unidirectional: the reference exists in one direction only, from parent to child.
  • Since it is 1:many, one parent row cannot store many child ids, so by default JPA creates a new (join) table to store the mapping.
  • By default it is lazy: when we query the parent, the child rows are not fetched.
@Table(name = "user_details")
@Entity
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long userId;
    private String name;
    private String phone;

    @OneToMany(cascade = CascadeType.ALL)
    private List<OrderDetails> orders = new ArrayList<>();

    public UserDetails() { }
}

@Table(name = "order_details")
@Entity
public class OrderDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String productName;
}

Three tables are created: USER_DETAILS, ORDER_DETAILS and a new join table USER_DETAILS_ORDER_DETAILS with columns ORDER_DETAILS_ID and USER_DETAILS_ID.

What if we do not want the extra table?

Use @JoinColumn. This tells JPA to store the foreign key in the child table instead of creating a new table.

@OneToMany(cascade = CascadeType.ALL)
@JoinColumn(name = "user_id_fk", referencedColumnName = "userId")
private List<OrderDetails> orders = new ArrayList<>();

Now ORDER_DETAILS has ID, USER_ID_FK, PRODUCT_NAME and there is no join table.

1. Insert call

POST /api/user
{ "name": "JohnXYZ", "phone": "1234567890",
  "orders": [ {"productName": "IceCream"}, {"productName": "ColdDrinks"} ] }

One row goes in USER_DETAILS and two in ORDER_DETAILS, each with USER_ID_FK = 1 (cascade does the child inserts).

2. Get call (LAZY)

@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @Autowired UserDetailsService userDetailsService;

    @PostMapping(path = "/user")
    public UserDetails saveUser(@RequestBody UserDetails userDetails) {
        return userDetailsService.saveUser(userDetails);
    }

    @GetMapping("/user/{id}")
    public UserDetailsDTO getUser(@PathVariable Long id) {
        UserDetails output = userDetailsService.findByID(id);
        System.out.println("going to map UserDetails to UserDTO");
        UserDetailsDTO userDTO = output.mapUserDetailsToUserDTO();
        return userDTO;
    }
}

public class UserDetailsDTO {
    private Long id;
    private String name;
    private String phone;
    private List<OrderDetails> orders;

    public UserDetailsDTO(UserDetails userDetails) {
        this.id = userDetails.getUserId();
        this.name = userDetails.getName();
        this.phone = userDetails.getPhone();
        System.out.println("going to query order table here now");
        this.orders = userDetails.getOrderDetails();      // lazy collection touched here
    }
}

Output order in the console: first select ... from user_details where user_id=?, then "going to map UserDetails to UserDTO", then "going to query order table here now", and only then select ... from order_details where user_id_fk=?. The child query fires exactly when the collection is first accessed.

EAGER fetch

@OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
@JoinColumn(name = "user_id_fk", referencedColumnName = "userId")
private List<OrderDetails> orders = new ArrayList<>();

Now the very first query is a single left join between user_details and order_details on user_id = user_id_fk: the parent and children load together.

Cascade types

CascadeTypeEffect
PERSISTSaving User (parent) also saves the related Orders (children).
MERGEUpdating User also updates Orders.
REMOVEDeleting User also deletes Orders.
ALLIncludes all cascade operations.

Orphan removal

Automatically removes a child entry when it is removed from the parent's collection.

@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
@JoinColumn(name = "user_id_fk", referencedColumnName = "userId")
private List<OrderDetails> orders = new ArrayList<>();

Test: insert a user with two orders (IceCream and ColdDrinks), then call an API that does:

@Transactional
public UserDetails removeFirstOrder(Long id) {
    UserDetails output = userDetailsService.findByID(id);
    output.getOrderDetails().remove(0);     // take IceCream out of the list
    return output;
}
  • Without orphanRemoval (false): Hibernate only fires update order_details set user_id_fk=null where user_id_fk=? and id=?. The IceCream row stays in the table with a null FK: an orphan record.
  • With orphanRemoval = true: the row is actually deleted from ORDER_DETAILS.

The persistence context knows all this information because the data is held in memory, so removing an element from the collection is detected at flush time (this is why the method must be transactional).

Good to know
  • CascadeType.REMOVE deletes children when the parent is deleted; orphanRemoval deletes a child when it is removed from the collection. Different triggers, so they are often used together.
  • With the join-table default, every insert touches an extra table; @JoinColumn gives a leaner schema, though a unidirectional one-to-many with a join column issues an extra UPDATE to set the FK after the child insert. A bidirectional mapping (next chapter) avoids that.
  • Accessing a lazy collection outside a transaction/session throws LazyInitializationException; the DTO conversion should happen inside the service/transaction, or use a fetch join.
Interview corner
Why does @OneToMany create a third table?

One parent row cannot hold many child ids, so JPA creates a join table. Add @JoinColumn to keep the FK in the child table.

Cascade REMOVE vs orphanRemoval?

REMOVE: deleting the parent deletes children. orphanRemoval: removing a child from the parent's collection deletes it.

What is the N+1 problem?

One query loads N parents and then lazy loading fires one extra query per parent for its children. Fix with fetch join, @EntityGraph or batch fetching.
