Exception Handling

What Spring Boot does when a controller throws, and how to take control: @ExceptionHandler, @ControllerAdvice, @ResponseStatus.

Who handles an exception?

When an exception escapes a controller, Spring MVC passes it through a chain of exception resolvers, held by HandlerExceptionResolverComposite:

ExceptiontryExceptionHandlerExceptionResolvernot handled?ResponseStatusExceptionResolvernot handled?DefaultHandlerExceptionResolverstill not handled?DefaultErrorAttributes (BasicErrorController)

Each resolver sets the right status and message for the exceptions it understands. If a resolver handled it, the chain stops there.

The default behaviour

@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @GetMapping(path = "/get-user")
    public String getUser() {
        throw new NullPointerException("throwing null pointer exception for testing");
    }
}

The response is a generic JSON with timestamp, status (500), error ("Internal Server Error") and path (/api/get-user), but no custom message.

Now a custom exception that carries a status and a message:

public class CustomException extends RuntimeException {
    HttpStatus status;
    String message;

    CustomException(HttpStatus status, String message) {
        this.status = status;
        this.message = message;
    }
    public HttpStatus getStatus() { return status; }
    @Override public String getMessage() { return message; }
}

@GetMapping(path = "/get-user")
public String getUser() {
    throw new CustomException(HttpStatus.BAD_REQUEST, "request is not correct, UserID is missing");
}

The output is again the same generic 500. Why is our BAD_REQUEST (400) and our message not shown?

  • We are not creating a ResponseEntity; we are just throwing, so some other class builds the response.
  • The exception passes through the three resolvers in sequence. NullPointerException and CustomException are not understood by any of them, so no status or message is set.
  • When control reaches DefaultErrorAttributes (used by the BasicErrorController behind /error), it fills the response with default values: timestamp, status, error, path, and (depending on configuration) message.
// DefaultErrorAttributes (simplified)
errorAttributes.put("timestamp", new Date());
addStatus(errorAttributes, webRequest);
addErrorDetails(errorAttributes, webRequest, includeStackTrace);
addPath(errorAttributes, webRequest);

If we want full control and do not want to depend on the resolvers' defaults, we have to build the ResponseEntity ourselves. The next sections show how.

1. ExceptionHandlerExceptionResolver: @ExceptionHandler and @ControllerAdvice

Controller-level handling

@RestController
@RequestMapping(value = "/api/")
public class UserController {

    @GetMapping(path = "/get-user")
    public ResponseEntity<?> getUser() {
        throw new CustomException(HttpStatus.BAD_REQUEST, "UserID is missing");
    }

    @ExceptionHandler(CustomException.class)
    public ResponseEntity<String> handleCustomException(CustomException ex) {
        return new ResponseEntity<>(ex.getMessage(), ex.getStatus());
    }
}
// 400 Bad Request, body: UserID is missing

Returning an error object

public class ErrorResponse {
    private Date timestamp;
    private String msg;
    private int status;
    // constructor + getters
}

@ExceptionHandler(CustomException.class)
public ResponseEntity<Object> handleCustomException(CustomException ex) {
    ErrorResponse errorResponse = new ErrorResponse(new Date(), ex.getMessage(), ex.getStatus().value());
    return new ResponseEntity<>(errorResponse, ex.getStatus());
}
// {"timestamp": "...", "msg": "UserID is missing", "status": 400}

Several handlers in one controller

@ExceptionHandler(CustomException.class)
public ResponseEntity<String> handleCustom(CustomException ex) {
    return new ResponseEntity<>(ex.getMessage(), ex.getStatus());
}

@ExceptionHandler(IllegalArgumentException.class)
public ResponseEntity<String> handleIllegal(IllegalArgumentException ex) {
    return new ResponseEntity<>(ex.getMessage(), HttpStatus.BAD_REQUEST);
}

One handler for several exceptions

@ExceptionHandler({CustomException.class, IllegalArgumentException.class})
public ResponseEntity<String> handle(Exception ex) {
    return new ResponseEntity<>(ex.getMessage(), HttpStatus.BAD_REQUEST);
}

A handler that does not return a ResponseEntity

If the handler does not build the response, DefaultErrorAttributes creates it. By default Spring Boot hides the message field from this default body; show it with:

server.error.include-message=always

Global handling with @ControllerAdvice

Controller-level @ExceptionHandler has a problem: if several controllers can throw the same exception, the same handler gets copied into each of them, which is code duplication. @ControllerAdvice (or @RestControllerAdvice) moves it to one place for all controllers.

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(CustomException.class)
    public ResponseEntity<String> handleCustomException(CustomException ex) {
        return new ResponseEntity<>(ex.getMessage(), ex.getStatus());
    }
}
Priority rules
  • Controller-level vs global: if both define a handler for the exception, the controller-level one wins (the response shows e.g. "UserID is missing: from Controller ExceptionHandler" rather than the global text).
  • Two handlers that can handle the same exception: Spring picks the closest match in the class hierarchy: first an exact match, then its parent, and so on up the tree. A CustomException handler beats a RuntimeException handler for a CustomException.
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(CustomException.class)                 // chosen for CustomException
    public ResponseEntity<String> custom(CustomException ex) { ... }

    @ExceptionHandler(RuntimeException.class)                // chosen for every other RuntimeException
    public ResponseEntity<String> runtime(RuntimeException ex) {
        return new ResponseEntity<>(ex.getMessage(), HttpStatus.INTERNAL_SERVER_ERROR);
    }
}

2. ResponseStatusExceptionResolver: @ResponseStatus

Handles uncaught exceptions annotated with @ResponseStatus.

Use case 1: on the exception class

@ResponseStatus(HttpStatus.BAD_REQUEST)
public class CustomException extends RuntimeException {
    CustomException(String message) { super(message); }
}

@GetMapping(path = "/get-user")
public ResponseEntity<?> getUser() {
    throw new CustomException("UserID is missing");
}
// 400 Bad Request: {"timestamp": ..., "status": 400, "error": "Bad Request", "path": "/api/get-user"}

You can also give a reason: @ResponseStatus(value = HttpStatus.BAD_REQUEST, reason = "Invalid Request Passed"); that text appears as the message.

Use case 2: on an @ExceptionHandler method

The ResponseStatusExceptionResolver handles uncaught exceptions. When @ResponseStatus sits on an @ExceptionHandler method, the exception is handled by Spring's request handling mechanism itself, not by this resolver.

It gets confusing when the handler also sets the status itself. For example, the handler calls response.sendError(403, ...) and also has @ResponseStatus(400): sendError has already set the status and message, and the @ResponseStatus handling then tries to set them again, which fails on an already committed response (an IOException inside the resolver).

So it is advisable not to use @ExceptionHandler and @ResponseStatus together. If you must, let the handler return nothing and let the annotation decide:

@ExceptionHandler(CustomException.class)
@ResponseStatus(value = HttpStatus.BAD_REQUEST, reason = "Invalid Request Sent")
public void handle(CustomException e) { }

3. DefaultHandlerExceptionResolver

Handles Spring framework related exceptions only, for example HTTP method not supported (405), no handler/resource found (404), missing request parameter or type mismatch (400), unsupported media type (415).

A modern pattern
  • Spring 6 / Boot 3 supports RFC 7807 ProblemDetail: return ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "UserID is missing") from a handler for a standard error body (enable defaults with spring.mvc.problemdetails.enabled=true).
  • Bean validation failures (@Valid on @RequestBody) raise MethodArgumentNotValidException; handle it in your @RestControllerAdvice and return the field errors with a 400.
  • Throw ResponseStatusException(HttpStatus.NOT_FOUND, "user not found") for a quick, one-off error without writing a class.
  • Never expose stack traces to clients (server.error.include-stacktrace=never).
Interview corner
How do you handle exceptions globally in Spring Boot?

@RestControllerAdvice with @ExceptionHandler methods returning a consistent error body.

@ControllerAdvice vs @RestControllerAdvice?

The latter adds @ResponseBody, so handler return values go to the body as JSON.

If a controller and an advice both handle the exception, which wins?

The controller-local handler.

Which resolvers does Spring use, and in what order?

ExceptionHandlerExceptionResolver, ResponseStatusExceptionResolver, DefaultHandlerExceptionResolver; whatever remains falls to Boot's /error endpoint.
