JPA: Mapping Classes to Tables (Part 5)

ddl-auto, @Table, @Column, @Id, composite keys and the id generation strategies (IDENTITY, SEQUENCE, TABLE).

spring.jpa.hibernate.ddl-auto

This setting tells Hibernate how to create and manage the DB schema.

spring.jpa.hibernate.ddl-auto=update
ValueCreate schemaUpdate schemaDelete schemaDetails
nonenononoDo nothing. Good for production.
updateyesyesnoUpdates the schema without deleting existing data or schema. Good for the development environment.
validatenononoAt startup, matches entities against the DB schema and throws an exception on mismatch.
createyesyesyesDrops and re-creates the schema at application startup.
create-dropyesyesyesCreates the schema at startup and drops it at shutdown. Generally the default for in-memory databases like H2.

For production prefer none/validate together with a migration tool (Flyway or Liquibase).

@Table

  • Optional. If not defined, Hibernate generates the table name from the entity name, usually CamelCase to snake_case: UserDetails becomes USER_DETAILS.
  • Attributes: name, schema, catalog, uniqueConstraints, indexes.
@Table(name = "USER_DETAILS")
@Entity
public class UserDetails { /* fields, getters and setters */ }

@Table(name = "USER_DETAILS", schema = "ONBOARDING")      // table inside the ONBOARDING schema
@Entity
public class UserDetails { ... }

@Table(name = "USER_DETAILS",
       schema = "ONBOARDING",
       uniqueConstraints = {
           @UniqueConstraint(columnNames = "phone"),
           @UniqueConstraint(columnNames = {"name", "email"})      // the pair must be unique together
       })
@Entity
public class UserDetails {
    @Id Long id;
    String name;
    String email;
    String phone;
}

@Table(name = "USER_DETAILS",
       indexes = {
           @Index(name = "index_phone", columnList = "phone"),
           @Index(name = "index_name_email", columnList = "name, email")
       })
@Entity
public class UserDetails { ... }

You can verify each one in the H2 console through INFORMATION_SCHEMA (for example CONSTRAINT_COLUMN_USAGE and INDEX_COLUMNS): the unique constraints and indexes show up as generated.

@Column

Optional too: if not defined, JPA adds the column with default values.

@Table(name = "user_details")
public class UserDetails {
    @Id
    private Long id;

    @Column(name = "full_name", unique = true, nullable = false, length = 255)
    private String name;

    private String email;
    private String phone;
}

The table gets the columns ID, EMAIL, FULL_NAME, PHONE. Other attributes: insertable, updatable, precision, scale, columnDefinition.

@Id

  • A primary key must be unique, not null and uniquely identify each record.
  • @Id marks the field as the primary key. An entity has one primary key, and only one field can be annotated with @Id (unless it is a composite key, below).

Composite primary key

A combination of two or more columns that together form the primary key. Two approaches: @IdClass with @Id, and @Embeddable with @EmbeddedId.

Rules for both approaches:

  • The key class must be public.
  • It must implement Serializable.
  • It must have a no-arg constructor.
  • It must override equals() and hashCode().
Why these rules?
  • equals/hashCode: JPA keeps a first-level cache (and optionally a second-level one) in hash maps keyed by the primary key, so key equality must be exact.
  • Serializable: unlike a simple key like String or Long, a composite key is a custom class, and it must be serialisable in case it needs to travel over the network (distributed caching).

Approach 1: @IdClass and @Id

Say we want name and address to be the composite key:

public class UserDetailsCK implements Serializable {
    private String name;
    private String address;

    public UserDetailsCK() { }

    @Override
    public boolean equals(Object obj) {
        if (this == obj) return true;
        if (!(obj instanceof UserDetailsCK)) return false;
        UserDetailsCK userCK = (UserDetailsCK) obj;
        return this.name.equals(userCK.name) && this.address.equals(userCK.address);
    }

    @Override
    public int hashCode() { return Objects.hash(name, address); }
}

@Table(name = "user_details")
@IdClass(UserDetailsCK.class)
@Entity
public class UserDetails {
    @Id private String name;
    @Id private String address;
    private String phone;

    public UserDetails() { }
}

Approach 2: @Embeddable and @EmbeddedId

@Embeddable
public class UserDetailsCK implements Serializable {
    private String name;
    private String address;
    public UserDetailsCK() { }
    // equals() and hashCode() as above
}

@Table(name = "user_details")
@Entity
public class UserDetails {
    @EmbeddedId
    UserDetailsCK userDetailsCK;
    private String phone;

    public UserDetails() { }
}

Both give a table with ADDRESS, NAME, PHONE and a primary key on (name, address). With @EmbeddedId the key is one object (userDetails.getUserDetailsCK().getName()); with @IdClass the fields are on the entity itself.

@GeneratedValue

We know how to define a primary key; we can also define how it is generated. By default primary key columns are not auto-filled. It works with @Id (single key, not with a composite key).

1. GenerationType.IDENTITY

Each insert generates a new identifier (an auto-increment column).

@Table(name = "user_details")
@Entity
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String phone;
}

2. GenerationType.SEQUENCE

  • Used to generate unique numbers.
  • Efficient when we cache sequence values, and gives more control than IDENTITY.
CREATE SEQUENCE user_seq INCREMENT BY 25 START WITH 100 MAXVALUE 9999;
@Table(name = "user_details")
@Entity
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "unique_user_seq")
    @SequenceGenerator(name = "unique_user_seq", sequenceName = "db_seq_name",
                       initialValue = 100, allocationSize = 5)
    private Long id;
    private String name;
    private String phone;
}

Posting two users gives ids 100 and 101.

  • name: a unique name internal to JPA; it is what generator refers to (reusable across entities).
  • sequenceName: the name created in the DB (or the name of a sequence you already created manually).
  • initialValue: the number the sequence starts from.
  • allocationSize: Hibernate prefetches this many ids beforehand so it does not query the DB again and again.

With allocationSize = 5, Hibernate asks the DB sequence once and hands out 5 ids from memory (1st to 5th call); only after the 5th call does it go to the DB again to fetch the next 5.

Insert 1 to 5one sequence call, ids from memoryInsert 6next sequence callnext 5 ids

Advantages of SEQUENCE over IDENTITY:

  1. Custom logic (start point, increment and so on).
  2. Sequence generation is independent of the table, so multiple tables can use it.
  3. A range of ids can be cached, so we avoid hitting the DB for each new id. (With IDENTITY, the DB auto-generates the id during the insert, which needs an additional DB call, and it also prevents Hibernate from batching inserts.)
  4. Better portability: IDENTITY is very DB specific while SEQUENCE behaves more consistently across databases.

3. GenerationType.TABLE

Uses the @TableGenerator annotation, but it is very inefficient:

  • A separate table is created just to manage unique ids.
  • Each time an id is required, a SELECT-UPDATE is executed.
  • Concurrency handling is complex: parallel operations need lock/unlock, which can become a performance bottleneck.

In SEQUENCE the DB handles this internally with an atomic counter, so it is much more efficient.

Good to know
  • GenerationType.AUTO lets the provider choose (with Hibernate 6 it usually picks SEQUENCE where supported). MySQL has no sequences, so IDENTITY is the usual choice there.
  • Use a wrapper type (Long, not long) for generated ids so that "not yet saved" can be null; that is how save() knows to persist instead of merge.
  • Use @Enumerated(EnumType.STRING) for enum columns, never the default ordinal.
Interview corner
ddl-auto values and what you'd use in production?

none, validate, update, create, create-drop. In production use none or validate and manage the schema with Flyway/Liquibase.

IDENTITY vs SEQUENCE?

IDENTITY is DB auto-increment: an id exists only after the insert (disables JDBC insert batching). SEQUENCE lets Hibernate pre-allocate id blocks (allocationSize), which is faster and batch-friendly.

Why override equals and hashCode for a composite key?

Because entity caches are keyed by id; without value-based equality the same row would look like different keys.

@IdClass vs @EmbeddedId?

@IdClass repeats the key fields on the entity and in a separate class; @EmbeddedId groups them in one embeddable object, which is neater to pass around.
