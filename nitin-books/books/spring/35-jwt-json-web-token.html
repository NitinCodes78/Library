JWT (JSON Web Token)

What a JWT is, why it replaced session ids, its structure (header, payload, signature) and its known challenges.

What is a JWT

  • It provides a secure way of transmitting information between parties as a JSON object.
  • The information can be verified because it is digitally signed, using HMAC (a shared secret) or RSA (a public/private key pair) and so on.

Advantages:

  • Compact: small enough to be sent inside an HTTP header, so transmission is fast.
  • Self-contained / stateless: the payload holds all the required information about the user, so it avoids querying the database.
  • Can be signed with symmetric (HMAC) or asymmetric (RSA) keys.
  • A built-in expiry mechanism.
  • Custom claims (additional data) can be added to the JWT.

Where to use a JWT:

  • Authentication: confirming the user identity.
  • Authorization: checking the user's permission before giving access to resources.
  • SSO (Single Sign-On): authenticate once and access multiple applications.

The flow

1. Client logs in with username and password
2. Authentication server generates a token and returns it
3. Client requests the resources, sending the token in the Authorization header
4. Resource server authenticates the user using the token and sends the response

The resource server can validate the token on its own (by checking the signature), or may call endpoints of the authentication server to validate various parts of the token.

What was popular before JWT, and its problems

Session ID (JSESSIONID):

  1. The client logs in with username and password.
  2. The authorization server creates a session id and saves it in a DB with the other user information needed for authentication.
  3. It returns the session id in cookies.
  4. The client sends requests with the cookie.
  5. The resource server queries the DB to look up the session id and validates it.
  6. It sends the response.

Disadvantages:

  • Stateful: it relies on server-side state management, which causes problems in distributed systems.
  • It is just a unique random string; when the server gets this id, it has to perform a DB query to fetch the details.

JWT structure

Three parts separated by dots: aaaaaaaaaa.bbbbbbbbbb.cccccccccc = Header . Payload . Signature.

Header
{ "typ": "JWT", "alg": "RS256", "kid": "sfdsf234234" }

Payload
{ "iss": "https://example.com/auth",
  "sub": "1234567890",
  "exp": 1711945909,
  "email": "conceptandcoding@xyz.com",
  "jti": "unique_id_12312312" }

Signature
RSASHA256( Base64UrlEncode(Header) + "." + Base64UrlEncode(Payload), Key )

Header

  • Contains metadata about the token.
  • typ: type of the token, generally JWT always.
  • alg: the signing algorithm used, like RS256 (RSA) or HS256 (HMAC).
  • kid: key id, to know which key signed it.

Payload

Contains the claims: in simple terms, user information or any additional information. There are three kinds:

ClaimsMeaning
Registered claimsPredefined names and meaning.
Public claimsCustom claims which can be shared and understood by multiple parties.
Private claimsCustom claims intended for internal use only; not standardized, and not expected to be understood by other parties.

Registered claims:

  • iss (Issuer): the entity that issued the JWT.
  • sub (Subject): identifies the user.
  • aud (Audience): identifies the recipient for which the token is intended.
  • exp (Expiration time): after this time the token is not valid.
  • nbf (Not before): before this time the token should not be accepted.
  • iat (Issued at): the time at which the token was issued.
  • jti (JWT id): a unique JWT id.

Signature

  1. Encode the JWT header and payload separately using Base64 (URL-safe) encoding.
  2. Concatenate the encoded header and payload with ".", e.g. xxxxxxxx.yyyyyyyy. This is known as the message.
  3. Use RSA (asymmetric) or HMAC (symmetric) cryptography to create the digital signature of this message.
  4. Encode the signature generated in the previous step.
  5. Concatenate it with "." to get the full token.

Dummy JWT sample (three Base64 parts): eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4ifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV

Sample API request:

curl --location --request GET 'https://exampleHost.com:12345/api/resource' \
  --header 'Authorization: Bearer <the JWT>'

Challenges with JWT

  1. Token invalidation. Say I have blacklisted a user: how do I invalidate their token before it expires? Options:
    • The server keeps a list of blacklisted tokens, and a DB/cache lookup is then needed while validating (this brings state back).
    • Change the secret key, but this invalidates the JWT for all users.
    • Keep tokens very short lived.
    • Or tokens should be used only once.
  2. A JWT is encoded, not encrypted, so anyone can read the payload; it is less secure for sensitive data. Use JWE, meaning the payload part is encrypted, or simply keep sensitive data out of it.
  3. Unsecured JWT with "alg": "none": such a JWT should be rejected.
  4. JWK exploit: a public key embedded in the token itself (the jwk header) should not be used to verify the signature, otherwise an attacker can sign with their own key and ship their own public key inside the token. Here e stands for "exponent" and n for "modulus", and together they form the public key:
{ "typ": "JWT", "alg": "RS256",
  "jwk": { "n": "sfsdf234324324fsd4sfdsfsdf23", "e": "ABC4ED", "kid": "sdfds3432432432fwfdwfsfwf" } }
  1. Instead, use the kid in the header to look up the public key at https://{Auth server domain}/.well-known/jwks.json (a trusted list of keys published by the authentication server).
Good to know
  • Always verify the signature and exp, iss, aud, and pin the expected algorithm on the server.
  • Common design: a short-lived access token (minutes) plus a longer-lived refresh token that can be revoked server-side.
  • HS256 shares one secret between signer and verifier (simple, fine for one service); RS256 lets many services verify with the public key while only the auth server holds the private key.
  • Do not store JWTs in localStorage if XSS is a risk; an HttpOnly cookie is safer (then think about CSRF).
Interview corner
What are the three parts of a JWT?

Header (alg, typ), payload (claims) and signature over header.payload.

Is a JWT encrypted?

No: Base64url-encoded and signed. Anyone can read it; signing only guarantees it was not altered. JWE encrypts it.

How do you log a user out or revoke a JWT?

Short expiry plus refresh tokens, a deny-list of jti values in a cache, or rotating signing keys.

JWT vs session id?

Session id is an opaque pointer needing server-side lookup (stateful). JWT carries verified data itself (stateless) but is harder to revoke.

HS256 vs RS256?

HS256: one shared secret. RS256: private key signs, public key verifies, better for distributed verification.
