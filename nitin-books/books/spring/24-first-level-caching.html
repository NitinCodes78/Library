What does JpaRepository really do?

@Repository
public interface UserDetailsRepository extends JpaRepository<UserDetails, Long> { }
  • Internally it uses the EntityManager API only, but provides predefined methods like findAll, deleteAll and so on.
  • It also provides pagination and sorting.
  • It has @Transactional support on operations that need it (insert, modify, delete).
  • It starts and closes the EntityManager resources, so there is nothing to manage by hand.
// SimpleJpaRepository (Spring Data's implementation)
@Transactional
public <S extends T> S save(S entity) {
    Assert.notNull(entity, "Entity must not be null");
    if (this.entityInformation.isNew(entity)) {
        this.entityManager.persist(entity);      // new entity: INSERT
        return entity;
    } else {
        return this.entityManager.merge(entity); // existing: UPDATE
    }
}

save() is "persist or merge" depending on whether the entity is new (no id yet). Hibernate's SessionImpl is the implementation of the EntityManager APIs; it creates a PersistenceContext (StatefulPersistenceContext) for each EntityManager and does the first-level caching in a map keyed by EntityKey.

First-level cache in action

@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @Autowired UserDetailsService userDetailsService;

    @GetMapping(path = "/test-jpa")
    public UserDetails getUser() {
        UserDetails userDetails1 = new UserDetails("xyz", "xyz@conceptandcoding.com");
        userDetailsService.saveUser(userDetails1);
        UserDetails output1 = userDetailsService.getUser(1L);
        return output1;
    }

    @GetMapping(path = "/read-jpa")
    public UserDetails getUser2() {
        return userDetailsService.getUser(1L);
    }
}

@Service
public class UserDetailsService {
    @Autowired UserDetailsRepository userDetailsRepository;

    public void saveUser(UserDetails user) { userDetailsRepository.save(user); }

    public UserDetails getUser(Long primaryKey) {
        return userDetailsRepository.findById(primaryKey).get();
    }
}

The scope: PersistenceContext follows the EntityManager

This is easy to see by using the EntityManager directly:

@Service
public class UserDetailsService {
    @Autowired EntityManagerFactory entityManagerFactory;

    public UserDetails saveUser(UserDetails user) {

        EntityManager entityManager = entityManagerFactory.createEntityManager();   // session 1 created
        entityManager.getTransaction().begin();                                    // transaction created
        entityManager.persist(user);
        entityManager.find(UserDetails.class, 1L);
        UserDetails output = entityManager.find(UserDetails.class, 1L);            // served from cache: no SQL
        System.out.println("I am able to find the data, name is: " + output.getName());
        entityManager.getTransaction().commit();                                   // transaction committed
        entityManager.close();                                                     // session 1 closed

        EntityManager entityManager2 = entityManagerFactory.createEntityManager(); // session 2 created
        entityManager2.getTransaction().begin();
        entityManager2.find(UserDetails.class, 1L);                                // first time here: SELECT fired
        UserDetails output2 = entityManager2.find(UserDetails.class, 1L);          // then cached
        System.out.println("Session2: I am able to find the data, name is: " + output2.getName());
        entityManager2.getTransaction().commit();
        entityManager2.close();                                                    // session 2 closed
        return output2;
    }
}
  • Inside session 1, find() after persist() needs no SELECT.
  • Once the EntityManager is closed, its persistence context is gone. Session 2 starts empty: its first find() fires a SELECT, and the next find() in the same session is a cache hit.

In a Spring Boot app, when is it shared?

With Spring-managed repositories, the persistence context is bound to the transaction. All repository calls inside the same @Transactional method share one EntityManager, so the second call is a cache hit. Without a surrounding transaction, each repository call gets its own short-lived EntityManager, so it hits the DB each time. (Spring's "open EntityManager in view" setting, on by default, keeps one for the whole web request for reads, and Boot warns about it at startup; set spring.jpa.open-in-view=false to avoid surprises.)

Good to know
  • The first-level cache is always on, per EntityManager, and cannot be switched off. It caches by primary key (find/findById); JPQL queries still hit the DB, but the entities returned are the already-managed instances.
  • Because of it, within one persistence context find(1) twice returns the same Java object.
  • Dirty checking: change a managed entity's field and it is written at flush/commit without calling save().
  • entityManager.clear() or detach() empties it; refresh() reloads from the DB.
  • The cache shared across sessions is the second-level cache (next chapter).
Interview corner
What is the first-level cache and its scope?

The persistence context of an EntityManager/Hibernate Session: per session (per transaction in Spring), mandatory, keyed by entity id.

Why did my second findById not hit the DB?

It ran in the same persistence context, so the entity was already managed.

What does save() do internally?

If the entity is new: persist() (insert). Otherwise: merge() (update).
