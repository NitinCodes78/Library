Spring Boot Security: Parts 2 and 3 (User Creation and Form Login)

Where users come from (default, in-memory, database), password encoding, and form-based stateful authentication with sessions and roles.

User creation

Authentication and authorization of a user happen only after the user is created, so that is the first step. Add the security starter and start the server. In the logs you will see Global AuthenticationManager configured with UserDetailsService bean with name inMemoryUserDetailsManager and a generated password.

  • During startup a user is created automatically with the default username user.
  • A random password is generated (printed in the log) for testing. Every restart generates a new one.

Internally, UserDetailsServiceAutoConfiguration reads SecurityProperties and builds an InMemoryUserDetailsManager (which keeps users in a Map<String, MutableUserDetails> and adds each through createUser).

How can we control user creation?

1st: application.properties (only for development and testing)

spring.security.user.name=my_username
spring.security.user.password=my_password
spring.security.user.roles=ADMIN

Internally it uses reflection to call the setters on SecurityProperties and overrides the defaults. No default user or random password is generated now.

2nd: a custom InMemoryUserDetailsManager bean

UserDetailsServiceextended byUserDetailsManagerimplemented byInMemoryUserDetailsManager
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public UserDetailsService userDetailsService() {
        UserDetails user1 = User.withUsername("my_username_1")
                .password("{noop}my_password_1")
                .roles("ADMIN")
                .build();
        UserDetails user2 = User.withUsername("my_username_2")
                .password("{noop}my_password_2")
                .roles("USER")
                .build();
        return new InMemoryUserDetailsManager(user1, user2);
    }
}

Why do we append {noop}?

The default storage format of a password is {id}encodedPassword, where {id} can be {noop}, {bcrypt}, {sha256} and so on.

  • To store a password without any encoding or hashing, store {noop}plain_password.

During authentication:

  1. It fetches the user's stored password (here from memory).
  2. It goes to the comparison logic: stored password vs the password provided for authentication.
  3. It reads the {id} prefix ({noop}, {bcrypt} ...) and strips it from the stored value.
  4. If {noop}, it compares the remaining stored password directly with the provided password.
  5. If {bcrypt}, it hashes the provided password with BCryptPasswordEncoder and matches it with the remaining stored hash.
PasswordEncoder (interface)
DelegatingPasswordEncoder
the default; delegates to another encoder based on {id}
BCryptPasswordEncoder
NoOpPasswordEncoder

Store a bcrypt hash with the {bcrypt} prefix:

@Bean
public UserDetailsService userDetailsService() {
    UserDetails user1 = User.withUsername("my_username_1")
            .password("{bcrypt}" + new BCryptPasswordEncoder().encode("my_password_1"))
            .roles("ADMIN")
            .build();
    return new InMemoryUserDetailsManager(user1);
}

Memory holds {bcrypt}hashed_password. When we log in with my_password_1 it still succeeds, because the DelegatingPasswordEncoder first checks the stored format {bcrypt} and passes the incoming password to BCryptPasswordEncoder, which hashes and matches it.

If we do not want the {id} prefix, define which encoder to use as a bean. Since we always use one algorithm, control does not go through the DelegatingPasswordEncoder and goes straight to that encoder, so no {id} is needed in front of the password:

@Configuration
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    public UserDetailsService userDetailsService() {
        UserDetails user = User.withUsername("my_username_1")
                .password(new BCryptPasswordEncoder().encode("my_password_1"))
                .roles("ADMIN")
                .build();
        return new InMemoryUserDetailsManager(user);
    }
}

3rd: store username and hashed password in the DB (recommended for production)

@Entity
@Table(name = "user_auth")
public class UserAuthEntity implements UserDetails {    // implements UserDetails
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String username;
    private String password;
    private String role;
    // getters, plus UserDetails methods: getAuthorities() returns List.of(new SimpleGrantedAuthority(role)) ...
}

public interface UserAuthEntityRepository extends JpaRepository<UserAuthEntity, Long> {
    Optional<UserAuthEntity> findByUsername(String username);
}

@Service
public class UserAuthEntityService implements UserDetailsService {   // implements UserDetailsService
    @Autowired private UserAuthEntityRepository userAuthEntityRepository;

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        return userAuthEntityRepository.findByUsername(username)
                .orElseThrow(() -> new UsernameNotFoundException("User not found"));
    }
}

@RestController
@RequestMapping("/auth")
public class AuthController {
    @Autowired private UserAuthEntityService userAuthEntityService;
    @Autowired private PasswordEncoder passwordEncoder;

    @PostMapping("/register")
    public ResponseEntity<String> register(@RequestBody UserAuthEntity userAuthDetails) {
        userAuthDetails.setPassword(passwordEncoder.encode(userAuthDetails.getPassword()));   // store the hash only
        userAuthDetails.setRole("ROLE_USER");
        userAuthEntityService.saveUser(userAuthDetails);
        return ResponseEntity.ok("User registered successfully");
    }
}
  • Why implement UserDetails? During authentication (form, basic, JWT ...) the framework fetches the user and expects a UserDetails object. If our entity does not implement it, we would have to map UserAuthEntity to UserDetails ourselves.
  • Why implement UserDetailsService? Same reason: whatever the authentication method (basic, JWT ...), Spring Security first tries to load the user. Since we keep username and password in a DB, Spring Security does not know how to fetch them unless we provide this service.

By default all endpoints are authenticated, so how do we reach /auth/register, which is just the first step to create a user? We relax authentication for this API, which is industry standard:

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.csrf(csrf -> csrf.disable())            // see the CSRF note below
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/auth/register").permitAll()
                .anyRequest().authenticated())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}

After calling register the response says "User registered successfully" and the USER_AUTH table has the row with the bcrypt hash ($2a$10$...), role ROLE_USER and the username; the raw password is never stored.

(csrf.disable() is only here so that a plain Postman POST to register works. For form login keep CSRF on, see the disadvantages below.)

Form login authentication

  • A stateful authentication method: the server maintains the user's authentication state (a session), so the user does not provide username/password with every request.
  • The user enters credentials in an HTML login form. On success a session (JSESSIONID) is created to keep the authentication state across requests.
  • With subsequent requests the client passes only the JSESSIONID (cookie), and the server validates it against the stored session.
  • It is the default authentication method of Spring Boot Security. Default login URL /login, logout URL /logout.
1. Client: POST /login
username, password
2. Server creates an HTTP session, SESSION ID = #1, saves it in the servlet container
3. Response: Set-Cookie: JSESSIONID=#1
4. Next request: Cookie: JSESSIONID=#1
5. Server searches the HTTP session with id #1: found and valid, the request is fulfilled; not found or invalid, the user must authenticate again
  • By default the session time to live is 30 minutes (depends on the servlet container), and we can configure it.
  • We can also store the HTTP session in the DB.
application.properties
server.servlet.session.timeout=1m       # session expires after 1 minute of inactivity

# store the session in the DB (needs spring-session-jdbc)
spring.session.store-type=jdbc          # not needed in newer Boot versions, the dependency is auto-detected
spring.session.jdbc.initialize-schema=always

Note: if user activity keeps happening, the expiry keeps getting pushed out, so the session does not expire while the user is active. Spring Boot automatically creates and manages the SPRING_SESSION table (and SPRING_SESSION_ATTRIBUTES), and its expiry time keeps increasing as the user keeps sending requests.

Flow for form-based authentication

1. First login (no session exists yet, only the user exists): the login API is invoked.

Request /loginTomcat filtersSecurity Filter Chain: UsernamePasswordAuthenticationFilterdelegatesAuthenticationManagerproviderDaoAuthenticationProviderloads userUserDetailsServicePasswordEncodermatchesSecurityContext saved in HttpSession
  1. UsernamePasswordAuthenticationFilter builds an Authentication object (username, password) and delegates to the AuthenticationManager.
  2. It goes to the AuthenticationProvider (default DaoAuthenticationProvider).
  3. The provider gets the stored user from the UserDetailsService (InMemoryUserDetailsManager, or JdbcUserDetailsManager to manage users in the DB) and validates the incoming raw password with the PasswordEncoder against the stored hashed password.
  4. On success a fully populated Authentication object (username, roles) is stored in the SecurityContext, and the HttpSessionSecurityContextRepository saves that SecurityContext in the HTTP session.

After successful authentication: if the /login endpoint was used directly, the user is sent to the default endpoint (/, for example returning "hello"). If the user had first requested a specific endpoint (say /users), they were redirected to login, and after authenticating that specific endpoint is invoked.

2. Subsequent APIs after authentication:

  1. The request goes through the security filter chain; the SecurityContextHolderFilter tries to read the HTTP session based on the JSESSIONID.
  2. If the session is not valid or not found, the user is redirected to authenticate first.
  3. Otherwise the SecurityContext is loaded from the session via HttpSessionSecurityContextRepository into the SecurityContextHolder, which tells the later filters whether the request is authenticated, and the request goes on to the controller.

It needs almost no code

Form login is the default, so we do not write a line of code for it: it is all handled by the framework. SpringBootWebSecurityConfiguration provides the default chain:

@Bean
SecurityFilterChain defaultSecurityFilterChain(HttpSecurity http) throws Exception {
    http.authorizeHttpRequests(requests -> requests.anyRequest().authenticated());
    http.formLogin(withDefaults());
    http.httpBasic(withDefaults());
    return http.build();
}

All we added is the dependency and config (and, instead of a random password every time, the hard-coded user from the previous section if we want one):

pom.xml: spring-boot-starter-security, spring-session-jdbc

application.properties
spring.security.user.name=user
spring.security.user.password=pass
spring.session.jdbc.initialize-schema=always
server.servlet.session.timeout=5m

If we want to change things (custom login and logout pages, relax authentication on a few endpoints), we override the default SecurityFilterChain bean.

Authorization

Form based authentication is clear, but one thing is left: authorization. Once the user is authenticated and tries to access a resource, a check is needed to make sure the user has permission. By default Spring Boot Security puts no restriction on any resource; we do it manually. Authorization has 2 phases:

  1. Check as part of the SecurityFilter, with requestMatchers(...) (covered now).
  2. Check after the request passes the SecurityFilter and reaches the controller, with method security (covered later, common to all authentication methods: form, basic, JWT).
@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/users").hasRole("USER")
                .anyRequest().authenticated())
            .formLogin(Customizer.withDefaults());
        return http.build();
    }
}

application.properties
spring.security.user.name=user
spring.security.user.password=pass
spring.security.user.roles=USER
  • Any user trying to access /users must have the role ROLE_USER.
  • While using hasRole we do not write the ROLE_ prefix; it is appended automatically.
  • The AuthorizationFilter checks whether the endpoint has a restriction (for example a required role); if yes, it matches the roles in the SecurityContext with what the endpoint requires. If the required role is missing, it throws a Forbidden error (type=Forbidden, status=403).
  • A role can have any name (ADMIN, USER, ANONYMOUS ...) as it is just a string, but it should follow a proper meaning.
  • More than one role can be assigned to a user: spring.security.user.roles=USER,ADMIN, and the rule can be hasAnyRole("USER", "ADMIN").

Controlling sessions per user

One user can keep logging in from different browsers. How do we restrict the number of sessions per user?

http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/users").hasRole("USER")
        .anyRequest().authenticated())
    .sessionManagement(session -> session
        .maximumSessions(1)
        .maxSessionsPreventsLogin(true))
    .formLogin(Customizer.withDefaults());
  • I am already logged in from one browser. When I try to log in from a different browser as the same user, the login page shows "Maximum sessions of 1 for this principal exceeded".
  • maxSessionsPreventsLogin(true) blocks the new login. With false (the default), the new login is allowed and the oldest session is expired instead.

Session creation policies

.sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED))
PolicyBehaviour
IF_REQUIREDHttpSession is created only when needed (default). Example: for a public API where authentication is not required, no HttpSession is created.
ALWAYSHttpSession is always created; if one already exists it is used. Even for a public API with no authentication, a session is created.
NEVERDoes not create a session, but uses one if present.
STATELESSNo session is created; used for stateless applications.

Disadvantages of form-based authentication

  1. Vulnerable to security issues like CSRF and session hijacking. By default CSRF protection is enabled for form-based login and we should not disable it (.csrf(csrf -> csrf.disable()) is something we should not do for form-based authentication).
  2. Session management is a big overhead, and in a distributed system it can lead to scalability issues.
  3. Database load: if there are multiple servers, we may need to store the session in a DB or a cache, which again needs memory and lookup time, and can cause latency.
Good to know
  • Never store raw passwords: BCrypt adds a salt and is deliberately slow, which defends against brute force and rainbow tables.
  • In Spring Security 6 you configure with the lambda DSL (http.authorizeHttpRequests(auth -> ...)) and requestMatchers; the older antMatchers/authorizeRequests are gone. WebSecurityConfigurerAdapter is removed as well.
  • Roles are authorities with the ROLE_ prefix: hasRole("ADMIN") is the same as hasAuthority("ROLE_ADMIN").
  • Unauthenticated gives 401; authenticated but not permitted gives 403.
Interview corner
What does {noop} / {bcrypt} mean in a stored password?

It is the id the DelegatingPasswordEncoder uses to choose the encoder that matches the stored hash.

What do UserDetails and UserDetailsService do?

UserDetails is the user model Spring Security understands; UserDetailsService loads it by username for the authentication provider.

Stateful vs stateless authentication?

Stateful: the server keeps a session. Stateless: each request carries its own proof (Basic header, JWT), and the server stores nothing.

How do you limit concurrent logins?

sessionManagement().maximumSessions(n) with maxSessionsPreventsLogin to either block the new login or expire the old session.
