Hierarchy of transaction managers

A transaction manager is the object that actually begins, commits and rolls back a transaction on the underlying resource.

«interface» TransactionManager
«interface» PlatformTransactionManager
getTransaction, commit, rollback
«abstract class» AbstractPlatformTransactionManager

TransactionManager
  • JDBC (DataSourceTransactionManager) for plain Java Database Connectivity.
  • JPA (JpaTransactionManager) for Java Persistence API / Hibernate.
  • JTA (JtaTransactionManager) for Java Transaction API: used to manage distributed transactions across several resources.

Based on the underlying data source (JDBC, JPA ...), Spring Boot chooses the appropriate transaction manager for you.

Declarative

@Component
public class User {
    @Transactional
    public void updateUser() {
        System.out.println("UPDATE QUERY TO update the user db values");
    }
}

If you define more than one data source, you create one transaction manager per data source and name the one you want:

@Configuration
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        DriverManagerDataSource dataSource = new DriverManagerDataSource();
        dataSource.setDriverClassName("org.h2.Driver");
        dataSource.setUrl("jdbc:h2:mem:testdb");
        dataSource.setUsername("sa");
        dataSource.setPassword("");
        return dataSource;
    }

    @Bean(name = "userTransactionManager")
    public PlatformTransactionManager transactionManager(DataSource dataSource) {
        return new DataSourceTransactionManager(dataSource);
    }
}

@Component
public class UserDeclarative {
    @Transactional(transactionManager = "userTransactionManager")
    public void updateUser() {
        System.out.println("Insert Query ran");
        System.out.println("Update Query ran");
    }
}

Programmatic: two ways

Approach 1: PlatformTransactionManager directly

@Component
public class UserDAO {
    PlatformTransactionManager userTransactionManager;

    UserDAO(PlatformTransactionManager userTransactionManager) {
        this.userTransactionManager = userTransactionManager;
    }

    public void dbOperationWithRequiredPropagationUsingProgrammaticApproach1() {
        DefaultTransactionDefinition transactionDefinition = new DefaultTransactionDefinition();
        transactionDefinition.setName("Testing REQUIRED propagation");
        transactionDefinition.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);

        TransactionStatus status = userTransactionManager.getTransaction(transactionDefinition);
        try {
            // DB work: Propagation.REQUIRED, is transaction active: true
            userTransactionManager.commit(status);
        } catch (Exception e) {
            userTransactionManager.rollback(status);
        }
    }
}

Approach 2: TransactionTemplate

Less boilerplate: the template does the begin/commit/rollback for you.

TransactionTemplate template = new TransactionTemplate(userTransactionManager);
template.setName("TRANSACTION TEMPLATE REQUIRED PROPAGATION");
template.setPropagationBehavior(TransactionDefinition.PROPAGATION_REQUIRED);

template.execute(status -> {
    // DB work, runs inside a transaction; throw or status.setRollbackOnly() to roll back
    return null;
});

To inspect what is happening, use TransactionSynchronizationManager.isActualTransactionActive() and getCurrentTransactionName(). For a declarative method the name is the fully qualified method, like ...UserDeclarative.updateUser; for a non-transactional caller it prints false and null.

Propagation

When a transaction method is called, Spring first checks the propagation value. It tells whether we must create a new transaction or reuse the caller's (the "parent" transaction).

Seeing REQUIRED in action 
@Component
public class User {
    @Autowired UserDAO userDAOobj;

    @Transactional
    public void updateUser() {                                   // parent transaction
        System.out.println("Is transaction active: " + TransactionSynchronizationManager.isActualTransactionActive());
        System.out.println("Some initial DB operation");
        userDAOobj.dbOperationWithRequiredPropagationUsingProgrammaticApproach1();   // joins the parent
        System.out.println("Some final DB operation");
    }

    public void updateUserFromNonTransactionalMethod() {         // no parent
        System.out.println("Is transaction active: " + TransactionSynchronizationManager.isActualTransactionActive());
        userDAOobj.dbOperationWithRequiredPropagationUsingProgrammaticApproach1();   // creates its own
    }
}

From updateUser() the inner call prints the same transaction name as the outer method (it joined). From the non-transactional method it first prints false / null, and the inner call then creates a new transaction.

When to use which
  • REQUIRES_NEW: work that must commit even if the caller later rolls back, such as an audit log or a failed-attempt record.
  • NESTED: try something risky, and roll back only that part (needs savepoint support in the driver, JDBC mainly).
  • MANDATORY: a method that must never be called outside a transaction (it enforces the rule).
  • NOT_SUPPORTED / NEVER: long-running reads or calls where you do not want to hold a transaction (and connection) open.
  • Propagation is applied through the proxy, so it has the same self-invocation limitation as every other @Transactional setting.
Interview corner
REQUIRED vs REQUIRES_NEW?

REQUIRED joins the existing transaction (a rollback affects the whole group). REQUIRES_NEW suspends it and runs an independent one: it can commit or roll back on its own.

If an inner REQUIRED method throws and the outer catches it, does the outer commit?

No. The shared transaction was already marked rollback-only, so the outer commit fails with UnexpectedRollbackException.

Declarative vs programmatic transactions: when programmatic?

When you need a transaction boundary smaller than a method, or dynamic settings decided at runtime.
