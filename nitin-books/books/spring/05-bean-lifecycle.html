Bean and its Lifecycle

How Spring creates an object, prepares it, hands it to you, and later cleans it up.

What is a Bean?

A bean is simply a Java object whose creation and life is managed by the Spring IoC container (the ApplicationContext). You don't write new OrderService(); you describe the class, and Spring builds it, wires it, and keeps it.

Two common ways to tell Spring "make this a bean":

  • Stereotype annotations on the class: @Component, @Service, @Repository, @Controller. Found by component scanning.
  • @Bean methods inside a @Configuration class. Useful when the class is from a library and you can't annotate it.
Example: both ways 
@Service
public class OrderService { }

@Configuration
public class AppConfig {
    @Bean
    public ObjectMapper objectMapper() {
        return new ObjectMapper(); // third-party class
    }
}

@Component vs @Bean

The IoC container (the ApplicationContext provides its implementation) holds all the beans and manages them. There are two ways to create one.

1. @Component (and @Controller, @Service ...)

  • It follows convention over configuration: Spring Boot auto-configures based on conventions, reducing explicit configuration.
  • Spring internally calls new User() for you. That works while the class has a default constructor.

But what if the class only has a constructor with parameters?

@Component
public class User {
    String username;
    String email;

    public User(String username, String email) {   // Spring does not know what to pass here
        this.username = username;
        this.email = email;
    }
}
// APPLICATION FAILED TO START: no default constructor / unsatisfied parameter

2. @Bean: we supply the configuration

Here @Bean comes in: we provide the construction details in a @Configuration class and Spring uses them when creating the bean.

@Configuration
public class AppConfig {

    @Bean
    public User user() {
        return new User("defaultusername", "defaultemail");
    }
}

If you declare two @Bean methods that return the same class (say user() and anotherUser()), Spring creates two beans of it, named after the methods.

How does Spring find the beans?

  1. @ComponentScan scans the given package and its sub-packages for classes annotated with @Component, @Service and so on. @SpringBootApplication already includes it for the package of the main class. 
    @ComponentScan(basePackages = "com.conceptandcoding.learningspringboot")
public class SpringbootApplication { ... }
  2. Explicit definition through @Bean methods inside a @Configuration class.

The lifecycle at a glance

Step by step

  1. Container starts. Spring reads configuration and builds a BeanDefinition (a recipe) for every bean.
  2. Instantiate. The constructor runs. With constructor injection, dependencies arrive right here.
  3. Inject. Field and setter injection (@Autowired) happen now: Spring looks for a bean of the required type and injects it.
  4. Aware callbacks. If the bean implements BeanNameAware, ApplicationContextAware…, Spring hands it that info.
  5. Before-init post-processing. Every BeanPostProcessor gets a look at the bean.
  6. Init hooks, in order: @PostConstruct, then InitializingBean.afterPropertiesSet(), then a custom initMethod.
  7. After-init post-processing. This is where Spring may wrap your bean in a proxy (for @Transactional, @Async, AOP).
  8. In use until the context closes.
  9. Destroy hooks: @PreDestroy, then DisposableBean.destroy(), then a custom destroyMethod.
Example: watching the hooks fire 
@Component
public class CacheLoader {

    @Autowired
    private ProductRepository repo;

    public CacheLoader() {
        // repo is still null here!
        System.out.println("1. constructor");
    }

    @PostConstruct
    void warmUp() {
        // repo is injected now, safe to use
        System.out.println("2. @PostConstruct, loading " + repo.count());
    }

    @PreDestroy
    void cleanUp() {
        System.out.println("3. @PreDestroy, flushing cache");
    }
}

@PostConstruct runs after all dependencies have been injected (not right after the constructor, before injection). That is exactly why it exists: the constructor can't safely use field-injected dependencies, and @PostConstruct can.

Eager vs lazy, and scopes

Singleton beans are created eagerly at startup, so wiring errors show up immediately. Add @Lazy to create a bean only on first use.

For prototype beans, Spring creates a fresh object per request and runs the init hooks, but never calls destroy hooks. After handing it over, Spring stops tracking it. Cleanup is your job.

Interview corner
Why not put startup logic in the constructor?

With field or setter injection, dependencies are still null in the constructor. Use @PostConstruct, or prefer constructor injection so everything arrives together.

Are destroy callbacks called for prototype beans?

No. The container doesn't manage a prototype after creation, so @PreDestroy never runs for it.

Where in the lifecycle are proxies created, and why does it matter?

In postProcessAfterInitialization. Other beans receive the proxy, not the raw object. That's why calling a @Transactional method from inside the same class (self-invocation) skips the transaction: the call never goes through the proxy.

BeanPostProcessor vs BeanFactoryPostProcessor?

BeanFactoryPostProcessor edits bean definitions before any bean exists (e.g. resolving ${...} placeholders). BeanPostProcessor works on bean instances during the lifecycle.
