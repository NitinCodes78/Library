@Async: Part 1

Run a method in another thread, and which executor Spring really uses behind the scenes (it is not always SimpleAsyncTaskExecutor).

Thread pool in a nutshell

  • A thread pool is a collection of threads (workers) available to perform submitted tasks.
  • When a task completes, the worker goes back to the pool and waits for a new task, so threads are reused.
  • In Java it is created with ThreadPoolExecutor.

The @Async annotation

  • Marks a method that should run asynchronously.
  • It runs in a new thread, without blocking the main (caller) thread.
@SpringBootApplication
@EnableAsync
public class SpringbootApplication { ... }

@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @Autowired UserService userService;

    @GetMapping(path = "/getUser")
    public String getUser() {
        System.out.println("inside getUserMethod: " + Thread.currentThread().getName());
        userService.asyncMethodTest();
        return "done";
    }
}

@Component
public class UserService {
    @Async
    public void asyncMethodTest() {
        System.out.println("inside asyncMethodTest: " + Thread.currentThread().getName());
    }
}
inside getUserMethod: http-nio-8080-exec-1
inside asyncMethodTest: task-1
inside getUserMethod: http-nio-8080-exec-2
inside asyncMethodTest: task-2

The controller runs on the Tomcat thread (http-nio-...-exec-N) and the async method on a different thread (task-N).

Which executor does @Async use?

Many places say "Spring Boot uses SimpleAsyncTaskExecutor by default, which creates a new thread each time". That is not fully correct. The framework first looks for a default executor, and only if none is found does it fall back to SimpleAsyncTaskExecutor:

// AsyncExecutionInterceptor
protected Executor getDefaultExecutor(BeanFactory beanFactory) {
    Executor defaultExecutor = super.getDefaultExecutor(beanFactory);
    return (defaultExecutor != null ? defaultExecutor : new SimpleAsyncTaskExecutor());
}

Use case 1: we configure nothing

Only @EnableAsync and @Async. During startup Spring Boot sees no executor bean, so it creates its own default ThreadPoolTaskExecutor (a Spring wrapper around Java's ThreadPoolExecutor) with:

SettingValue
corePoolSize8
maxPoolSize2147483647 (Integer.MAX_VALUE)
keepAliveSeconds60
queueCapacity2147483647 (Integer.MAX_VALUE)

That is why the threads were named task-1, task-2 ... (the default name prefix).

This is not recommended at all:

  1. Under-utilisation of threads. With a fixed core size and an almost unbounded queue, most tasks sit in the queue instead of causing new threads to be created.
  2. High latency. The queue is so large that, under load, tasks wait a long time.
  3. Thread exhaustion. If the queue ever fills, the pool grows up to Integer.MAX_VALUE threads, and the server can go down from the overhead of managing them.
  4. High memory usage. Every thread needs memory.

Use case 2: our own ThreadPoolTaskExecutor bean (recommended)

@Configuration
public class AppConfig {

    @Bean(name = "myThreadPoolExecutor")
    public Executor taskExecutor() {
        int minPoolSize = 2;
        int maxPoolSize = 4;
        int queueSize = 3;
        ThreadPoolTaskExecutor poolTaskExecutor = new ThreadPoolTaskExecutor();
        poolTaskExecutor.setCorePoolSize(minPoolSize);
        poolTaskExecutor.setMaxPoolSize(maxPoolSize);
        poolTaskExecutor.setQueueCapacity(queueSize);
        poolTaskExecutor.setThreadNamePrefix("MyThread-");
        poolTaskExecutor.initialize();
        return poolTaskExecutor;
    }
}

At startup Spring Boot sees a ThreadPoolTaskExecutor bean and makes it the default. Even a bare @Async (no name) now picks myThreadPoolExecutor: threads are named MyThread-1, MyThread-2 ...

Put a sleep in the async method to simulate load and send many requests: first the 2 core threads work, extra tasks wait in the queue (size 3), then threads grow up to the max (4), and any task beyond that is rejected with TaskRejectedException / RejectedExecutionException. This is recommended because it solves every issue of use case 1: bounded size, bounded queue, predictable behaviour.

Use case 3: our own java.util.concurrent ThreadPoolExecutor bean

@Configuration
public class AppConfig {

    @Bean(name = "myThreadPoolExecutor")
    public ThreadPoolExecutor poolExecutor() {
        int minPoolSize = 2, maxPoolSize = 4, queueSize = 3;
        return new ThreadPoolExecutor(minPoolSize, maxPoolSize, 1, TimeUnit.HOURS,
                new ArrayBlockingQueue<>(queueSize), new CustomThreadFactory());
    }
}

class CustomThreadFactory implements ThreadFactory {
    private final AtomicInteger threadNo = new AtomicInteger(1);
    public Thread newThread(Runnable r) { return new Thread(r, "MyThread-" + threadNo.getAndIncrement()); }
}

@Component
public class UserService {
    @Async
    public void asyncMethodTest() { ... }        // no name given
}

Now Spring Boot sees an executor (the plain Java one) and so does not create its own ThreadPoolTaskExecutor; but a bare @Async cannot use a plain ThreadPoolExecutor as the default, so it falls back to SimpleAsyncTaskExecutor. Output: SimpleAsyncTaskExecutor-1, -2 ...

SimpleAsyncTaskExecutor is not recommended: it just creates a new thread every time, which leads to thread exhaustion, thread creation overhead (no reuse) and high memory usage.

So whenever you define a Java ThreadPoolExecutor bean, always name it in @Async:

@Async("myThreadPoolExecutor")
public void asyncMethodTest() {
    System.out.println("inside asyncMethodTest: " + Thread.currentThread().getName());
}

This prints MyThread-1, MyThread-2 ...

The clean way: set the default once

If you do not want to think about use cases 1, 2 or 3 and want your executor to always be the default for every @Async, implement AsyncConfigurer:

@Configuration
public class MyAsyncConfig implements AsyncConfigurer {

    @Override
    public Executor getAsyncExecutor() {
        int minPoolSize = 2, maxPoolSize = 4, queueSize = 3;
        ThreadPoolExecutor poolExecutor = new ThreadPoolExecutor(minPoolSize, maxPoolSize, 1,
                TimeUnit.HOURS, new ArrayBlockingQueue<>(queueSize), new CustomThreadFactory());
        return poolExecutor;                      // used by every @Async without a name
    }
}

Now even a plain @Async uses MyThread-N, not SimpleAsyncTaskExecutor.

Good to know
  • The configurable properties in Spring Boot 3: spring.task.execution.pool.core-size, max-size, queue-capacity, thread-name-prefix. You can tune the auto-configured executor without writing a bean.
  • A ThreadPoolTaskExecutor only grows past corePoolSize when the queue is full, which is why a huge queue makes maxPoolSize meaningless.
  • For fire-and-forget IO work on Java 21 you can also run tasks on virtual threads (spring.threads.virtual.enabled=true).
Interview corner
What executor does @Async use by default?

If there is an executor bean (Spring Boot auto-configures a ThreadPoolTaskExecutor named applicationTaskExecutor, or your own), it is used. Only if none can be resolved does Spring fall back to SimpleAsyncTaskExecutor, which creates a new thread per task.

Why is the default Boot executor risky in production?

Unbounded queue and max pool size: tasks pile up in memory and latency explodes. Configure bounded sizes.

What happens when the pool and queue are full?

The rejection policy kicks in: the default AbortPolicy throws RejectedExecutionException.
