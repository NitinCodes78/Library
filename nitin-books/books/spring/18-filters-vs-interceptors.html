Two places to intercept an HTTP request: one belongs to the servlet container, the other to Spring MVC.

What is a servlet (again)?

A servlet is a Java class that accepts the incoming request, processes it and returns the response. We can create several, for example Servlet 1 configured to handle REST APIs and Servlet 2 configured to handle SOAP APIs. In the same way, DispatcherServlet is the servlet provided by Spring, configured by default to handle all APIs (/*).

So a Filter can sit in front of any servlet, even a non-Spring one. An Interceptor only sees requests that already made it to the DispatcherServlet and were matched to a handler.

A filter in code

@Component
@Order(1)
public class RequestLoggingFilter implements Filter {

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        System.out.println("before: " + ((HttpServletRequest) request).getRequestURI());
        chain.doFilter(request, response);       // pass to the next filter / servlet
        System.out.println("after the response is produced");
    }
}

A filter must call chain.doFilter(...) to let the request continue; not calling it stops the request.

Multiple interceptors and ordering

Registered in order inside addInterceptors; preHandle runs in that order, postHandle/afterCompletion in reverse. If preHandle returns false, the next interceptor and the controller are not invoked.

@Configuration
public class AppConfig implements WebMvcConfigurer {
    @Autowired MyCustomInterceptor1 myCustomInterceptor1;
    @Autowired MyCustomInterceptor2 myCustomInterceptor2;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        // below order is maintained while calling the interceptors
        registry.addInterceptor(myCustomInterceptor1)
                .addPathPatterns("/api/*")                                   // apply to these URL patterns
                .excludePathPatterns("/api/updateUser", "/api/deleteUser");  // exclude for these
        registry.addInterceptor(myCustomInterceptor2)
                .addPathPatterns("/api/*")
                .excludePathPatterns("/api/updateUser");
    }
}
Which one should I use?
  • Filter: security (Spring Security is itself a chain of filters), CORS, compression, request/response logging or rewriting the raw request body, anything independent of Spring MVC.
  • Interceptor: logic that needs to know which controller method will run (HandlerMethod, its annotations), timing of handlers, per-endpoint checks.
  • AOP (the earlier chapter) works at the method level of any bean, not only web requests.
  • Filters can wrap the request/response objects (for example to cache the body); interceptors cannot replace them.
Interview corner
Filter vs Interceptor?

Filter belongs to the servlet container and runs before the DispatcherServlet; interceptor belongs to Spring MVC and runs after the handler is chosen, before and after the controller. Interceptors know the handler method; filters don't.

Which runs first?

Filters, then the DispatcherServlet, then interceptors, then the controller. On the way out the order reverses.

Where does Spring Security plug in?

As a filter chain (DelegatingFilterProxy / FilterChainProxy), so it runs before any interceptor.
