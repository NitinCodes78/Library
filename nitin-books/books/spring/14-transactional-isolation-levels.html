@Transactional: Isolation Levels

How much of one transaction's work another running transaction may see: dirty, non-repeatable and phantom reads.

What is an isolation level?

It tells how the changes made by one transaction are visible to other transactions running in parallel.

@Transactional(propagation = Propagation.REQUIRED, isolation = Isolation.READ_COMMITTED)
public void updateUser() { ... }
Isolation levelDirty readNon-repeatable readPhantom readConcurrency
READ_UNCOMMITTEDPossiblePossiblePossibleHighest
READ_COMMITTEDNoPossiblePossibleHigh
REPEATABLE_READNoNoPossibleLower
SERIALIZABLENoNoNoLowest

The default isolation level depends on the database: most relational databases (PostgreSQL, Oracle, SQL Server) default to READ_COMMITTED, while MySQL's InnoDB defaults to REPEATABLE_READ. With Isolation.DEFAULT, Spring just uses the database's own default.

The three problems

1. Dirty read

Transaction A reads uncommitted data of another transaction. If that other transaction is then rolled back, what A read never really existed: a dirty read.

T1BEGINBEGINid 123: Free
T2Update row 123 to Booked (not committed)id 123: Free (committed)
T3Read row 123: Booked
T4Rollbackid 123: Free

2. Non-repeatable read

Transaction A reads the same row several times and may get a different value because another transaction updated and committed it in between.

TimeTransaction AOther
T1BEGIN
T2Read row 1: Free
T3Another transaction changes row 1 to Booked and commits
T4Read row 1: Booked

3. Phantom read

Transaction A runs the same query several times, but the set of rows returned differs because another transaction inserted (or deleted) rows and committed.

TimeTransaction AOther
T2read where id > 0 and id < 5: 2 rows (id 1, 3)
T3Inserts row id 2 and commits
T4same query: 3 rows (id 1, 2, 3)
Easy way to remember

Dirty read: a row's uncommitted value. Non-repeatable: the same row's value changes. Phantom: the number of rows changes.

How databases enforce it: locking

Locks make sure no other transaction updates the locked rows.

Held lockAnother shared lockAnother exclusive lock
Shared lock (S), also called a read lockYesNo
Exclusive lock (X), also called a write lockNoNo
Isolation levelLocking strategy
Read UncommittedRead: no lock. Write: no lock.
Read CommittedRead: shared lock, released as soon as the read is done. Write: exclusive lock, kept to the end of the transaction.
Repeatable ReadRead: shared lock, released only at the end of the transaction. Write: exclusive lock, released at the end of the transaction.
SerializableSame as Repeatable Read, plus a range lock, all released at the end of the transaction.

This is the classic lock-based picture. Modern databases like PostgreSQL, Oracle and InnoDB mostly use MVCC (readers see a snapshot, so reads don't block writes) instead of read locks, but the guarantees per level stay as in the table above.

Interview corner
Which isolation level would you use for a booking or payment flow?

Usually READ_COMMITTED with explicit protection of the critical row (pessimistic lock SELECT ... FOR UPDATE or an optimistic @Version check). SERIALIZABLE is correct but kills throughput.

Explain dirty, non-repeatable and phantom reads.

Uncommitted data read; same row read twice gives two values; same query returns a different set of rows.

What is the trade-off as isolation goes up?

More consistency, but more locking or retries and lower concurrency.
