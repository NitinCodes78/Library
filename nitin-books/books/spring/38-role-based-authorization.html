Spring Boot Security: Role Based Authorization (Annotations)

@PreAuthorize and @PostAuthorize with roles, permissions and SpEL, instead of one long list of URL rules.

Why annotations?

We have covered the different types of authentication, and also how authorization can be done at the Security Filter layer itself:

http.authorizeHttpRequests(auth -> auth
        .requestMatchers("/users").hasRole("USER")
        .anyRequest().authenticated())
    .formLogin(Customizer.withDefaults());

But in a large-scale application with hundreds of APIs, managing the roles in the security filter becomes difficult and does not scale. That is where annotation-based role authorization comes in: the rule sits right on the controller (or service) method.

Recall the authentication flow (Basic as the example): BasicAuthenticationFilter decodes the header, creates an Authentication object (not authenticated yet), the AuthenticationManager and provider fetch the user via UserDetailsService and compare passwords, and on success the object's authenticated status is changed and it is stored in the SecurityContextHolder. It now carries the username and the authorities (roles and permissions). The annotations read these authorities.

The two annotations

AnnotationWhen
@PreAuthorizeDoes authorization before the execution of the API/method.
@PostAuthorizeDoes authorization after the execution of the API/method, but before the response is sent back to the user.

Create users first (dynamically)

As in the user-creation chapter, but now a user has one role (ROLE_ADMIN, ROLE_USER ...) and many permissions (ORDER_READ, SALES_DELETE ...), which are more granular.

@Entity
@Table(name = "user_login")
public class UserLoginEntity implements UserDetails {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(unique = true, nullable = false)
    private String username;
    @Column(nullable = false)
    private String password;
    private String role;

    @OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
    private List<UserPermissionEntity> permissions = new ArrayList<>();

    @Override
    public Collection<? extends GrantedAuthority> getAuthorities() {
        Set<GrantedAuthority> authorities = new HashSet<>();
        authorities.add(new SimpleGrantedAuthority(role));                       // the role, e.g. ROLE_USER
        permissions.forEach(permission ->
            authorities.add(new SimpleGrantedAuthority(permission.getName())));  // each permission, e.g. ORDER_READ
        return authorities;
    }
    @Override public String getPassword() { return password; }
    @Override public String getUsername() { return username; }
    // getters and setters
}

@Entity
@Table(name = "user_permission")
public class UserPermissionEntity {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    // getters and setters
}

@Service
public class UserLoginEntityService implements UserDetailsService {
    @Autowired private UserLoginEntityRepository userLoginEntityRepository;

    @Override
    public UserDetails loadUserByUsername(String username) throws UsernameNotFoundException {
        return userLoginEntityRepository.findByUsername(username)
                .orElseThrow(() -> new UsernameNotFoundException("user not found"));
    }
    public UserDetails save(UserLoginEntity userLoginEntity) { return userLoginEntityRepository.save(userLoginEntity); }
}

@Repository
public interface UserLoginEntityRepository extends JpaRepository<UserLoginEntity, Long> {
    Optional<UserLoginEntity> findByUsername(String username);
}

@RestController
public class UserController {
    @Autowired UserLoginEntityService userLoginEntityService;
    @Autowired PasswordEncoder passwordEncoder;

    @PostMapping("/user-login")
    public ResponseEntity<String> register(@RequestBody UserLoginEntity userLoginEntity) {
        userLoginEntity.setPassword(passwordEncoder.encode(userLoginEntity.getPassword()));
        userLoginEntityService.save(userLoginEntity);
        return ResponseEntity.ok("User registered successfully!");
    }
}

Security config

@Configuration
@EnableWebSecurity
@EnableMethodSecurity(prePostEnabled = true)       // without this, @PreAuthorize / @PostAuthorize are ignored
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/user-login").permitAll()
                .anyRequest().authenticated())
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())
            .httpBasic(Customizer.withDefaults());
        return http.build();
    }
}

(@EnableMethodSecurity is the current annotation; prePostEnabled is true by default in it. The older @EnableGlobalMethodSecurity is deprecated.)

hasRole vs hasAuthority

Spring treats both in a similar way. The only difference: for hasRole the prefix "ROLE_" is appended. SecurityExpressionRoot shows this:

private String defaultRolePrefix = "ROLE_";

public final boolean hasAuthority(String authority) { return hasAnyAuthority(authority); }
public final boolean hasAnyAuthority(String... authorities) { return hasAnyAuthorityName(null, authorities); }

public final boolean hasRole(String role) { return hasAnyRole(role); }
public final boolean hasAnyRole(String... roles) { return hasAnyAuthorityName(this.defaultRolePrefix, roles); }

private boolean hasAnyAuthorityName(String prefix, String... roles) {
    Set<String> roleSet = getAuthoritySet();
    for (String role : roles) {
        String defaultedRole = getRoleWithDefaultPrefix(prefix, role);
        if (roleSet.contains(defaultedRole)) return true;       // found a matching authority
    }
    return false;
}

So hasRole('USER') checks for the authority ROLE_USER, while hasAuthority('ORDER_READ') checks for exactly ORDER_READ.

How does it run before the controller method?

It is because of interceptors, but method-level ones (AOP proxies around the bean): @PreAuthorize is intercepted by AuthorizationManagerBeforeMethodInterceptor. (What interceptors are, how they work and how they differ from filters we have already covered in depth.) The flow: the request passes the security filters (authentication), reaches the DispatcherServlet and the controller proxy, where the method interceptor checks the annotation first.

Requestsecurity filters: authenticateDispatcherServletproxyAuthorizationManagerBeforeMethodInterceptorallowedController method

The expression is SpEL

@PreAuthorize("hasRole('USER') and hasAuthority('ORDER_READ')") uses SpEL (Spring Expression Language). The framework's SpelExpressionParser compiles these strings. High-level flow:

  1. Read the string from the @PreAuthorize annotation.
  2. Parse it with SpelExpressionParser, converting the string into an AST (Abstract Syntax Tree); and becomes an OpAnd node, whose evaluation returns false at once if the left operand is false, otherwise it evaluates the right operand.
  3. AuthorizationManagerBeforeMethodInterceptor resolves the references found in the expression (hasRole, hasAuthority, authentication ...).
  4. It validates the result and decides whether to invoke the method or not (access denied, 403).

Method parameters can be referenced with #, and the current user with authentication.principal, so a user can be allowed to read only their own data:

@PreAuthorize("#id == authentication.principal.id")
@GetMapping("/users/{id}")
public User fetchUserDetails(@PathVariable Long id) {
    return userServiceObject.fetchUserDetails(id);
}

(This needs the principal to expose getId(), which our UserLoginEntity does.)

@PostAuthorize

  • Authorization happens after the method executes but before the response goes back to the user.
  • It is intercepted by AuthorizationManagerAfterMethodInterceptor.
  • Typical use: the decision depends on what the method returned (use returnObject in the expression), for example only the owner of an order may see it.

Example. Two users were created (a_user and b_user, both ROLE_USER, with ORDER_READ). For testing, the API hard-codes the user id in the returned order to the id of a_user:

@RestController
@RequestMapping("/api")
public class OrderController {

    @GetMapping("/orders")
    @PreAuthorize("hasRole('USER') and hasAuthority('ORDER_READ')")
    @PostAuthorize("returnObject.userID == authentication.principal.id")
    public OrderDTO getOrders() {
        OrderDTO orderDTO = new OrderDTO();
        orderDTO.userID = 1L;                  // for testing: id of a_user
        orderDTO.orderID = 106001;
        return orderDTO;
    }
}
  • Invoke it with b_user's credentials: the method runs, but the returned object's userID does not match the logged-in principal's id, so the response is 403 Forbidden and the data is not sent.
  • Invoke it with a_user's credentials: the ids match and the order is returned.

Note: the method body has already executed by then (a write would already have happened), so use @PostAuthorize for reads and put the cheap check in @PreAuthorize when you can.

Good to know
  • Method security works through Spring AOP proxies, so it applies only when the call goes through the proxy: a method calling another annotated method on this (self-invocation) bypasses the check, and it works on Spring beans only (the same limitation as @Transactional).
  • Put the annotations on the service layer as well if the logic can be reached from outside the controller.
  • Related: @Secured("ROLE_ADMIN") and @RolesAllowed are simpler (no SpEL), and @PreFilter/@PostFilter filter collections.
  • Unauthenticated gives 401; authenticated but lacking the role/permission gives 403. Handle AccessDeniedException with a @ControllerAdvice or AccessDeniedHandler for a custom body.
  • Roles are coarse ("what kind of user"), permissions are fine-grained ("what action"); granting permissions to roles in the DB keeps the annotations stable while access rules change.
Interview corner
@PreAuthorize vs @PostAuthorize?

Pre checks before the method runs (can use arguments); Post checks after, using returnObject, before the response is returned.

hasRole vs hasAuthority?

hasRole adds the ROLE_ prefix; hasAuthority matches the exact string. Both look at the same granted authorities.

My @PreAuthorize is ignored. Why?

Method security is not enabled (@EnableMethodSecurity), or the call bypasses the proxy (self-invocation, non-bean, final/private method).

URL-based vs annotation-based authorization?

URL rules are central and coarse; annotations sit next to the code, support SpEL and method arguments/return values, and scale better in big APIs. Many apps use both.

How do you let users see only their own data?

@PreAuthorize("#id == authentication.principal.id"), or @PostAuthorize on the returned object's owner.
