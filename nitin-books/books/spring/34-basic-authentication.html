Spring Boot Security: Basic Authentication

Stateless authentication where the client sends username and password in the Authorization header on every request.

What it is

  • A stateless authentication method: the server does not maintain the user's authentication state (no session).
  • The client must pass the username and password with every request using the Authorization header:
Authorization: Basic <base64(username:password)>
  • The credentials are encoded with Base64, which is not encryption, so Basic authentication is insecure over plain HTTP. Always use HTTPS.

Step by step

1st: create a user

We have already discussed all the ways to create users (properties, in-memory bean, DB with a registration API and BCrypt) in the previous chapter; refer to it if there is any doubt. For testing:

application.properties
spring.security.user.name=my_username
spring.security.user.password=my_password
spring.security.user.roles=USER

2nd: how the header is read

The BasicAuthenticationFilter:

  1. Reads the Authorization header.
  2. Decodes the Base64 value to get the username and password the client passed.
  3. Creates an UsernamePasswordAuthenticationToken and hands it to the AuthenticationManager.

For example Authorization: Basic bXlfdXNlcm5hbWU6bXlfcGFzc3dvcmQ= decodes to my_username:my_password. (Postman does the encoding for you when you choose Basic Auth.)

Why in the Authorization header, and not in the body or elsewhere?

  1. Standard. The HTTP standard (RFC 7617) defines this format, so it is universally accepted across APIs and clients. If everybody sent credentials differently (some in headers, some in the body ...), dealing with multiple APIs and clients would be difficult.
  2. Security. Web servers sometimes log the request body for debugging or analytics, but headers like Authorization are typically not logged, which reduces the risk of exposing the credentials.
  3. Support for all HTTP methods. Apart from POST and PUT, requests like GET do not accept a body. With headers, credentials can be sent consistently for every kind of API.

The flow

If the form-based flow is understood, this is very similar, just without a session.

Request + Authorization headerTomcat filtersSecurity Filter Chain: BasicAuthenticationFilterdecode headerAuthenticationManagerproviderDaoAuthenticationProviderload userUserDetailsServicehash and comparePasswordEncoderon successAuthorizationFilterrole checkController
  1. BasicAuthenticationFilter decodes the Authorization header and builds the authentication object (username and password).
  2. AuthenticationManager to AuthenticationProvider (default DAO implementation).
  3. The provider fetches the user via UserDetailsService (InMemoryUserDetailsManager or JdbcUserDetailsManager to manage username/password in the DB), hashes the incoming password with the PasswordEncoder and compares it with the stored hash.
  4. On success the authenticated object goes into the SecurityContext for this request only (stateless: nothing is saved in a session).
  5. AuthorizationFilter checks the role needed by the endpoint, then the controller runs.

What we need to implement it

pom.xml: spring-boot-starter-security (+ web)
application.properties: the user, as above
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                .requestMatchers("/users").hasAnyRole("USER", "ADMIN")      // added for authorization
                .anyRequest().authenticated())
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))     // stateless: no session
            .csrf(csrf -> csrf.disable())                                   // CSRF is not required for a stateless API
            .httpBasic(Customizer.withDefaults());                          // Basic authentication
        return http.build();
    }
}
  • httpBasic(...) turns Basic authentication on (and we do not call formLogin).
  • STATELESS tells Spring not to create or use an HttpSession.
  • CSRF protection is not needed here because the browser does not automatically attach Basic credentials in the way it attaches session cookies to forged requests from other sites (a client-side script must set the header itself). Keep it enabled if a browser could be sending the credentials automatically.

Disadvantages of Basic authentication

  1. Credentials are sent in every request. If HTTPS is not enforced they can be intercepted and decoded.
  2. If the credentials are compromised, the only way is to change the credentials (there is no short-lived token to revoke).
  3. Not suitable for large-scale applications, as sending credentials with every request is extra overhead:
    • the request size grows because of the Authorization header;
    • extra work like decoding, hashing the incoming password (BCrypt is intentionally slow) and comparing, on every single request;
    • a DB lookup to fetch the user details, which increases latency too.
Good to know
  • Basic authentication is fine for service-to-service calls inside a trusted network, internal tools and quick tests. For user-facing APIs prefer token based approaches (JWT, OAuth2), covered next.
  • The 401 response carries WWW-Authenticate: Basic realm="Realm", which makes a browser pop up its own login dialog.
Interview corner
Is Base64 encryption?

No, it is reversible encoding. Anyone who sees the header can decode it, so use HTTPS.

Why is Basic authentication called stateless?

The server keeps no session; credentials arrive and are verified on every request.

Why send credentials in a header instead of the body?

RFC 7617 standard format, headers are less likely to be logged than bodies, and it works for GET requests which have no body.

Why disable CSRF with Basic auth plus STATELESS?

CSRF abuses ambient cookie-based sessions; with no session and an explicit header there is nothing automatically attached by the browser to forge.
