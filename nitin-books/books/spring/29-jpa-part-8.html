Derived queries

  • Spring Data automatically generates the query from the method name.
  • You must follow a specific naming convention.
  • Derived queries are used for GET / REMOVE operations, not for INSERT/UPDATE. Insert and update are supported through save().

The method name is parsed by PartTree using a pattern like:

^(find|read|get|query|search|stream|count|exists|delete|remove)((\p{Lu}.*?))??By

That means the name must start with one of find / read / get / query / search / stream / count / exists / delete / remove, then zero or more characters (starting with an uppercase letter, for example UserDetails), and then By, followed by the conditions.

@Entity
@Table(name = "user_details")
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long userId;
    @Column(name = "user_name")
    private String name;
    private String phone;
}

@Repository
public interface UserDetailsRepository extends JpaRepository<UserDetails, Long> {
    List<UserDetails> findUserDetailsByName(String userName);
}

It translates to select ud1_0.user_id, ud1_0.user_name, ud1_0.phone from user_details ud1_0 where ud1_0.user_name=?.

Pagination and sorting

Spring Data provides two types in org.springframework.data.domain: Pageable (page number, page size = records per page) and Sort.

@Repository
public interface UserDetailsRepository extends JpaRepository<UserDetails, Long> {
    List<UserDetails> findUserDetailsByNameStartingWith(String userName, Pageable pageable);
}

public List<UserDetails> findByNameDerived(String name) {
    Pageable pageable = PageRequest.of(1, 3);            // page index (starts at 0), size 3
    return userDetailsRepository.findUserDetailsByNameStartingWith(name, pageable);
}

The SQL ends with offset ? rows fetch first ? rows only. If you need more information about the pages, use Page as the return type:

Page<UserDetails> findUserDetailsByNameStartingWith(String userName, Pageable page);

Page<UserDetails> userDetailsPage = userDetailsRepository.findUserDetailsByNameStartingWith(name, pageable);
List<UserDetails> list = userDetailsPage.getContent();
System.out.println("total pages: " + userDetailsPage.getTotalPages());
System.out.println("is first page: " + userDetailsPage.isFirst());
System.out.println("is last page: " + userDetailsPage.isLast());

With 5 matching rows and page size 3, page index 1 gives total pages 2, is first false, is last true. (Page fires an additional count query; Slice skips it.)

Sorting only, and pagination with sorting

List<UserDetails> findUserDetailsByNameStartingWith(String userName, Sort sort);

userDetailsRepository.findUserDetailsByNameStartingWith(name, Sort.by("name").descending());
userDetailsRepository.findUserDetailsByNameStartingWith(name, Sort.by("name", "phone").ascending());
  • Sort.by accepts multiple fields; sorting is applied in order: first by the first field, and if there are duplicates then the second field is used, and so on.
  • For a different order per field:
Sort sort = Sort.by(
    Sort.Order.asc("name"),
    Sort.Order.desc("phone")
);
return userDetailsRepository.findUserDetailsByNameStartingWith(name, sort);

// both together
Pageable pageable = PageRequest.of(0, 3, Sort.by("name").ascending());

JPQL

For queries which are a little complex and cannot be handled by a derived query, use JPQL (Java Persistence Query Language).

  • Similar to SQL but works on entity objects instead of directly on the database.
  • Database independent.
  • Works with entity names and field names, not table and column names.
@Query("SELECT u FROM UserDetails u WHERE u.name = :userFirstName")
List<UserDetails> findByUserName(@Param("userFirstName") String userName);
  • UserDetails is an entity (not a table name); u is the alias and selecting it returns all fields; u.name is the entity field (not a column name).
  • :userFirstName is a named parameter, bound to the method parameter by @Param.
  • There is no strict rule for the return type: a List or a single object. But if more than one row comes back and the return type is a single object, JPA throws an exception (IncorrectResultSizeDataAccessException).

JPQL with JOIN

OneToOne:

@Query("SELECT ud FROM UserDetails ud JOIN ud.userAddress ad WHERE ud.name = :userFirstName")
List<UserDetails> findUserDetailsWithAddress(@Param("userFirstName") String userName);

SQL: from user_details ud1_0 join user_address ua1_0 on ua1_0.id = ud1_0.user_address_id where ud1_0.user_name=?.

To select only some fields, return List<Object[]>:

@Query("SELECT ud.name, ad.country FROM UserDetails ud JOIN ud.userAddress ad WHERE ud.name = :userFirstName")
List<Object[]> findUserDetailsWithAddress(@Param("userFirstName") String userName);

public List<UserDTO> findByNameDerived(String name) {
    List<Object[]> dbOutput = userDetailsRepository.findUserDetailsWithAddress(name);
    List<UserDTO> output = new ArrayList<>();
    for (Object[] val : dbOutput) {
        String userName = (String) val[0];
        String country = (String) val[1];
        output.add(new UserDTO(userName, country));
    }
    return output;
}

If we do not want Object[], we can return a custom DTO directly with a constructor expression: SELECT new com.example.UserDTO(ud.name, ad.country) FROM ... (or an interface projection).

OneToMany: the same syntax:

@Entity @Table(name = "user_details")
public class UserDetails {
    ...
    @OneToMany(cascade = CascadeType.ALL)
    @JoinColumn(name = "user_id")
    private List<UserAddress> userAddressList = new ArrayList<>();
}

@Query("SELECT ud FROM UserDetails ud JOIN ud.userAddressList ad WHERE ud.name = :userFirstName")
List<UserDetails> findUserDetailsWithAddress(@Param("userFirstName") String userName);

The N+1 problem and its solutions

Problem

Say one user can have many addresses, and our query can fetch more than one user. With N users JPA fires:

  • 1 query to fetch all the users;
  • for each user, a query to fetch its addresses, so N more.

Total queries hit: N + 1. We need a way to hit just one.

1 queryusersN users+ N queriesaddresses per user

Example: two users named "AA" with two address rows. The JPQL above returns 2 users; for each user Hibernate fires a separate select ... from user_address where user_id=?, so 2 selects on the child table (in total 3 queries).

Can EAGER fetching solve it?

No. EAGER works as a single join query only when we fetch one parent by id (like findById): JPA drafts a join. When a query fetches multiple parents each with multiple children, EAGER does not collapse into one query: it first fetches all the parents, then for each parent fetches its children, which is the same N+1.

Solution 1: JOIN FETCH (JPQL)

@Query("SELECT ud FROM UserDetails ud JOIN FETCH ud.userAddressList ad WHERE ud.name = :userFirstName")
List<UserDetails> findUserDetailsWithAddress(@Param("userFirstName") String userName);

Now one SQL with a join returns users and addresses together: 1 query.

Solution 2: @BatchSize(size = 10)

  • It will not make it only 1 query, but it reduces the count by dividing the loading into batches.
@OneToMany(cascade = CascadeType.ALL, fetch = FetchType.EAGER)
@JoinColumn(name = "user_id")
@BatchSize(size = 10)
private List<UserAddress> userAddressList = new ArrayList<>();

Instead of one query per user, Hibernate fetches children with where user_id in (?, ?, ...) for up to 10 parents at a time: N users need about 1 + N/10 queries.

Solution 3: @EntityGraph

  • Used over the method (helpful with derived methods).
  • Tells JPA to fetch all the UserAddress entries along with the user details.
@EntityGraph(attributePaths = "userAddressList")
List<UserDetails> findUsersBy();

Joining many tables

It is almost the same as SQL. Table A has a one-to-many with B, and B has a one-to-many with C:

@Query("SELECT a FROM A a JOIN a.bList b JOIN b.cList c WHERE c.someProperty = :someValue")
List<A> findAWithBAndC(@Param("someValue") String someValue);

@Modifying

  • When @Query is used, JPA by default expects a SELECT.
  • If we use DELETE, UPDATE or INSERT with @Query, JPA throws an error.
  • @Modifying tells JPA to expect a DELETE/UPDATE (or INSERT) query.
  • Since we are changing the DB we also need @Transactional.
@Modifying
@Query("DELETE FROM UserDetails ud WHERE ud.name = :userFirstName")
void deleteByUserName(@Param("userFirstName") String userName);

flush and clear with @Modifying

  • flush pushes the persistence-context changes to the DB but keeps the values in the persistence context.
  • clear purges the persistence context, so a fresh DB call is needed afterwards.

A bulk JPQL delete goes straight to the DB and bypasses the persistence context. Test: findById(id) to load the user, call deleteByUserName(name) (delete fires), then findById(id) again: the entity is still in the first-level cache, so the output says present: true although the row is gone. Fix it:

@Modifying(flushAutomatically = true, clearAutomatically = true)
@Query("DELETE FROM UserDetails ud WHERE ud.name = :userFirstName")
void deleteByUserName(@Param("userFirstName") String userName);
  • flushAutomatically = true: pending changes are flushed to the DB before the query runs.
  • clearAutomatically = true: the persistence context is cleared after it, so the next read hits the DB (and finds nothing).

Pagination and sorting in JPQL

Same as in derived queries: add a Pageable (or Sort) parameter.

@Query("SELECT ud FROM UserDetails ud WHERE ud.name = :userFirstName")
List<UserDetails> findUserDetails(@Param("userFirstName") String userName, Pageable pageable);

public List<UserDetails> findByUserName(String name) {
    Pageable page = PageRequest.of(0, 2);
    return userDetailsRepository.findUserDetails(name, page);
}

The SQL gets fetch first 2 rows only (with an offset for later pages).

@NamedQuery

We can name a query so it can be reused.

@Table(name = "user_details")
@Entity
@NamedQuery(name = "UserDetails.findByUserName",
            query = "SELECT u FROM UserDetails u WHERE u.name = :userFirstName")
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long userId;
    @Column(name = "user_name")
    private String name;
    private String phone;
    @OneToOne(cascade = CascadeType.ALL)
    private UserAddress userAddress;
}

// repository: the method name matches "Entity.methodName"
List<UserDetails> findByUserName(@Param("userFirstName") String userName);

Spring Data looks for a named query called <EntityName>.<methodName> before deriving one from the method name.

Good to know
  • JOIN FETCH combined with pagination makes Hibernate paginate in memory (it logs a HHH000104 warning), which is dangerous for big tables. For paged collections prefer @BatchSize or a two-step query (ids first, then fetch).
  • Fetching two List collections together in one query gives MultipleBagFetchException; use Sets or fetch them separately.
  • The count query for Page can be customised with countQuery in @Query.
  • Native SQL is available via @Query(value = "...", nativeQuery = true) when JPQL cannot express it, but it ties you to the database.
Interview corner
What is the N+1 problem and how do you fix it?

One query for the parents plus one per parent for lazily/eagerly loaded children. Fix with JOIN FETCH, @EntityGraph, or @BatchSize.

Why doesn't EAGER fix N+1?

For a multi-parent query Hibernate still loads children with separate selects; EAGER only decides when, not how many queries.

Why do @Modifying queries need @Transactional, and what are flushAutomatically / clearAutomatically?

They change data. flush writes pending changes before the bulk query; clear drops stale entities from the first-level cache afterwards.

Derived query vs JPQL vs native?

Derived: simple conditions by method name. JPQL: complex, entity-based and DB independent. Native: DB-specific SQL when needed.

Page vs Slice vs List?

Page adds a count query and totals; Slice only knows if a next page exists; List just returns the rows.
