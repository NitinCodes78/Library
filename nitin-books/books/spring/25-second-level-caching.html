JPA Second-Level Caching (Part 4)

Share cached entities across sessions: setup with Ehcache, regions, and the four concurrency strategies.

From first level to second level

From the previous chapter we know that for each HTTP request a different EntityManager (session) is created, and each has its own persistence context (first-level cache). Data cached in one session is invisible to the next.

1st POST callEntityManager 1own L1 cache2nd GET callEntityManager 2own L1 cache3rd GET callEntityManager 3own L1 cache

With second-level (L2) caching one cache sits underneath all sessions (per EntityManagerFactory): once a GET loads an entity from the DB, the next GET in any other session finds it in the L2 cache and does not touch the DB.

The happy flow

pom.xml
<dependency>
    <groupId>org.ehcache</groupId>
    <artifactId>ehcache</artifactId>
    <version>3.10.8</version>
    <classifier>jakarta</classifier>       (needed with Spring Boot 3 / Hibernate 6)
</dependency>
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jcache</artifactId>
    <version>6.5.2.Final</version>        (match the Hibernate version Boot uses)
</dependency>
<dependency>
    <groupId>javax.cache</groupId>
    <artifactId>cache-api</artifactId>
    <version>1.1.1</version>
</dependency>

application.properties
spring.jpa.properties.hibernate.cache.use_second_level_cache=true
spring.jpa.properties.hibernate.cache.region.factory_class=org.hibernate.cache.jcache.JCacheRegionFactory
spring.jpa.properties.hibernate.javax.cache.provider=org.ehcache.jsr107.EhcacheCachingProvider
logging.level.org.hibernate.cache.spi=DEBUG
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE, region = "userDetailsCache")
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String email;
    // constructors, getters and setters
}

@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @Autowired UserDetailsService userDetailsService;

    @PostMapping(path = "/user")
    public UserDetails saveUser(@RequestBody UserDetails userDetails) {
        return userDetailsService.saveUser(userDetails);
    }

    @GetMapping("/user/{id}")
    public UserDetails getUser(@PathVariable Long id) {
        return userDetailsService.findByID(id);
    }
}

@Service
public class UserDetailsService {
    @Autowired UserDetailsRepository userDetailsRepository;

    public UserDetails saveUser(UserDetails user) { return userDetailsRepository.save(user); }
    public UserDetails findByID(Long primaryKey) { return userDetailsRepository.findById(primaryKey).get(); }
}

What the logs show:

  1. Insert (POST): data goes directly into the DB; no cache insertion or validation happens.
  2. First GET: JPA checks the cache. It is a cache miss, so it fetches from the DB (a SELECT is printed) and puts it into the cache.
  3. Second GET (even from a different session): a cache hit; Hibernate's DEBUG log prints Cache hit: region = "userDetailsCache" and no SQL is fired.

2. application.properties and regions

  • hibernate.cache.use_second_level_cache=true turns it on.
  • hibernate.cache.region.factory_class=...JCacheRegionFactory tells Hibernate to use hibernate-jcache to manage caching (you may also give the Ehcache factory class directly, bypassing JCache).
  • javax.cache.provider names the JCache provider (EhcacheCachingProvider).

Region

A region is a logical grouping of cached data. For each region (group) you can apply a different caching strategy: eviction policy, TTL, cache size, concurrency strategy and so on. That gives granular control over cached entities, collections or query results.

@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE, region = "userDetailsCache")
public class UserDetails { ... }

@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE, region = "orderDetailsCache")
public class OrderDetails { ... }

The regions are then configured in a file in src/main/resources, ehcache.xml (Ehcache 3 format), pointed to with spring.jpa.properties.hibernate.javax.cache.uri=classpath:ehcache.xml:

<config xmlns="http://www.ehcache.org/v3">
    <cache alias="userDetailsCache">
        <expiry><ttl unit="seconds">60</ttl></expiry>
        <heap unit="entries">100</heap>
    </cache>
    <cache alias="orderDetailsCache">
        <expiry><ttl unit="seconds">200</ttl></expiry>
        <heap unit="entries">1000</heap>
    </cache>
</config>

So userDetailsCache holds at most 100 entries, each living 60 seconds, and orderDetailsCache up to 1000 entries for 200 seconds. (An older Ehcache 2 file used maxElementsInMemory and evictionStrategy for the same ideas.)

3. CacheConcurrencyStrategy

StrategyUse
READ_ONLYStatic data that never changes
READ_WRITERead and update with safe locking (strong consistency)
NONSTRICT_READ_WRITERead-heavy, small risk of stale data is fine
TRANSACTIONALFull transactional cache (needs a JTA-capable setup)

1. READ_ONLY

  • Good for static data that does not require updates.
  • If you try to update the entity, an exception comes: UnsupportedOperationException: Can't update readonly object (thrown from EntityReadOnlyAccess.update), and the API returns 500.
@Entity
@Cache(usage = CacheConcurrencyStrategy.READ_ONLY, region = "userDetailsCache")
public class UserDetails { ... }

// PUT /api/user/1 with {"name":"sj_updated", ...}  ->  500 Internal Server Error

2. READ_WRITE

  • During read, a shared lock is taken: other reads may also take a shared lock, but no write.
  • During update, an exclusive lock is taken: no other read or write is allowed.
  1. Update: transaction begins.
  2. Acquire a lock on the cache entry (prevents stale reads: no read or write allowed) and mark the cache data invalidated.
  3. On commit: update the cache with the latest data, remove the invalidate flag and release the lock. On rollback: the old data stays and the lock is released.
  4. A read that misses the cache goes to the DB and puts the result back into the cache.
Insertstraight to DBGet 1: missread DB, put in cacheUpdatelock cache, update DB and cache on successGet 2: hitno DBdone

3. NONSTRICT_READ_WRITE

  • During read: no lock at all.
  • During update: after the transaction commits, the cache entry is marked invalidated; it is not updated with fresh data, and the next read reloads it.
  • Good for read-heavy applications.
  • If an update and a read happen in parallel, the read may see stale data.

4. TRANSACTIONAL

  • Acquires both a read lock and a write lock.
  • Updates the cache after the transaction commits successfully.
  • Any other read while the cache is locked goes directly to the DB; any other write waits in a queue.
Good to know
  • L2 caching works at the entity-by-id level. Collections need @Cache on the collection field; query results need @Cacheable on the query plus hibernate.cache.use_query_cache=true.
  • Remember: it is per application instance (in-JVM). With several instances, each has its own cache, so you need a distributed provider (Hazelcast, Infinispan, Redis-based) or short TTLs.
  • Updates made by raw SQL or other applications bypass Hibernate, so cached entities can go stale until the TTL expires.
  • Use it for data that is read often and changes rarely (countries, configurations, catalogues).
Interview corner
First-level vs second-level cache?

L1: per session/EntityManager, always on, automatic. L2: shared across sessions of one SessionFactory, optional, provider-backed, configured per entity/region.

Which concurrency strategy for which data?

READ_ONLY for static data, NONSTRICT_READ_WRITE for read-heavy tolerant data, READ_WRITE when staleness is not acceptable, TRANSACTIONAL when you need JTA-level consistency.

What is a cache region?

A named cache area with its own TTL, size and eviction policy.
