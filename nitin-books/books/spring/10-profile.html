@Profile

Different configuration for dev, QA and prod, and beans that exist only in the right environment.

Why profiles?

The same application runs in different environments, and each has its own settings:

Environmentusernamepassword
Dev (local machine)devUsernamedevPassword
QA (stage machine)qaUsernameqaPassword
Prod (live)prodUsernameprodPassword

Username and password are just one example. Many other settings differ per environment: URL and port, connection timeout, request timeout, throttle values, retry values and more.

We put configuration in application.properties. But how do we handle different environments? That is where profiling comes in.

application-dev.properties           application-prod.properties
username=devUsername                 username=prodUsername
password=devPassword                 password=prodPassword

The pattern is application-{profile}.properties. The common file is always loaded; the profile file is loaded on top of it and its values override the common ones.

@Value("${username}") String username;
@Value("${password}") String password;

@PostConstruct
public void init() {
    System.out.println("username: " + username + " password: " + password);
}

Choosing the active profile

At startup we tell Spring Boot which file to pick through spring.profiles.active:

application.properties
spring.profiles.active=prod

or pass it when starting the application itself, which is better because the same build can then run anywhere:

mvn spring-boot:run -Dspring-boot.run.profiles=prod
java -jar app.jar --spring.profiles.active=prod
SPRING_PROFILES_ACTIVE=prod            (environment variable)

The log confirms it: The following 1 profile is active: "prod", and the program prints username: prodUsername password: prodPassword. With no profile set, you see "No active profile set, falling back to 1 default profile: default" and the default values are used.

We can also set multiple profiles at a time, comma separated:

spring.profiles.active=prod,qa

When profiles define the same key, the last one listed wins.

The @Profile annotation

Using @Profile we tell Spring Boot to create a bean only when a particular profile is active.

@Component
@Profile("dev")
public class DevDBConnection { ... }          // exists only when "dev" is active

@Component
@Profile("prod")
public class ProdDBConnection { ... }

@Component
@Profile("!prod")                              // every profile except prod
public class MockPaymentClient { ... }

@Component
@Profile({"qa", "stage"})                      // either of the two
public class TestDataLoader { ... }

The interview scenario

You have 2 applications and 1 common code base. How do you make sure a bean is created for only one application and not the other?

// Common codebase
@Component
@Profile("app1")
public class NoSQLConnection {

    @Value("${username}") String username;
    @Value("${password}") String password;

    @PostConstruct
    public void init() {
        System.out.println("NoSQL username: " + username + " : " + password);
    }
}

Application 1 runs with spring.profiles.active=app1 (and its own application.properties), so the bean is created. Application 2 runs with another profile, so the bean is simply never created there, even though the class is in the same shared jar.

Good to know
  • Beans with no @Profile are created in every profile.
  • The default profile is active when nothing else is set; @Profile("default") beans exist only then.
  • Never commit real production passwords into application-prod.properties. Pass secrets as environment variables or from a secret manager.
  • Read the active profiles in code with Environment.getActiveProfiles().
  • Spring Boot also allows a profile-specific application-dev.yml, or one multi-document YAML with spring.config.activate.on-profile.
Interview corner
How do you handle different configuration per environment?

Profiles: application-{profile}.properties plus spring.profiles.active, passed at launch so the same artifact is promoted unchanged from dev to prod.

What if two active profiles define the same property?

The profile listed later wins.

How can a bean exist only in dev and QA but not in prod?

@Profile({"dev","qa"}) or @Profile("!prod").
