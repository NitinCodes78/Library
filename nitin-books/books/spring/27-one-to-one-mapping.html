JPA: OneToOne Mapping (Part 6)

Unidirectional and bidirectional @OneToOne, @JoinColumn, cascade types, eager vs lazy loading and the serialization trap.

@OneToOne unidirectional

  • One entity (A) references only one instance of another entity (B).
  • The reference exists in one direction only: from parent (A) to child (B).
@Table(name = "user_details")
@Entity
public class UserDetails {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String name;
    private String email;

    @OneToOne
    private UserAddress userAddress;
}

@Table(name = "user_address")
@Entity
public class UserAddress {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String street;
    private String city;
    private String state;
    private String zipCode;
    public UserAddress() { }
}

In USER_DETAILS a column user_address_id appears: it is a foreign key to USER_ADDRESS. By default Hibernate:

  • names the FK as <field_name>_id (so the field userAddress gives user_address_id);
  • points it to the primary key of the other table.

@JoinColumn for more control

@OneToOne
@JoinColumn(name = "user_address_fk", referencedColumnName = "id")
private UserAddress userAddress;

name is the FK column in this table; referencedColumnName is the column it points to in the other table.

What if the child has a composite key?

Use @JoinColumns and map all the columns:

@Embeddable
public class UserAddressCK implements Serializable {
    private String street;
    private String city;
    // equals() and hashCode()
}

@Entity
public class UserAddress {
    @EmbeddedId
    private UserAddressCK userAddressCK;
    private String state;
    private String zipCode;
}

@Entity
public class UserDetails {
    ...
    @OneToOne
    @JoinColumns({
        @JoinColumn(name = "address_street", referencedColumnName = "street"),
        @JoinColumn(name = "address_city",   referencedColumnName = "city")
    })
    private UserAddress userAddress;
}

CascadeType

Values: ALL, PERSIST, MERGE, REMOVE, REFRESH, DETACH.

  • Without a cascade type, any operation on the parent does not affect the child entity.
  • Managing child entities explicitly is error-prone.

CascadeType.PERSIST

Persisting (inserting) the User entity automatically persists its associated UserAddress.

@OneToOne(cascade = CascadeType.PERSIST)
private UserAddress userAddress;

Now one POST with the user and nested address inserts both rows.

CascadeType.MERGE

Updating the User entity automatically updates its associated UserAddress.

Let us first see what happens with only PERSIST:

@Service
public class UserDetailsService {
    @Autowired UserDetailsRepository userDetailsRepository;

    public UserDetails saveUser(UserDetails user) { return userDetailsRepository.save(user); }

    public UserDetails updateUser(Long id, UserDetails user) {
        Optional<UserDetails> existingUser = userDetailsRepository.findById(id);
        if (existingUser.isPresent()) {
            return userDetailsRepository.save(user);
        }
        ...
    }
}

We use the same save method to update. Internally it checks whether the entity is new by looking at the id field; since we pass the id in the request body, it updates instead of inserting.

  1. 1st: INSERT: both tables get rows.
  2. 2nd: UPDATE with changes in both UserDetails and UserAddress: only the UserDetails changes are reflected; the address row is unchanged.

If we want both insert and update to carry over, we need both PERSIST + MERGE:

@OneToOne(cascade = {CascadeType.PERSIST, CascadeType.MERGE})
private UserAddress userAddress;

Then insert works as before, and the update changes both tables.

CascadeType.REMOVE

Deleting the User entity automatically deletes its associated UserAddress. (1st INSERT as before, 2nd DELETE removes the rows from both tables.)

CascadeType.REFRESH

  • Less frequently used. JPA has access to the EntityManager, which maintains the persistence context and thus the first-level cache.
  • Sometimes we want to bypass the first-level cache, so the EntityManager has a refresh method: it reads that entity directly from the DB instead of the cache.
  • With CascadeType.REFRESH we tell JPA to read the parent and its associated child entities from the DB. Whenever refresh() is invoked on UserDetails, it is also invoked on UserAddress.

CascadeType.DETACH

  • Like persist, remove and refresh, the EntityManager also has detach: its purpose is to remove the given entity from the persistence context, so JPA no longer manages its lifecycle.
  • With CascadeType.DETACH, detaching the parent also detaches the associated child.

CascadeType.ALL

All the capabilities together: PERSIST, MERGE, REMOVE, REFRESH and DETACH.

@OneToOne(cascade = CascadeType.ALL)
private UserAddress userAddress;

What about GET? Eager vs lazy loading

Do child entities always load with the parent?

Eager loading

  • The associated entity is loaded immediately along with the parent.
  • Default for @OneToOne and @ManyToOne. JPA assumes that since there is only one child, it will probably be needed when the parent is accessed.

Lazy loading

  • The associated entity is not loaded until accessed, for example when we call userDetails.getUserAddress().
  • Default for @OneToMany and @ManyToMany. There can be many child rows, so returning them all could hurt performance.

We can control the default:

@OneToOne(cascade = CascadeType.ALL, fetch = FetchType.LAZY)
private UserAddress userAddress;

The serialization trap

Testing this code: the insert succeeds, but the GET fails with InvalidDefinitionException: No serializer found for class org.hibernate.proxy.pojo.bytebuddy.ByteBuddyInterceptor.

  • With lazy loading, userAddress is only a Hibernate proxy when the response JSON is created. Jackson does not know how to serialize it and fails while constructing the response.
  • Why did INSERT not fail? Because on insert the data goes to the DB and also sits in the persistence context (first-level cache), so the real UserAddress object is already in memory and the response needs no DB call.

Two ways to fix the GET:

OptionNotes
@JsonIgnore on the fieldRemoves UserAddress from the response.
DTO (Data Transfer Object)Much cleaner and recommended: map the entity to a response class containing only what you want to expose.

Bidirectional @OneToOne

Here both sides know each other: UserDetails has userAddress and UserAddress has userDetails. Only one side owns the foreign key; the other side uses mappedBy.

@Entity
public class UserDetails {
    ...
    @OneToOne(cascade = CascadeType.ALL)
    @JoinColumn(name = "user_address_id")       // owning side: holds the FK column
    private UserAddress userAddress;
}

@Entity
public class UserAddress {
    ...
    @OneToOne(mappedBy = "userAddress")         // inverse side: no column, points to the field name in UserDetails
    private UserDetails userDetails;
}
  • Set both sides in code (user.setUserAddress(a); a.setUserDetails(user);), otherwise the inverse side stays null.
  • When serializing to JSON, the two references point at each other and cause infinite recursion: break the loop with @JsonIgnore / @JsonManagedReference + @JsonBackReference, or better, return a DTO.
Good to know
  • Cascade is about operations flowing parent to child; it is separate from fetch type.
  • orphanRemoval = true additionally deletes a child that is detached from its parent (set the field to null).
  • Never expose entities from the controller if you can avoid it: DTOs avoid lazy-proxy and recursion problems and keep your API independent of the schema.
Interview corner
What is the owning side of a relationship?

The side with the foreign key column (@JoinColumn). The other side uses mappedBy and does not change the FK.

Default fetch types?

EAGER for @OneToOne and @ManyToOne; LAZY for @OneToMany and @ManyToMany.

Why did GET fail with "No serializer found ... ByteBuddyInterceptor"?

The lazy association was an uninitialised proxy at serialization time. Use a DTO or ignore the field.

Cascade PERSIST vs MERGE?

PERSIST propagates insert of a new parent to the child; MERGE propagates an update of an existing (detached) parent. For both, use both (or ALL).
