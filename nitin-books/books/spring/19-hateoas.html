HATEOAS

Hypermedia As The Engine Of Application State: let the response tell the client what it can do next.

What is it?

HATEOAS = Hypermedia As The Engine Of Application State. It tells the client what next action it can perform on a particular item.

Example: user onboarding

POST /addusercreatesUnverified userPOST /sms-verify-startSMS verify startedPOST /sms-verify-finishVerified user

An unverified user can be fetched (GET), removed (DELETE), or verified through SMS or through email (email-verify-start then email-verify-finish). Which call is valid depends on the user's current state.

The response of POST /adduser:

Without HATEOAS

{
  "userID": "123456",
  "name": "SJ",
  "verifyStatus": "UNVERIFIED"
}

With a HATEOAS link

{
  "userID": "123456",
  "name": "SJ",
  "verifyStatus": "UNVERIFIED",
  "links": [{
    "rel": "self",
    "href": "http://localhost:8080/api/getUser/123456",
    "type": "GET"
  }]
}

When and why to use it

The two major purposes are:

  • Loose coupling
  • API discovery

The server provides the next set of actions (APIs) inside the response, so the client needs less business logic about which API to call, when and how.

Do not add every possible action

Adding all the next actions bloats the response and has several costs: more complexity on the server, latency impact and larger payload size. Never add all possible next actions "just like that". Analyse what actually helps to achieve loose coupling.

"links": [
  { "rel": "self",          "href": ".../api/getUser/123456",         "type": "GET" },
  { "rel": "remove",        "href": ".../api/removeUser/123456",      "type": "DELETE" },
  { "rel": "update",        "href": ".../api/updateUser/123456",      "type": "PATCH" },
  { "rel": "verify-start",  "href": ".../api/sms-verify-start/123456","type": "POST" },
  { "rel": "verify-finish", "href": ".../api/sms-verify-finish/123456","type": "POST" }
]       // too much: this is the bloated version to avoid

Where the real coupling is

In the onboarding flow, the tight coupling lies in the verify process. The client needs extra information before it can decide which verify API to invoke:

// client has to carry this business logic
if (verifyStatus == "UNVERIFIED") {
    if (verifyType == "SMS") {
        if (verifyState == "NOT_YET_STARTED")  call POST /sms-verify-start
        else if (verifyState == "STARTED")     call POST /sms-verify-finish
    } else if (verifyType == "EMAIL") {
        if (verifyState == "NOT_YET_STARTED")  call POST /email-verify-start
        else                                   call POST /email-verify-finish
    }
}

This dependency is removed by a HATEOAS link. The server decides the next step and sends just that:

{
  "userID": "123456",
  "name": "SJ",
  "verifyStatus": "UNVERIFIED",
  "links": [{
    "rel": "verify",
    "href": "http://localhost:8080/api/sms-verify-finish/123456",
    "type": "POST"
  }]
}

Now the client code is tiny and loosely coupled:

if (verifyStatus == "UNVERIFIED") {
    // invoke the verify URI given in the HATEOAS link
}

Implementation

<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-hateoas</artifactId>
</dependency>

(No version is needed: Spring Boot's parent manages it.) The notes build a small base class that holds a list of links, and make the response extend it:

public class HateoasLinks {
    private List<Link> links = new ArrayList<>();

    public void addLink(Link link) { links.add(link); }
    public List<Link> getLinks() { return links; }
}

public class UserResponse extends HateoasLinks {
    private String userID;
    private String name;
    private String verifyStatus;
    // getters and setters
}

@RestController
@RequestMapping("/api")
public class UserController {

    @PostMapping(path = "/adduser")
    public ResponseEntity<UserResponse> addUser(@RequestBody UserRequest request) {
        UserResponse response = userService.addUser(request);

        Link verifyLink = linkTo(UserController.class)
                .slash("sms-verify-finish")
                .slash(response.getUserID())
                .withRel("verify")
                .withType("POST");
        response.addLink(verifyLink);

        return ResponseEntity.status(HttpStatus.CREATED).body(response);
    }
}

Another way to create a link, by hand:

Link verifyLink = Link.of("/api/sms-verify-finish/" + response.getUserID())
        .withRel("verify")
        .withType("POST");
Good to know
  • Spring HATEOAS also has ready-made models: EntityModel<T>, CollectionModel<T> and RepresentationModel; you can extend RepresentationModel instead of writing your own base class, and linkTo(methodOn(UserController.class).getUser(id)) builds links from real controller methods so they never go stale.
  • The rel value says what the link means (self, verify, next, cancel).
  • HATEOAS is the top level (level 3) of the Richardson maturity model of REST.
Interview corner
What is HATEOAS and when would you use it?

The response carries links to the next valid actions, so clients follow links instead of hard-coding URLs and state rules. Use it where the allowed next steps depend on server-side state (workflows like onboarding, order lifecycle).

What are its downsides?

Bigger payloads, more server logic, extra latency, and most clients ignore the links anyway, so add only the links that remove real client logic.
