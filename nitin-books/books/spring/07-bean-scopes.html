Bean Scopes

Singleton, Prototype, Request and Session: how many objects Spring creates and when, plus the classic "request bean inside a singleton" trap.

A scope decides how many instances of a bean Spring creates and how long each one lives. The four you must know:

Singleton

One instance per IoC container. Default.

Prototype

A new instance every time the bean is requested.

Request

A new instance for every HTTP request.

Session

A new instance for every HTTP session.

Singleton

  • The default scope.
  • Only one instance is created per IoC container.
  • Eagerly initialised: the object is created at application startup.
@Component
public class User {
    public User() { System.out.println("User initialization"); }
    public void init() { System.out.println("User object hashCode: " + this.hashCode()); }
}

@RestController
@RequestMapping(value = "/api/")
public class TestController1 {
    @Autowired User user;
    ...
}
@RestController
public class TestController2 {
    @Autowired User user;
    ...
}

At startup the log shows "User initialization" once, then the controllers are created. Both controllers print the same hashCode for User: they share one object.

Prototype

  • A new object is created each time the bean is needed.
  • Lazily initialised: created only when required, not at startup.
@Component
@Scope(value = "prototype")
public class Student {
    public Student() { System.out.println("Student instance initialization"); }
}

@RestController
public class TestController1 {
    @Autowired User user;         // singleton
    @Autowired Student student;   // prototype
}

Injected into two different controllers, Student prints different hash codes, while User stays the same. Each injection point gets its own object.

Request

  • A new object is created for each HTTP request.
  • Lazily initialised, and available only inside a web application.
@Component
@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class User {
    public User() { System.out.println("User initialization"); }
}

Call /api/fetchUser twice: the log prints "User initialization" twice, with two different hash codes, one per request.

Why the proxyMode?

Suppose the request-scoped User is injected into a singleton controller without proxyMode. Spring creates a request-scoped bean only when an active HTTP request exists. A singleton is created eagerly at startup, when no request is active on the thread, so the application fails to start ("Scope 'request' is not active for the current thread").

With proxyMode = ScopedProxyMode.TARGET_CLASS Spring injects a proxy into the singleton instead. On every call the proxy looks up the real bean of the current request and forwards the call to it. This is the general fix for injecting a shorter-lived bean (request, session, prototype) into a longer-lived one.

Session

  • A new object is created for each HTTP session.
  • Lazily initialised: the session (and the bean) is created when the user first accesses an endpoint.
  • It stays active until the session expires or is invalidated.
@Component
@Scope(value = "session", proxyMode = ScopedProxyMode.TARGET_CLASS)
public class User { ... }

@GetMapping(path = "/fetchUser")
public ResponseEntity<String> fetchUser() { ... }

@GetMapping(path = "/logout")
public ResponseEntity<String> logout(HttpServletRequest request) {
    HttpSession session = request.getSession();
    session.invalidate();               // ends the session: the next call gets a new bean
    return ResponseEntity.status(HttpStatus.OK).body("");
}

Calling /fetchUser repeatedly from the same browser session gives the same User hash code. After /logout invalidates the session, the next call creates a new one.

Good to know
  • Also exist: application (one per ServletContext) and websocket scope.
  • A singleton is one object shared by all threads, so it must be stateless (or thread-safe). Keep per-user state in request or session scope, or outside the bean.
  • Spring does not call @PreDestroy on prototype beans: after creating one it stops tracking it.
  • Injecting a prototype into a singleton gives you the same prototype object forever (it is injected once). Use ObjectProvider<Student>, @Lookup or a scoped proxy to get a fresh one each time.
Interview corner
Is a singleton bean thread-safe?

No. There is one shared instance, so Spring gives no thread-safety; keep the bean stateless or synchronise carefully.

Singleton bean in Spring vs the Singleton design pattern?

Spring's singleton is one instance per container (per ApplicationContext), the pattern is one instance per JVM/classloader.

What if a prototype bean is injected into a singleton?

It is injected only once, so it behaves like a singleton. Use ObjectProvider, @Lookup or proxyMode.

Why did my request-scoped bean fail at startup?

No HTTP request was active when the singleton was created. Add a scoped proxy.
