JPA: Native Query, Criteria API and Specification API (Parts 9 and 10)

When JPQL is not enough: plain SQL, then dynamic type-safe queries with the Criteria API, and finally reusable Specifications.

Native query

  • Plain SQL queries that interact directly with the database. If the DB changes in future, the code has to change too.
  • No caching, lazy loading or entity life-cycle management happens for the results.

When to use it over JPQL:

  • More complex queries, including DB-specific features such as JSONB or LATERAL JOIN.
  • When you need non-entity results, or to join tables that have no entity relationship.
  • Query efficiency, such as bulk operations.
public interface UserDetailsRepository extends JpaRepository<UserDetails, Long> {
    @Query(value = "SELECT * FROM user_details WHERE user_name = :userFirstName", nativeQuery = true)
    List<UserDetails> getUserDetailsByNameNativeQuery(@Param("userFirstName") String userName);
}

When all the fields (*) are returned, JPA does the mapping between DB column names and entity fields itself. But when the native query returns partial fields, JPA does not map it to the entity, and you get an error like Column "userid" not found from H2. We must tell JPA how to map.

Way 1: @SqlResultSetMapping with @NamedNativeQuery

Declare a DTO, a result-set mapping and a named native query, then refer to the name in the repository:

public class UserDTO {
    private String userName;
    private String phone;
    public UserDTO(String userName, String phone) { this.userName = userName; this.phone = phone; }
}

@Entity
@Table(name = "user_details")
@SqlResultSetMapping(
    name = "UserDTOMapping",
    classes = @ConstructorResult(targetClass = UserDTO.class,
        columns = { @ColumnResult(name = "user_name", type = String.class),
                    @ColumnResult(name = "phone", type = String.class) }))
@NamedNativeQuery(
    name = "UserDetails.getUserDetailsByNameNativeQuery",
    query = "SELECT user_name, phone FROM user_details WHERE user_name = :userFirstName",
    resultSetMapping = "UserDTOMapping")
public class UserDetails { ... }

public interface UserDetailsRepository extends JpaRepository<UserDetails, Long> {
    @Query(name = "UserDetails.getUserDetailsByNameNativeQuery", nativeQuery = true)
    List<UserDTO> getUserDetailsByNameNativeQuery(@Param("userFirstName") String userName);
}

Way 2: manual mapping

Return List<Object[]> and map yourself:

@Query(value = "SELECT user_name, phone FROM user_details WHERE user_name = :userFirstName", nativeQuery = true)
List<Object[]> getUserDetailsByNameNativeQuery(@Param("userFirstName") String userName);

public List<UserDTO> getUserDetailsByNameNativeQuery(String name) {
    List<Object[]> results = userDetailsRepository.getUserDetailsByNameNativeQuery(name);
    return results.stream()
            .map(obj -> new UserDTO((String) obj[0], (String) obj[1]))
            .collect(Collectors.toList());
}

(Spring Data interface projections, where the interface has getters named after the selected columns, are a simpler third option.)

Dynamic native query

Build the SQL string at runtime and run it through the EntityManager:

String sql = "SELECT ud.user_name, ud.phone AS phone FROM user_details ud "
           + "JOIN user_address ua ON ud.user_address_id = ua.id "
           + "WHERE ud.user_name = ?1";
Query query = entityManager.createNativeQuery(sql);
query.setParameter(1, userName);
List<Object[]> rows = query.getResultList();

Always bind values with parameters; never concatenate user input into the SQL (SQL injection).

Pagination and sorting in native SQL

  • 1st way: write it in the SQL itself: ... ORDER BY ud.phone DESC OFFSET ? ROWS FETCH FIRST ? ROWS ONLY (syntax depends on the database).
  • 2nd way: pass a Pageable; for native queries Spring Data appends the paging and also needs a countQuery if you return a Page. Sorting via Pageable in native queries is limited, so putting ORDER BY in the SQL is safer.

Criteria API

Native SQL supports dynamic query building but is database dependent and does not use JPA's abstraction. That is why the Criteria API exists: it lets you build dynamic, type-safe queries in Java without writing raw SQL.

The hierarchy

CriteriaBuilder: used to create everything
CriteriaQuery: defines the query structure
Root (from): the entity we fetch from; join for related entities
select(root): full entity; multiselect(...): specific columns
Predicate (where): filters, combined by and(), or(), not()
Order (orderBy), groupBy(), having()
TypedQuery: executes the query
getResultList(): many results; getSingleResult(): one result
setFirstResult(offset) and setMaxResults(limit): pagination

A first example

@GetMapping("/user/{phone}")
public List<UserDetails> getUser(@PathVariable Long phone) {
    return userDetailsService.getUserDetailsByPhoneCriteriaAPI(phone);
}

@Service
public class UserDetailsService {
    @PersistenceContext EntityManager entityManager;

    public List<UserDetails> getUserDetailsByPhoneCriteriaAPI(Long phoneNo) {
        CriteriaBuilder cb = entityManager.getCriteriaBuilder();
        CriteriaQuery<UserDetails> crQuery = cb.createQuery(UserDetails.class);
        Root<UserDetails> user = crQuery.from(UserDetails.class);       // from clause
        crQuery.select(user);
        Predicate predicate = cb.equal(user.get("phone"), phoneNo);     // where phone = ?
        crQuery.where(predicate);
        TypedQuery<UserDetails> query = entityManager.createQuery(crQuery);
        return query.getResultList();
    }
}

@Table(name = "user_details")
@Entity
public class UserDetails {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long userId;
    @Column(name = "user_name")
    private String name;
    private Long phone;
}

Calling /user/120 returns the users with phone 120, and Hibernate logs ... from user_details ud1_0 where ud1_0.phone=?.

Select multiple fields

public List<UserDTO> getUserDetailsByPhoneCriteriaAPI(Long phoneNo) {
    CriteriaBuilder cb = entityManager.getCriteriaBuilder();
    CriteriaQuery<Object[]> crQuery = cb.createQuery(Object[].class);
    Root<UserDetails> user = crQuery.from(UserDetails.class);
    crQuery.multiselect(user.get("name"), user.get("phone"));
    Predicate predicate = cb.equal(user.get("phone"), phoneNo);
    crQuery.where(predicate);

    TypedQuery<Object[]> query = entityManager.createQuery(crQuery);
    List<Object[]> results = query.getResultList();
    List<UserDTO> output = new ArrayList<>();
    for (Object[] row : results) {
        String name = (String) row[0];
        Long phone = (Long) row[1];
        output.add(new UserDTO(name, phone));
    }
    return output;
}

Pagination and sorting

CriteriaQuery<UserDetails> crQuery = cb.createQuery(UserDetails.class);
Root<UserDetails> user = crQuery.from(UserDetails.class);
crQuery.select(user);
Predicate predicate = cb.equal(user.get("phone"), phoneNo);
crQuery.where(predicate);
crQuery.orderBy(cb.desc(user.get("name")));              // sorting

TypedQuery<UserDetails> query = entityManager.createQuery(crQuery);
query.setFirstResult(0);                                  // offset
query.setMaxResults(5);                                   // limit (page size)
List<UserDetails> results = query.getResultList();

With rows A to H having the same phone, ordered by name descending and limited to 5, the response holds H, G, F, E, D.

Specification API

Problem 1: code duplicity

In the Criteria API the same filter (predicate) may be needed in multiple methods and classes, so duplication is always a challenge and it is error prone. The Specification API solves it: you package a predicate in a reusable object.

The Specification interface:

MethodUse
toPredicate()The abstract method: we provide the WHERE-clause implementation
spec1.and(spec2)WHERE cond1 AND cond2
spec1.or(spec2)WHERE cond1 OR cond2
Specification.not(spec1)WHERE NOT cond1
public class UserSpecification {

    public static Specification<UserDetails> equalsPhone(Long phoneNo) {
        return (root, query, cb) -> cb.equal(root.get("phone"), phoneNo);
    }

    public static Specification<UserDetails> likeName(String name) {
        return (root, query, cb) -> cb.like(root.get("name"), name + "%");
    }
}

Using it in the service still needs all the criteria plumbing:

CriteriaBuilder cb = entityManager.getCriteriaBuilder();
CriteriaQuery<UserDetails> crQuery = cb.createQuery(UserDetails.class);
Root<UserDetails> userRoot = crQuery.from(UserDetails.class);
crQuery.select(userRoot);
Specification<UserDetails> specification = UserSpecification.equalsPhone(phoneNo);
Predicate predicate = specification.toPredicate(userRoot, crQuery, cb);
crQuery.where(predicate);
TypedQuery<UserDetails> query = entityManager.createQuery(crQuery);
List<UserDetails> results = query.getResultList();

Problem 2: code boilerplate

Even though the filtering logic is out, plenty of boilerplate remains: we manage the CriteriaBuilder, CriteriaQuery, Root and Predicate objects and run the query ourselves. All we need to tell JPA is:

  • from which table to fetch, including joins;
  • which columns;
  • the filter in the where clause.

JPA should take care of everything else: object creation, query building and execution.

JpaSpecificationExecutor

Extend this interface in the repository:

public interface UserDetailsRepository
        extends JpaRepository<UserDetails, Long>, JpaSpecificationExecutor<UserDetails> { }
Method
Optional<T> findOne(Specification<T> spec)
List<T> findAll(Specification<T> spec)
Page<T> findAll(Specification<T> spec, Pageable pageable)
List<T> findAll(Specification<T> spec, Sort sort)
long count(Specification<T> spec) and boolean exists(Specification<T> spec)

Internally (SimpleJpaRepository) the framework builds the query for you: it gets the CriteriaBuilder, creates the CriteriaQuery and Root (applySpecificationToCriteria), calls spec.toPredicate(root, query, builder), and if the predicate is not null applies query.where(predicate), then runs it and applies the paging.

public List<UserDetails> getUserDetailsByPhoneSpec(Long phoneNo) {
    Specification<UserDetails> result = Specification
            .where(UserSpecification.equalsPhone(phoneNo))
            .and(UserSpecification.likeName("AA"));
    return userDetailsRepository.findAll(result);
}

// a join specification
public static Specification<UserDetails> joinAddress() {
    return (root, query, cb) -> {
        Join<UserDetails, UserAddress> address = root.join("userAddress", JoinType.INNER);
        return cb.isNotNull(address.get("id"));    // any predicate on the join, or null to just join
    };
}

Compared to the raw Criteria API version (create builder, query, root, join, two predicates, cb.and, typed query, getResultList), the Specification API is much cleaner and the pieces are reusable: each specification can be combined with and / or / not in any method.

Good to know
  • Choosing: derived query for 1 or 2 simple conditions; @Query JPQL for fixed complex queries; Specification (or Criteria) when filters are optional and dynamic (a search screen where any combination of fields may be given); native only when SQL features demand it.
  • Build dynamic filters by chaining only the specs whose inputs are present: spec = spec.and(nameLike(...)) only if the name was supplied.
  • Typo-safe field names: use the JPA static metamodel (UserDetails_.phone, generated by hibernate-jpamodelgen) instead of the strings "phone".
  • A different, popular option for dynamic queries is Querydsl.
Interview corner
When would you use a native query?

DB-specific features, non-entity results or joins without relations, performance-tuned bulk operations. Cost: portability, no entity management.

Why Criteria API over string-concatenated JPQL?

It builds dynamic queries safely, with compile-time checked structure and no injection from string building.

What problems do Specifications solve over Criteria?

Duplicate predicates (they become reusable, composable objects) and boilerplate (the repository builds the CriteriaBuilder/Root/query for you).

How do you make a repository support Specifications?

Extend JpaSpecificationExecutor<T> alongside JpaRepository.
