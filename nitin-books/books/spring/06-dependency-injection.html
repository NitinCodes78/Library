Dependency Injection

Field, setter and constructor injection, why constructor injection wins, and how to fix circular and ambiguous dependencies.

What is Dependency Injection?

  • With DI we make our class independent of its dependencies.
  • It removes the dependency on a concrete implementation: the dependency is injected from an external source (the Spring container).

The problem first

public class User {
    Order order = new Order();           // User creates its own Order

    public User() { System.out.println("initializing user"); }
}
public class Order {
    public Order() { System.out.println("initializing Order"); }
}

Issues with this structure:

  1. Tight coupling. If the creation logic of Order changes (say Order later becomes an interface with many concrete classes such as OnlineOrder), the User class has to change too.
  2. It breaks the Dependency Inversion rule of SOLID: do not depend on a concrete implementation, depend on an abstraction.
public interface Order { }
public class OnlineOrder implements Order { }
public class OfflineOrder implements Order { }

public class User {
    Order order;                          // depends on the abstraction only

    public User(Order orderObj) {         // handed in from outside
        this.order = orderObj;
    }
}

In Spring Boot we achieve this through Dependency Injection. @Autowired first looks for a bean of the required type; if a bean is found, Spring injects it.

1. Field injection

  • The dependency is set directly into the fields. Spring uses reflection: it iterates over the fields and resolves the dependency.
@Component
public class User {
    @Autowired
    Order order;
}

Advantage: very simple and easy to write.

Disadvantages:

  • Cannot be used with immutable (final) fields.
  • Chances of NullPointerException: new User().process() outside Spring leaves order as null.
  • Unit testing is difficult: there is no constructor or setter to pass a mock into, so you need reflection. That is what Mockito's @InjectMocks does internally.
class UserTest {
    @Mock
    Order orderMockObj;
    @InjectMocks
    User user;

    @BeforeEach
    void setup() {
        MockitoAnnotations.openMocks(this);   // (older code: initMocks)
    }
}

2. Setter injection

@Component
public class User {
    Order order;

    @Autowired
    public void setOrder(Order order) {
        this.order = order;
    }
}

Advantages: the dependency can be changed any time after creation; testing is easy because a mock can be passed straight in.

Disadvantages:

  • The field cannot be final, so the class cannot be immutable.
  • Harder to read and maintain: by convention an object should be fully initialised at creation, so this hurts readability.

3. Constructor injection (recommended)

The dependency is resolved at the time the object is initialised.

@Component
public class User {
    private final Order order;

    public User(Order order) {            // no @Autowired needed (one constructor)
        this.order = order;
    }
}
  • When there is only one constructor, @Autowired on it is optional (since Spring 4.3).
  • When there is more than one constructor, @Autowired on the one Spring should use is mandatory. Otherwise Spring looks for a default constructor and fails with "No default constructor found".
Why constructor injection is recommended
  1. All mandatory dependencies exist at initialisation, so the object is 100% fully initialised. No NPE at runtime, no unnecessary null checks.
  2. Immutable objects are possible (private final Order order).
  3. Fail fast. A missing dependency stops the application at startup (and with a plain new User() it fails at compile time), instead of surfacing at run time.
  4. Unit testing is easy: new User(Mockito.mock(Order.class)).
class UserTest {
    Order orderMockObj;
    User user;

    @BeforeEach
    void setup() {
        orderMockObj = Mockito.mock(Order.class);
        user = new User(orderMockObj);       // plain Java, no Spring needed
    }
}

Common issues with DI

1. Circular dependency

Order needs Invoice and Invoice needs Order. Spring cannot build either first, and the app fails with APPLICATION FAILED TO START: the dependencies of some of the beans in the application context form a cycle.

@Component
public class Order {
    @Autowired Invoice invoice;
}
@Component
public class Invoice {
    @Autowired Order order;
}
OrderneedsInvoiceneedsOrder

Solutions:

  1. Refactor first. Move the common code both depend on into a separate class; this breaks the cycle and is the real fix.
  2. @Lazy on the injection point. Spring injects a proxy instead of creating the real bean at startup, and builds the real one on first use. 
    @Component
public class Order {
    @Autowired
    @Lazy
    Invoice invoice;
}
  3. Break the cycle with a setter and @PostConstruct. Construct without the dependency, then wire it afterwards: 
    @Component
public class Invoice {
    public Order order;
    public void setOrder(Order order) { this.order = order; }
}
@Component
public class Order {
    @Autowired Invoice invoice;

    @PostConstruct
    public void init() {
        invoice.setOrder(this);          // wire the back-reference after construction
    }
}

Since Spring Boot 2.6, circular references are prohibited by default (the app fails at startup), so you cannot lean on setter or field injection to hide a cycle.

2. Unsatisfied / ambiguous dependency

When Order is an interface with several implementations, a bare @Autowired Order order fails: Spring does not know which implementation to inject.

public interface Order { }

@Component public class OnlineOrder implements Order { }
@Component public class OfflineOrder implements Order { }

Solutions:

  1. @Primary: mark one implementation as the default choice. 
    @Component
@Primary
public class OnlineOrder implements Order { }
  2. @Qualifier: name the one you want at the injection point (the default bean name is the class name with a lowercase first letter). 
    @Component
public class User {
    @Autowired
    @Qualifier("offlineOrder")
    Order order;
}

If both are present, @Qualifier wins over @Primary.

Interview corner
Why is constructor injection preferred over field injection?

Immutability, guaranteed non-null mandatory dependencies, fail-fast, and trivial unit testing without reflection or a Spring context.

How do you handle a circular dependency?

Redesign (extract the shared logic into a third bean). As a workaround use @Lazy on one injection point, or a setter plus @PostConstruct.

What is the difference between @Primary and @Qualifier?

@Primary marks the default bean when several of the same type exist; @Qualifier picks a specific bean by name at the injection point and takes precedence.

What exception do you get with two beans of the same type and no qualifier?

NoUniqueBeanDefinitionException. With none at all you get NoSuchBeanDefinitionException ("unsatisfied dependency").
