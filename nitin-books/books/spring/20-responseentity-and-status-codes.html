ResponseEntity and HTTP Status Codes

Control status, headers and body of the response, and know exactly which status code to return when.

ResponseEntity

ResponseEntity represents the entire HTTP response: status code, headers and body. It is built with the Builder pattern: status(...) and headers(...) return a builder, and the body must be last because the body(...) call returns the final ResponseEntity.

public static BodyBuilder status(HttpStatusCode status) { ... }

BodyBuilder headers(HttpHeaders headers);
<T> ResponseEntity<T> body(T body);
<T> ResponseEntity<T> build();          // when there is no body
@GetMapping(path = "/get-user")
public ResponseEntity<User> getUser() {
    User user = new User("XYZ", 28);
    HttpHeaders headers = new HttpHeaders();
    headers.add("My-Header1", "SomeValue1");
    headers.add("My-Header2", "SomeValue2");
    return ResponseEntity.status(HttpStatus.OK).headers(headers).body(user);
}

// no body wanted: use build()
@GetMapping(path = "/get-user")
public ResponseEntity<Void> getUser() {
    HttpHeaders headers = new HttpHeaders();
    headers.add("My-Header1", "SomeValue1");
    return ResponseEntity.status(HttpStatus.OK).headers(headers).build();
}

Shortcuts: ResponseEntity.ok(body), ResponseEntity.created(uri).body(x), ResponseEntity.noContent().build(), ResponseEntity.notFound().build().

Returning a POJO directly: default 200 OK

@RestController
@RequestMapping(value = "/api/")
public class UserController {

    @GetMapping(path = "/get-user")
    public User getUser() {
        return new User("XYZ", 28);        // serialised to JSON, status 200 OK by default
    }
}

@ResponseBody and @RestController

When we return a plain String or POJO from a controller, @ResponseBody is required. It tells Spring to treat the value as the response body and not as a view name. In the example above we did not write it because @RestController automatically puts @ResponseBody on every method (@RestController is meta-annotated with @Controller and @ResponseBody).

With a plain @Controller this fails:

@Controller
public class UserController {
    @GetMapping(path = "/get-user")
    public String getUser() {
        return "XYZ";       // treated as a VIEW name: Spring looks for a view called XYZ, finds none, error
    }
}

HTTP status codes

1xxinformational2xxsuccess3xxredirection4xxclient error5xxserver error

2xx: Success

The request from the client was received and processed successfully.

CodeReasonMostly used inDetails
200OKGET, POST (idempotent calls)Request successful and we return a response body.
201CreatedPOSTRequest successful and a new resource was created (often with a Location header).
202AcceptedPOSTRequest accepted but processing is not complete yet. Batch work like export or import.
204No ContentDELETERequest successful and we return no data in the body.
206 / 207Partial / Multi-StatusPOSTPartial success, e.g. bulk addition of 100 users where 95 passed and 5 failed. (Strictly, 206 Partial Content is for ranged downloads; 207 Multi-Status is the code for a mixed bulk result.)

3xx: Redirection

The client must take an additional action to complete the request.

CodeReasonUsed when
301Moved PermanentlyMigrating from a legacy API to a new one: all requests should go to the new URI. (Older code; the newer one is 308.)
308Permanent RedirectSame as 301, but it does not allow the HTTP method to change on redirect: a POST to the old API must be a POST to the new one (301 relaxes this).
304Not ModifiedGET with caching: (1) the client GETs and the server returns it with a Last-Modified time in a header; (2) the client caches the response; (3) the next GET passes that time in the If-Modified-Since header; (4) the server compares with the resource's last update: if unchanged it returns 304 with no body; (5) if modified it processes the request as usual and returns the new values.

Avoid 304 with PATCH: if you try to update a user's name and it is already that name, return 204 or 200, not 304.

4xx: Client errors (validation)

The client needs to send a correct request.

CodeReasonDetails
400Bad RequestThe client is not passing the details needed to process the request (missing or malformed fields).
401UnauthorizedAn API that requires authentication (Bearer token, Basic auth ...) is called without valid authentication details.
403ForbiddenThe client is authenticated but not allowed. Say only ADMIN can perform an operation; if anyone else calls it, throw 403.
404Not FoundThe requested resource does not exist, e.g. GET user with id 123 but no such id in the DB.
405Method Not AllowedHitting a GET API with the POST method. In Spring Boot the DispatcherServlet raises this, so the request never reaches your controller.
422Unprocessable EntityBusiness validation failed: e.g. users from France are not allowed to open an account because that country is not supported yet.
429Too Many RequestsRate limiting: if the rule is "max 10 calls per minute per user", the 11th call of user 12345 within that minute gets 429.

5xx: Server errors

The request failed at the server even though the client sent a valid one: something is wrong on the server side.

CodeReasonDetails
500Internal Server ErrorGeneric error when no more specific code fits.
501Not ImplementedThe API lacks the ability to fulfil the request, or it is still in development and will exist in the future.
502Bad GatewayA server acting as a proxy got an invalid response from upstream. Example: your app is behind a reverse proxy (Nginx) and Nginx cannot reach it (wrong port, misconfiguration).
503Service UnavailableThe server is temporarily unable to handle requests (overloaded, down for maintenance, circuit open).
504Gateway TimeoutThe proxy or gateway did not get a response from upstream in time.

1xx: Informational

Interim responses that communicate progress before the final response.

100 Continue (POST): the client checks with the server before sending a big request.

  1. The client first sends only headers: Content-Length: 1048576, Content-Type: multipart/form-data and Expect: 100-continue.
  2. The server sees Expect: 100-continue, meaning the client is just checking. It validates everything it can (authentication, authorisation, content type, length).
  3. If the server is okay it returns 100 Continue.
  4. The client then sends the actual body and the server processes the request.
Picking the right code (quick rules)
  • 401 = "who are you?" (not authenticated). 403 = "I know you, but no" (not authorised).
  • 400 = malformed or missing input. 422 = well-formed but breaks a business rule.
  • Created something? 201 plus a Location header. Deleted with nothing to return? 204.
  • PUT/DELETE should be idempotent: repeating the call gives the same result.
Interview corner
401 vs 403?

401: missing or invalid credentials. 403: valid credentials, insufficient permission.

PUT vs POST vs PATCH?

POST creates (not idempotent). PUT replaces a whole resource (idempotent). PATCH changes part of it.

Why use ResponseEntity instead of returning the object?

You control status and headers per case (201, 204, 404 ...); returning the object always gives 200.

Your app behind Nginx returns 502. What does it mean?

The proxy could not get a valid response from your app (down, wrong port, crashed). 504 would mean it timed out.
