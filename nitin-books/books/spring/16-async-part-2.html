@Async: Part 2

The rules that make @Async work, what happens to transactions, return types (Future, CompletableFuture) and exception handling.

Conditions for @Async to work

  1. Call it from a different class. If an @Async method is called from another method in the same class, the proxy is skipped, because internal method calls are not intercepted. It then runs on the caller's thread.
  2. The method must be public. AOP interception works only on public methods.
// WRONG: both methods in the same class, the proxy is bypassed
@Component
public class UserService {
    public void getUser() {
        System.out.println("inside getUserMethod: " + Thread.currentThread().getName());
        asyncMethodTest();                       // plain call, no new thread
    }

    @Async
    public void asyncMethodTest() {
        System.out.println("inside asyncMethodTest: " + Thread.currentThread().getName());
    }
}
// inside getUserMethod: http-nio-8080-exec-1
// inside asyncMethodTest: http-nio-8080-exec-1     <- same thread!

Correct: put the @Async method in a different class and make it public.

@Async and transaction management

The transaction context is thread-bound. When @Async hands the work to another thread, the transaction does not travel with it.

CaseWhat happens
1. A @Transactional caller calls an @Async methodThe transaction context is not transferred from the caller thread to the new thread. The async method does not run inside the caller's transaction.
2. @Async and @Transactional on the same methodUse with care: a new thread is created and has its own transaction management, but the context is not the same as the parent thread's, so propagation will not behave as expected (REQUIRED will not join the caller's transaction).
3. @Async method calling a @Transactional method of another beanThat inner method gets its own, new transaction on the async thread. This is the clean pattern: async outside, transaction inside.

Return type of an @Async method

An async method can return void, Future or CompletableFuture. (A plain String would be pointless: the caller would not have it yet.)

Using Future

@Component
public class UserService {
    @Async
    public Future<String> performTaskAsync() {
        return new AsyncResult<>("async task result");
    }
}

@GetMapping(path = "/getUser")
public String getUser() {
    Future<String> result = userService.performTaskAsync();
    String output = null;
    try {
        output = result.get();             // blocks until the task is done
        System.out.println(output);
    } catch (Exception e) {
        System.out.println("some exception");
    }
    return output;
}
Future methodPurpose
boolean cancel(boolean mayInterruptIfRunning)Attempts to cancel the task. Returns false if it cannot be cancelled (typically because it already completed), true otherwise.
boolean isCancelled()True if the task was cancelled before it completed.
boolean isDone()True if the task completed: by normal termination, an exception or cancellation.
V get()Waits if required for completion, then retrieves the result.
V get(long timeout, TimeUnit unit)Waits at most the given period; throws TimeoutException if the task is still not completed.

Using CompletableFuture (Java 8)

@Async
public CompletableFuture<String> performTaskAsync() {
    return CompletableFuture.completedFuture("async task result");
}

CompletableFuture<String> result = userService.performTaskAsync();
String output = result.get();              // or chain: result.thenApply(...).thenAccept(...)

Prefer CompletableFuture: it can be composed without blocking (thenApply, thenCombine, exceptionally). AsyncResult is deprecated in recent Spring versions.

Exception handling

Method returns a Future / CompletableFutureMethod returns void
The exception is carried inside the future. The caller gets it when calling get() (wrapped in ExecutionException) and can catch it there.The caller has already moved on, so there is nobody to catch the exception. It must be handled in the async thread.

For a void async method there are two options:

  1. Handle it inside the async method itself with try/catch. 
    @Async
public void performTaskAsync() {
    try {
        int i = 0;
        System.out.println(5 / i);
    } catch (Exception e) {
        // handle or log
    }
}
  2. Implement a custom AsyncUncaughtExceptionHandler through AsyncConfigurer: 
    @Configuration
public class MyAsyncConfig implements AsyncConfigurer {

    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return new CustomAsyncExceptionHandler();
    }
}

class CustomAsyncExceptionHandler implements AsyncUncaughtExceptionHandler {
    @Override
    public void handleUncaughtException(Throwable ex, Method method, Object... params) {
        System.out.println("in default Uncaught Exception method");
    }
}

If we do not handle it at all, Spring's default SimpleAsyncUncaughtExceptionHandler is used: it only logs the error.

public class SimpleAsyncUncaughtExceptionHandler implements AsyncUncaughtExceptionHandler {
    public void handleUncaughtException(Throwable ex, Method method, Object... params) {
        if (logger.isErrorEnabled()) {
            logger.error("Unexpected exception occurred invoking async method: " + method, ex);
        }
    }
}
Interview corner
Why does my @Async method run on the same thread?

Self-invocation (called from the same class) or a non-public method, so the proxy never intercepts it. Also check that @EnableAsync is present.

Is the caller's transaction available inside an @Async method?

No. Transactions are bound to a thread; the async thread has its own.

How do you handle exceptions from a void @Async method?

try/catch inside, or an AsyncUncaughtExceptionHandler.

Future vs CompletableFuture?

Future only allows blocking get(). CompletableFuture (Java 8) adds non-blocking composition and exception callbacks.
