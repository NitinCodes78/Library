Spring Boot Security: OAuth2 / OIDC Login

Third-party login ("Login with Google/GitLab/Auth0") using the authorization code flow, what Spring does internally, and how to make it stateless.

What is OAuth 2.0

  • An open authorization framework that enables secure third-party access to user-protected data (like "Sign up with Google / Facebook").
  • It has different grant types: Authorization Code, Implicit (legacy, avoid), Client Credentials and so on.

Quick recap of the Authorization Code grant (an Instagram-like third-party app wants the user's Gmail data):

The user clicks login/connect in the client → 2. client redirects the user to the authorization server (client id, scope, redirect uri, state) → 3. the user logs in and gives consent → 4. authorization server redirects back to the client's redirect URI with an authorization code → 5. the client calls the token endpoint with the code + client id + client secret → 6. it gets the access token (and refresh/ID token) → 7. the client calls the resource server with the access token → 8. the resource server validates the token and returns the data

Step 1: register the third-party app with the authorization server

Our Spring Boot app is the third-party app. It registers itself with the authorization servers (Auth0, GitLab and so on) and gets a Client ID and Client Secret. Registration needs the app name, the callback (redirect) URL such as http://localhost:8080/login/oauth2/code/gitlab, and the scopes (openid, and so on). Store the secret securely: it is shown only once.

The part after registration. (gitlab, auth0) is the registration id. Well-known providers (Google, GitHub, Facebook, Okta) have built-in defaults, and with an issuer-uri Spring can auto-discover the other endpoints.

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .csrf(csrf -> csrf.disable())
            .oauth2Login(Customizer.withDefaults());
        return http.build();
    }
}

Let us try

  1. Notice that we have not created any user in our Spring Boot app.
  2. Start the server and type localhost:8080: it takes us to the /login endpoint, showing "Login with OAuth 2.0" and the two authorization servers we added in application.properties (Auth0 and GitLab).
  3. Clicking Auth0 redirects to the Auth0 login page ("Log in to ... to continue to My SpringBoot App"). After sign-in and consent we land on localhost:8080: "hello, you are logged in".
  4. Now any other API (/users) works without signing in again.

With just pom.xml, application.properties and SecurityConfig.java we ran the complete OAuth2 flow: Spring Security provides the full OAuth2 client functionality; we do not code anything.

The twist

When we call /users from Postman (not the browser), it takes us back to the login page. Why? Because Spring Boot assumes OAuth2 login happens in a browser, so by default it creates a session; Postman has no session cookie.

What happens internally

  1. Login page. A request to / goes to /login. The DefaultLoginPageGeneratingFilter (generateLoginPageHtml()) builds the page listing the authorization servers; the list is filled at startup from the registrations in application.properties.
  2. Authorization request. The user clicks one; /oauth2/authorization/{registration_id} is invoked (the registration id is auth0 or gitlab as configured). OAuth2AuthorizationRequestRedirectFilter builds the authorization request and redirects the user to the provider's authorization-uri with the client id, scope, redirect uri and a state value.
  3. Login and consent at the authorization server. Then it calls our redirect URI http://localhost:8080/login/oauth2/code/auth0 with the authorization code (and the state).
  4. Code exchange. OAuth2LoginAuthenticationFilter handles this redirect. It creates an OAuth2LoginAuthenticationToken (an Authentication object) and calls the AuthenticationManager. Because our scope includes openid, the OidcAuthorizationCodeAuthenticationProvider handles it: it invokes the provider's token-uri passing the code, client id and client secret, and gets back the access token and ID token (and refresh token if any), then builds a fully authenticated object with the user's details.
  5. Store. The tokens and user details are saved (the authorized client in InMemoryOAuth2AuthorizedClientService, keyed by registration id + unique user name), the Authentication is placed in the SecurityContextHolder, and an HttpSession is created (the session id goes back in a cookie).
  6. Later requests. The browser sends the session cookie, SecurityContextHolderFilter loads the SecurityContext through HttpSessionSecurityContextRepository, and the request is authenticated.

Observations on the tokens: the access token is not a JWT (a JWT has three parts separated by dots), so it is opaque. The ID token is a JWT, and its payload carries everything required to authenticate the user (iss, sub, aud, exp, iat, and the profile data if profile was requested).

Problem: it is stateful

  • That is why Postman asked for login again: the session id was not set in a cookie.
  • While the session is valid, the token is not validated again on every request, so the ID token could be invalidated while the session is still active.
  • It also makes OAuth login stateful.

Fix: make it stateless

  • Set SessionCreationPolicy.STATELESS.
  • Return the ID token in the response after login.
  • With each request the client passes the token and we validate the token.

The parent class of OAuth2LoginAuthenticationFilter has onAuthenticationSuccess(), which by default cleans up and redirects once authentication completes. We override it with a custom success handler that writes the ID token into the response body:

@Component
public class CustomOAuth2SuccessHandler implements AuthenticationSuccessHandler {
    @Override
    public void onAuthenticationSuccess(HttpServletRequest request, HttpServletResponse response,
                                        Authentication authentication) throws IOException {
        OidcUser user = (OidcUser) authentication.getPrincipal();
        String idToken = user.getIdToken().getTokenValue();
        response.setContentType("text/plain");
        response.getWriter().write(idToken);               // client keeps this and sends it as Bearer token
    }
}

A new filter validates the token on every request, in place of the session:

public class OAuthValidationFilter extends OncePerRequestFilter {
    private final OAuthTokenValidatorUtil tokenValidatorUtil;

    @Autowired
    public OAuthValidationFilter(OAuthTokenValidatorUtil tokenValidatorUtil) {
        this.tokenValidatorUtil = tokenValidatorUtil;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain filterChain) throws ServletException, IOException {
        String token = extractJwtFromRequest(request);
        if (token != null) {
            String username = tokenValidatorUtil.isTokenValid(token);
            if (StringUtils.isNullOrEmpty(username)) {
                response.sendError(HttpServletResponse.SC_UNAUTHORIZED, "Invalid or expired token");
                return;
            }
            Authentication auth = new UsernamePasswordAuthenticationToken(username, null, List.of());
            SecurityContextHolder.getContext().setAuthentication(auth);
        }
        filterChain.doFilter(request, response);
    }

    private String extractJwtFromRequest(HttpServletRequest request) {
        String bearerToken = request.getHeader("Authorization");
        if (bearerToken != null && bearerToken.startsWith("Bearer ")) return bearerToken.substring(7);
        return null;
    }
}

// utility that validates the token against the provider's published keys (JWK set)
@Component
public class OAuthTokenValidatorUtil {
    public String isTokenValid(String accessToken) {
        String issuer = getIssuerFromToken(accessToken);
        JwtDecoder decoder = JwtDecoders.fromIssuerLocation(issuer);   // fetches the issuer's keys (jwks)
        Jwt jwt = decoder.decode(accessToken);                         // verifies signature, expiry, issuer
        if (jwt != null) return (String) jwt.getClaims().get("sub");
        return null;
    }
}

One safety point: the issuer must not be trusted just because the token says so (an attacker could name their own issuer). Check iss against a fixed list of trusted issuers (the ones configured in application.properties) before building the decoder, or configure the decoder with the known issuer directly. Then the security config:

@Configuration
@EnableWebSecurity
public class SecurityConfig {
    @Autowired private OAuthTokenValidatorUtil tokenValidatorUtil;

    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http,
                                                   CustomOAuth2SuccessHandler successHandler) throws Exception {
        http.authorizeHttpRequests(auth -> auth.anyRequest().authenticated())
            .sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(csrf -> csrf.disable())
            .oauth2Login(oauth -> oauth.successHandler(successHandler))
            .addFilterBefore(new OAuthValidationFilter(tokenValidatorUtil), UsernamePasswordAuthenticationFilter.class);
        return http.build();
    }
}

Now after logging in via Auth0 the browser shows the ID token; in Postman GET /users with Bearer Token set to it returns 200 OK with "fetched the details of successfully".

Good to know
  • The same stateless result is available out of the box with spring-boot-starter-oauth2-resource-server: http.oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults())) with spring.security.oauth2.resourceserver.jwt.issuer-uri validates provider-issued JWTs for you. Note the resource server expects an access token meant for your API (audience); an ID token is intended for the client app.
  • Use the authorization code flow with PKCE for public clients (SPAs, mobile); the implicit grant and the password grant are deprecated in OAuth 2.1.
  • Client credentials is the machine-to-machine grant: no user, the app authenticates itself with client id/secret and gets an access token.
  • The state parameter protects the redirect against CSRF; never skip it.
Interview corner
OAuth 2.0 vs OpenID Connect?

OAuth 2.0 is about delegated authorization (access tokens); OIDC adds authentication on top (ID token, openid scope, userinfo).

Walk through the authorization code flow.

Redirect to the authorization server, user consents, redirect back with a code, the backend exchanges the code (plus client secret) for tokens, then uses the access token on the resource server.

Why is the authorization code exchanged at the back channel?

So the tokens and client secret never pass through the browser/URL.

Why did the same call fail in Postman but work in the browser?

Spring's OAuth2 login is session-based by default; Postman had no session cookie. Make it stateless and send the token.

What is an opaque token?

A random string with no readable content; only the authorization server can validate it (introspection endpoint).
