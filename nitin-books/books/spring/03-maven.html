Maven

The build tool behind every Spring Boot project: pom.xml, the build lifecycle and how it produces your jar.

What is Maven?

  • A project management tool. It helps developers with build generation, dependency resolution, documentation and so on.
  • Maven uses a POM (Project Object Model) to do this.
  • When the mvn command is run, it looks for pom.xml in the current directory and reads the configuration it needs.

Understanding pom.xml

ElementWhat it does
<project ...> and <modelVersion>Specifies the XML schema and makes sure the file follows the structure and version Maven expects
<parent>The parent project whose configuration this project inherits (here spring-boot-starter-parent, which in turn inherits from the Maven Super POM). If no parent is given, Maven inherits from the Super POM by default
groupId + artifactId + versionThe unique identifier of your project
<properties>Key-value pairs for configuration (like java.version) that can be referenced anywhere in the pom
<repositories>Where Maven looks to download the project dependencies (the artifacts / jars). Default is Maven Central
<dependencies>Where we declare the libraries our project relies on
<build><plugins>Plugins used during the build, e.g. spring-boot-maven-plugin

Maven build lifecycle

Validateproject structure ok?Compilesource codeTestunit testsPackagejar / warVerifyintegrity of the packageInstallinto local repositoryDeployto remote repository
  • If you run the package phase, all the phases before it are executed first.
  • If you run one specific goal of a phase, all the goals of the previous phases plus the goals of that phase defined before it will run first.

Validate: mvn validate

Maven already defines the validate phase and its goal. To attach extra work to a phase, add a plugin in the <build> element and bind its goal to that phase, for example a Checkstyle check:

<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-checkstyle-plugin</artifactId>
    <version>3.1.2</version>
    <executions>
        <execution>
            <id>validate-checkstyle</id>
            <phase>validate</phase>
            <goals><goal>check</goal></goals>
        </execution>
    </executions>
    <configuration>
        <configLocation>myCodeStyle.xml</configLocation>
    </configuration>
</plugin>

Compile: mvn compile

Validates and compiles the code and puts the classes under ${project.basedir}/target/classes. The log shows the resources plugin copying src/main/resources, then the compiler plugin running javac. If nothing changed it prints "Nothing to compile - all classes are up to date".

Test: mvn test

Runs the unit tests (through the Surefire plugin and JUnit) against the compiled code. A line like Tests run: 1, Failures: 0, Errors: 0, Skipped: 0 followed by BUILD SUCCESS means it passed.

Package: mvn package

First validate, compile and test run, and then the package phase generates the .jar or .war file. After mvn package, the target folder contains:

  • learningspringboot-0.0.1-SNAPSHOT.jar: the runnable "fat" jar built by the Spring Boot plugin.
  • learningspringboot-0.0.1-SNAPSHOT.jar.original: the plain jar before Spring Boot repackaged it.
java -jar target/learningspringboot-0.0.1-SNAPSHOT.jar

Install and Deploy

  • mvn install: installs the package into your local repository (~/.m2) so other local projects can use it.
  • mvn deploy: copies the package to a remote repository (like Nexus or Artifactory) for other developers.
Good to know
  • mvn clean belongs to a separate clean lifecycle: it deletes the target folder. mvn clean install is the common combination.
  • Dependency scope matters: compile (default), test (only for tests, like spring-boot-starter-test), provided (the runtime supplies it, e.g. servlet API in an external Tomcat) and runtime.
  • Run the app straight from Maven during development with mvn spring-boot:run.
Interview corner
Name the Maven default lifecycle phases in order.

validate, compile, test, package, verify, install, deploy.

What is the difference between install and deploy?

install copies the artifact to your local .m2 repository; deploy pushes it to a remote shared repository.

What does spring-boot-starter-parent give you?

Managed versions of many dependencies (so you omit versions), sensible plugin and Java defaults, and resource filtering.

How do you resolve a dependency version conflict?

Inspect with mvn dependency:tree, then exclude the unwanted transitive dependency or pin the version in dependencyManagement.
