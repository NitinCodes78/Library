@Transactional: Part 1

Why we need transactions, ACID, and how Spring turns one annotation into begin, commit and rollback using AOP.

The critical section problem

A critical section is a code segment where shared resources are accessed and modified.

// Book a car with id 1001
Read the car row with id 1001
If status is Available:
    Update it to Booked

When multiple requests reach this section at the same time, two users can both read "Available" and both book the car: data inconsistency. The solution is a transaction, which gives us the ACID properties.

LetterPropertyMeaning
AAtomicityAll operations in the transaction complete, or none do. If any operation fails, the entire transaction is rolled back.
CConsistencyThe database state before and after the transaction is consistent (all rules and constraints hold).
IIsolationEven when many transactions run in parallel, they do not interfere with each other.
DDurabilityOnce committed, the data is never lost, even after a crash.
BEGIN_TRANSACTION;
  Debit from A
  Credit to B
  if all success:  COMMIT;
  else:            ROLLBACK;
END_TRANSACTION;

Using @Transactional in Spring Boot

  1. Add the dependency. For a relational database that is Spring Data JPA, which lets you talk to the database without writing much code (a database driver dependency is also needed, covered later): 
    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
</dependency>
  2. Activate transaction management with @EnableTransactionManagement on the main class. Spring Boot auto-configures it, so you normally do not need to add it.
@SpringBootApplication
@EnableTransactionManagement      // optional with Spring Boot
public class SpringbootApplication {
    public static void main(String[] args) { SpringApplication.run(SpringbootApplication.class, args); }
}

Class level vs method level

On the class

The transaction applies to all public methods of the class.

@Transactional
public class User {
    public void a() { }
    public void b() { }
    private void c() { }   // not transactional
}

On a method

The transaction applies to that method only.

public class User {
    @Transactional
    public void updateUser() { }
    public void other() { }
}

How does it work? AOP again

Transaction management in Spring Boot is built on AOP.

  1. A pointcut expression finds methods carrying @Transactional, like @within(org.springframework.transaction.annotation.Transactional).
  2. Once it matches, an @Around advice runs. That advice is the method invokeWithinTransaction in the TransactionInterceptor class.
@RestController
@RequestMapping(value = "/api/")
public class UserController {
    @Autowired User user;

    @GetMapping(path = "/updateUser")
    public String updateUser() {
        user.updateUser();
        return "user is updated successfully";
    }
}

@Component
public class User {
    @Transactional
    public void updateUser() {
        System.out.println("UPDATE QUERY TO update the user db values");
    }
}

What the proxy effectively does around updateUser():

// inside invokeWithinTransaction (simplified)
BEGIN_TRANSACTION;
try {
    // YOUR TASK: updateUser() body runs here
    COMMIT;                         // all success: commit the transaction
} catch (Throwable ex) {
    ROLLBACK;                       // exception: rollback (per the rollback rules)
    throw ex;
}

Rollback rules (a favourite question)
  • By default Spring rolls back on unchecked exceptions (RuntimeException) and Error. A checked exception does not trigger rollback unless you ask: @Transactional(rollbackFor = Exception.class).
  • If you catch the exception inside the method and swallow it, the proxy never sees it, so it commits.
  • Self-invocation (one method calling another @Transactional method of the same class) bypasses the proxy, so no new transaction starts.
  • Only public methods are proxied by default.

Interview corner
How does @Transactional work internally?

Spring creates a proxy around the bean (AOP). The proxy's TransactionInterceptor begins a transaction before the method, commits on success and rolls back on a qualifying exception.

Does a checked exception roll back the transaction?

Not by default. Use rollbackFor.

Why does @Transactional not work on a method called from the same class?

Self-invocation skips the proxy.

What is ACID?

Atomicity, Consistency, Isolation, Durability.
